## 입문 다음의 질문까지

C 문법을 익힌 뒤에도 실제 프로그램을 만들 때는 새로운 질문이 생긴다.
버퍼가 가득 차면 거절할지 늘릴지, 함수가 돌려준 포인터는 언제까지 유효한지,
파일을 나누면 무엇을 공개하고 무엇을 숨길지 결정해야 한다.

이 책은 **기계의 표현 → C의 타입과 수명 → 오류와 계약 → 라이브러리와 프로젝트 설계**로
그 질문들을 연결한다. 여기서 계약은 함수의 입력 조건, 결과, 실패했을 때의 약속이다.

| 입문 이후의 질문 | 책에서 다루는 내용 |
| --- | --- |
| 메모리는 누가 얻고 누가 해제하는가? | 수명·소유권·할당기, 수명이 같은 메모리를 묶어 관리하는 아레나 |
| 문자열과 배열의 크기는 어떻게 관리하는가? | 길이와 용량, 데이터를 복사하지 않고 가리키는 뷰, 컨테이너 |
| 함수가 실패하면 무엇이 남는가? | 오류를 값으로 반환하기, 실패 시 원래 상태를 보존하는 설계 |
| 같은 문제를 다르게 설계하면 무엇이 달라지는가? | [간이 JSON의 세 구현](docs/ko/ch100.html): 순수 C, proven, 중첩을 다루는 명시적 스택 |
| 여러 파일을 하나의 프로젝트로 어떻게 관리하는가? | [빌드와 시험](docs/ko/ch102.html): 헤더·의존성·공개와 내부의 경계·회귀 시험 |

C로 개발을 계속하고 싶은 독자에게는 이 연결이 다음 단계의 바탕이 된다.
C++는 목적과 도구에 따라 선택하는 다른 언어이며, C 학습의 필수 다음 과정은 아니다.
이 책은 C 안에서 메모리·오류·모듈을 어떻게 설계할지 다룬다.

## 누구에게, 어떻게 읽히는 책인가

- **프로그래밍이 처음이라면:** 앞에서부터 읽는다. 첫 두 부에서는 기계와 표현에
  익숙해지고, 제3부의 [헬로 월드](docs/ko/ch16.html)에서 첫 프로그램을 만난다.
- **C 입문서를 마쳤다면:** 포인터·수명·변환을 다시 확인하고, 제12부의 라이브러리
  설계와 [프로젝트 구성](docs/ko/ch102.html)으로 이어 읽을 수 있다. 장마다 선수 지식이 적혀 있다.
- **이미 C를 쓰고 있다면:** 헷갈렸던 규칙과 설계 선택을 필요한 장에서 찾아 읽는다.
  장 사이의 의존 관계와 용어 대조표가 돌아볼 곳을 안내한다.

각 장은 「먼저 알아야 할 것 → 돌아보기 → 이 장이 끝나면 → 이 장에서 답할 질문」으로
열린다. 설명 사이에 문답·흔한 오해·실제 사례·반례를 두어, 규칙이 성립하는 조건과
그 조건을 어겼을 때의 차이를 함께 읽게 했다.

**읽기 중심의 책이며 연습문제는 없다.** 처음부터 읽는다면 첫 프로그램 앞에
열다섯 장의 배경 설명이 있다. 코드부터 보고 싶다면 헬로 월드를 먼저 살펴보고,
낯선 개념은 앞 장으로 돌아가 읽어도 좋다.

게임·GUI·서버를 완성하는 분야별 제작 교재는 아니다. 그런 프로그램에 필요한
메모리 관리와 오류 처리, 빌드·시험의 기반을 다루며, 분야별 도구와 직접 만드는 경험은
그다음에 더해야 한다.

## proven으로 배우는 설계 습관

제12부는 [proven C 라이브러리](https://github.com/rubidus-api/proven_c_lib)를 사례로
C의 반복되는 문제를 공통 API로 다루는 방법을 보여 준다. C23의 새 기능뿐 아니라
**메모리의 출처, 값의 수명, 실패 후의 상태를 코드에 드러내는 관습**을 다룬다.

- **할당기를 명시한다.** 함수에 전달하거나 객체에 보관해 메모리를 어디서 얻을지 정한다.
- **소유와 빌림을 구분한다.** 길이를 지닌 뷰로 복사를 줄이고, 원본을 언제까지 살려 둘지 설명한다.
- **실패 정책을 나눈다.** 고정 용량에서 거절할지, 일부만 처리할지, 용량을 늘릴지 API로 구분한다.
- **같은 문제를 비교한다.** 간이 JSON 예제에서 크기 검사·오류 처리·복사가 어떻게 달라지고,
  대신 어떤 수명 의무가 생기는지 살펴본다.

이 관습은 proven을 쓰지 않는 코드에도 적용할 수 있다. 라이브러리를 외우는 데서
끝내지 않고, 자기 함수와 자료구조의 약속을 정하는 데 연결하는 것이 이 부의 목적이다.

proven은 호출자의 수명 위반이나 잘못된 할당기 사용을 모두 막아 주지는 않는다.
함께 실린 판의 검증 범위와 도입 시 고려할 점은
[proven 소개](docs/ko/ch91.html)와 [라이브러리의 경계](docs/ko/ch99.html)에 설명한다.

부록은 열일곱이다. 조회용 다섯(연산자, `printf`·`scanf` 서식, 암묵 변환, 더

그리고 기계 쪽을 다루는 묶음 — 덤프 읽기, 실행 파일 형식, OS 없이 도는 C, 부팅,
장치를 잇는 선, 디스크의 배치, 재어 보는 기계, **기억을 다스리는 장치들**이 있다.

## 이 책이 다른 점

- **실행 결과를 예제에서 가져온다.** 지면에 실리는 예제 223개의 실행 결과는
  검증 스크립트가 캡처한다. GCC 14 기준 전수 검증과 Clang 19 교차 검증을 기록하며,
  교차에서 건너뛴 7건의 이유는 [건너뜀 목록](docs/example-cross-skip.tsv)에 남긴다.
- **표준의 규칙과 실측을 구분한다.** 최적화 수준에 따라 달라지는 실행이나
  메모리 접근 비용을 코드로 확인하고, 관찰한 환경을 밝힌다. 특정 기계에서 나온
  결과가 모든 C 구현의 약속은 아니라는 점도 함께 설명한다.
- **C23을 기본값으로 설명한다.** `bool`·`nullptr`·`[[noreturn]]`·
  `<stdckdint.h>`를 필요한 문맥에서 배우고, 기존 코드의 관행과 차이를 살펴본다.
- **두 판을 함께 낸다.** 한국어판과 영어판, 그리고 예제까지 판마다 갈라
  둔다(영어판은 주석과 출력 문구가 영어인 `examples-en/` 트리). 두 트리 모두
  매 빌드마다 전수 검증한다.
- **AI를 보조 도구로 삼아 집필했다.** 구성·방침·수록 여부는 저자가 정하고
  검토했다. 실행 예제와 지면의 코드 조각에는 각각 검사를 적용하며, 서술의 정확성과
  오류 수정의 책임은 저자에게 있다.

> **검증이 뜻하는 범위.** 위의 검증은 *예제가 이 환경에서 빌드되고 돌며, 지면의
> 출력이 그 실행에서 나왔다*는 사실까지다(x86-64 리눅스, GCC 14.2 기준 전수 ·
> Clang 19.1 교차, 건너뜀 7건). 이는 책의 모든 서술에 대한 표준 적합성 감사도,
> 보안 감사도, 대규모 실사용 검증도 아니다. 서술의 근거는 표준 조항과 1차 자료로
> 따로 대며, 함께 실린 proven 라이브러리의 검증 범위와 한계는 위의 소개·경계
> 장에 설명한다.

## 장 사이의 의존 관계

각 장 서두의 「먼저 알아야 할 것」이 곧 의존 선언이라, 그것을 그대로 뽑아 관계도로
그린다. 관계도는 *원고에서 생성하며*, 원고의 의존 선언이 바뀌면 다시 만든다.

[![장 사이의 의존 관계](docs/dependency-graph.svg)](docs/DEPENDENCIES.md)

가로축에는 장을 순서대로 놓고, 호 하나가 의존 하나다 — 왼쪽(기댄 곳)에서
오른쪽(그 장)으로 걸린다. 호가 길수록 멀리서 끌어오는 것이고, 점이 클수록 여러
장이 그 장에 기댄다. 뒤 장에 기대는 자리가 있으면 붉은 점선으로 드러난다.

- 표로 보기 — [DEPENDENCIES.md](docs/DEPENDENCIES.md) · [English](docs/DEPENDENCIES-en.md)
- 더 잔 눈금 — [절 단위 지도](docs/SECTIONS.md): 절별 앞질러 참조·난이도·성격·분량
- 용어 — [한국어–영어 대조표](docs/TERMS.md): 개념어와 그 정의 장
- 다시 만들기 — `python3 scripts/make-depgraph.py`, `scripts/section-map.py`, `scripts/check-terms.py`

## 예제 직접 돌려 보기

본문에 실린 예제는 전부 이 저장소에 있고, 한 번에 빌드·실행해 볼 수 있다.

```sh
scripts/verify-examples.sh              # 한국어판 예제 전수 빌드 + 실행 + 출력 캡처
scripts/verify-examples.sh examples-en  # 영어판 예제 트리
CC=clang scripts/verify-examples.sh     # 다른 컴파일러로 교차 검증
```

- C23 컴파일러가 필요하다. *실제로 재 본 것은* GCC 14.2(전수 통과)와 Clang 19.1(7건
  건너뜀)이다 — 그 아래 판은 시험하지 않았으므로 통과를 약속하지 않는다.
- `#include <proven...>`을 쓰는 예제는 `vendor/proven`이 자동으로 함께
  빌드된다.

> 원고(Typst 소스)와 조판 스크립트는 공개하지 않는다. 저장소의 `scripts/`에는
> 예제 검증과 점검 도구만 둔다. 이 저장소가 담는 것은 완성된 책(PDF·HTML)과
> 예제 코드다.
