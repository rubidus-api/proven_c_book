Looking back

Chapter 26 read input with fgets and parsed it with sscanf, and chapter 76 said sscanf does not tell you “where and why it failed”. Then what is the most accurate way to turn one string into an integer?

A. The strtol family. This function tells three things at once — the converted value, where it stopped (the end pointer), and whether the range was exceeded (errno being ERANGE). atoi tells none of them. Its name is short so it appears often in introductions, but it is a function not used in the field.

The need for this chapter, and its context

As a drawer holds odds and ends, so does this header. Still there is a reason for placing this chapter here: dynamic allocation from chapter 46 and reporting failure from chapter 55 both live here, so two threads already learned can be pulled at once.

By the end of this chapter

A drawer named, exactly as it says, “the standard library”. Functions that turn strings into numbers, random numbers, dynamic allocation, program termination, sorting and binary search are all in here together. In place of anything in common there are many traps — in particular conversion functions with no way to report failure and the subtle differences between the terminating functions are this chapter’s two axes.

81.1 Conversion — why atoi is abandoned#

examples-en/stdlib-h/convert.c

#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <limits.h>
#include <string.h>

/* Ways of turning a string into a number, and the difference between them */
static void try_atoi(const char *s)
{
    printf("  atoi(\"%s\") = %d\n", s, atoi(s));   /* it has no way of reporting failure */
}

static void try_strtol(const char *s)
{
    errno = 0;
    char *end;
    long v = strtol(s, &end, 10);

    if (end == s)                 printf("  strtol(\"%s\"): not a number\n", s);
    else if (errno == ERANGE)     printf("  strtol(\"%s\"): out of range (ERANGE)\n", s);
    else if (*end != '\0')        printf("  strtol(\"%s\"): %ld, characters left over [%s]\n", s, v, end);
    else                          printf("  strtol(\"%s\"): %ld (whole)\n", s, v);
}

int main(void)
{
    const char *cases[] = { "42", "abc", "42abc", "99999999999999999999", " 7", "" };

    printf("atoi — failure and 0 cannot be told apart:\n");
    for (size_t i = 0; i < sizeof cases / sizeof cases[0]; i++) try_atoi(cases[i]);

    printf("strtol — it tells you what went wrong:\n");
    for (size_t i = 0; i < sizeof cases / sizeof cases[0]; i++) try_strtol(cases[i]);

    printf("LONG_MAX = %ld\n", LONG_MAX);
    return 0;
}

Output

atoi — failure and 0 cannot be told apart:
  atoi("42") = 42
  atoi("abc") = 0
  atoi("42abc") = 42
  atoi("99999999999999999999") = -1
  atoi(" 7") = 7
  atoi("") = 0
strtol — it tells you what went wrong:
  strtol("42"): 42 (whole)
  strtol("abc"): not a number
  strtol("42abc"): 42, characters left over [abc]
  strtol("99999999999999999999"): out of range (ERANGE)
  strtol(" 7"): 7 (whole)
  strtol(""): not a number
LONG_MAX = 9223372036854775807

Put the output side by side and the difference is clear.

  • atoi("abc") is 0. But atoi("0") is 0 too — failure and success cannot be distinguished.
  • atoi("42abc") is 42. It quietly ignores the trailing rubbish.
  • atoi("99999999999999999999") came out as −1. The standard says only that this case is undefined behaviour — −1 came out by accident; any value at all could come out and nothing is guaranteed.

strtol distinguished, for the same inputs, “not a number”, “characters left over” and “out of range” separately. The checking code looks long, but that length is precisely the real complexity of handling a string that came from outside.

Counter-example. Reading user input with atoi

int port = atoi(argv[1]);      /* "0" and "bad input" are the same value */

Mended, it goes like this.

errno = 0;
char *end;
long v = strtol(argv[1], &end, 10);
if (end == argv[1] || *end != '\0') { /* not a number */ }
else if (errno == ERANGE || v < 1 || v > 65535) { /* out of range */ }
else port = (int)v;

Setting errno to 0 just before the call is the convention (chapter 90). Without it you read the value a previous call left behind.

Conversion to floating point is the same. atof cannot report failure, while strtod gives an end pointer and ERANGE. And strtod may, according to the locale, read the decimal point as , rather than . (chapter 82) — a point always to be remembered when parsing a data format.

Q. Why does qsort take its comparison through two void * — would knowing the type not be faster?

A. Because the standard library must sort an array of any type at all. C has no generics, so the only passage that erases a type is void * (chapter 36), and the price is a cast and a dereference inside the comparator every time. The price is not only speed. Where the type has been erased, a mistake gets no help from the compiler: pass the wrong element size, or write a comparator that takes int where it must take int*, and it collapses quietly. That is why chapter 113’s proven_array_sort pins the type with a macro, and why chapter 106 counts “the unchecked callback” among the five bugs.

81.2 Dynamic allocation — five functions and their contracts#

We organise what chapter 46 taught, function by function.

This is where calloc’s multiplication check pays off. malloc(k * n) may have the product wrap round as seen in chapter 57, but for calloc(k, n) the standard requires the implementation to check for overflow and return null. If sizes must be multiplied, calloc is the safer choice.

Counter-example. Assigning realloc’s return value straight to the original

buf = realloc(buf, new_size);   /* on failure the original address is lost → a leak */
if (!buf) return -1;

The correct idiom goes through a temporary variable.

char *tmp = realloc(buf, new_size);
if (!tmp) { /* buf is still valid — it can be cleaned up or still used */ return -1; }
buf = tmp;

It is why chapter 79’s line-reading example used this idiom.

realloc has two more peculiar rules. realloc(NULL, n) is the same as malloc(n), and realloc(p, 0) is not to be used. Its status changed from edition to edition — up to C17 it was implementation-defined and marked as deprecated, and in C23 it became outright undefined behaviour (proposal N2464). It is a place where implementations diverged so far that the standard gave up on settling it.

What this change leaves in practice is one line — to release, use free(p). Code that reallocates to a size that may become 0 must filter that case first.

proven_err_t resize(char **buf, size_t n) {
    if (n == 0) { free(*buf); *buf = nullptr; return OK; }  /* never pass 0 */
    char *tmp = realloc(*buf, n);
    ...
}

81.3 Termination — the difference between four ways#

The difference lies in the buffer. exit empties the streams while _Exit and abort do not — the “output vanishing” accident seen in chapter 79 happens here. It is also why the last log of a program dying by abort is not seen.

Functions registered with atexit are called in the reverse order of registration, and the standard guarantees registration of at least 32. Calling exit again inside a registered function is outside the contract.

81.4 Sorting and searching — qsort and bsearch#

Written out exactly, the contract of the two functions is this.

  • The comparator is int cmp(const void *a, const void *b) and returns a negative, zero or positive value. Making it by subtraction can overflow — return *x - *y; is wrong for large values. return (*x > *y) - (*x < *y); is the safe idiom.
  • The comparator must be a total order (chapter 106). If it is inconsistent the result is not merely jumbled — it can trespass outside the array.
  • qsort is not a stable sort. The relative order of equal values is not preserved. If it is needed, make the comparator also compare the original index to break ties.
  • Worst-case performance is settled by the implementation. The standard guarantees nothing — the reason a complexity attack, feeding the worst input to slow the sort down, is possible.
  • bsearch presumes a sorted array. If it is not sorted the result is meaningless.

81.5 Random numbers — the limits of rand#

rand returns a number from 0 to RAND_MAX. RAND_MAX is guaranteed only to be at least 32767, so if a larger range is needed it must be composed.

Counter-example. Making a range with rand() % n

int dice = rand() % 6 + 1;      /* the values are not even */

If RAND_MAX + 1 is not a multiple of n, the values at the front come out more often. If the range is small the bias is small too, but as n grows it becomes noticeable. On top of that, some old implementations had poor quality in the low bits, so % 2 even came out alternating.

If an even distribution is needed, use rejection sampling — throw away a value that exceeds the range and draw again. And never use it for secrets (Part XIV’s random number story).

Give no seed with srand and it is the same as srand(1) — the same sequence every time. srand(time(NULL)) is a common idiom, but two processes started in the same second get the same sequence.

81.6 The environment and processes#

getenv returns an environment variable, but that string must not be modified and may not be valid after a subsequent setenv-like call. If the value is needed, copy it.

system raises a shell and executes a command. If user input is mixed into that string it becomes command injection — the same class as the classic vulnerability of web applications. Within the standard there is no alternative, and the right answer is to use a platform API (posix_spawn, CreateProcess) and pass the arguments as an array.

In practice. A real bug made by subtraction in a qsort comparator

A comparator of the form return a - b; is the most common mistake in sorting code. If the values are near INT_MIN the subtraction overflows and the sign flips, and the sort quietly gives a wrong result — since the signed overflow learned in chapter 6 is outside the contract, the symptom even changes with the compiler’s optimisation.

This pattern has been reported repeatedly in kernels, databases and game engines alike, common enough that static analysis tools catch it with a rule of their own. The mend is one line — do not subtract, compare.
