97 From macro to keyword — bool, nullptr and their companions

What to know first

chapter 93, What the new standards added, and the *_s controversy · what the standards added
chapter 31, Booleans and comparison · the type of true and false

Looking back

Chapter 93 mentioned only in a table that C23 made <stdbool.h> effectively unnecessary and that nullptr came in. But why put into the language what worked fine as macros — is it not merely a change of name?

A. It is not merely a change of name. A macro is the preprocessor changing text and so has neither type nor scope, and the user can #undef it or define it again with another meaning. A keyword is a grammatical element of the language, so it has a type, can be diagnosed, and nobody can redefine it. Where that difference really prevents accidents is this chapter’s content — and nullptr in particular is not a renaming but a new type.

The need for this chapter, and its context

Placing C23’s changes to the language near the end of the library part may look odd. But bool and nullptr were for a long time macros in headers, and this is the story of their becoming keywords — so the boundary between library and language is where it belongs, after chapter 93’s “what the standard added” and the three chapters behind it (threads, atomics, checked arithmetic), and before the last two, on memory layout and the allocator.

By the end of this chapter

We treat the most conspicuous change C23 made to the language: why things long imitated with macros in headers — bool, true, false, static_assert, alignas, thread_local — rose to being keywords, what nullptr was newly made to prevent, what rules and limits come with them, and in what order to move existing code over.

The questions this chapter answers

  1. What format is used when printing a bool with printf?
  2. For a project that must keep compiling with an old standard, is this chapter somebody else’s story?

97.1 What was promoted#

examples-en/macro-to-keyword/keywords.c

/* What was promoted to a keyword in C23 — and what changed */
#include <stdio.h>

/* before the promotion these lines demanded <stdbool.h>, <stdalign.h>, <assert.h> */
static_assert(sizeof(int) >= 4, "this code assumes an int of 32 bits or more");

/* nullptr has a type of its own (nullptr_t) — it is neither 0 nor (void *)0 */
static void take_ptr(int *p) { printf("  pointer: %s\n", p ? "has a value" : "null"); }

/* the place where the difference between NULL and nullptr shows in variadic arguments */
static void print_all(const char *first, ...)
{
    printf("  %s ...\n", first);
}

int main(void)
{
    bool ready = true;                 /* a real keyword, neither _Bool nor a macro */
    printf("sizeof bool = %zu, true = %d, false = %d\n", sizeof(bool), true, false);
    printf("ready = %d, !ready = %d\n", ready, !ready);

    /* bool narrows every non-zero value to 1 — a property an int cannot imitate */
    bool  b = 42;
    int   i = 42;
    printf("bool b = 42 -> %d,  int i = 42 -> %d\n", b, i);

    int   x  = 7;
    int  *p  = &x;
    int  *np = nullptr;
    take_ptr(p);
    take_ptr(np);
    printf("nullptr compared with nullptr: %d,  with a pointer: %d\n", nullptr == nullptr, p == nullptr);

    /* typeof: it writes down a nameless type as it is */
    typeof(x) y = x * 2;
    printf("typeof(x) y = %d\n", y);

    /* constexpr: a real constant — usable as an array size and as a switch label */
    constexpr int LANES = 4;
    int lane[LANES];
    printf("constexpr LANES = %d, elements in the array = %zu\n", LANES, sizeof lane / sizeof lane[0]);

    print_all("pass nullptr in variadic arguments", nullptr);
    return 0;
}

Output

sizeof bool = 1, true = 1, false = 0
ready = 1, !ready = 0
bool b = 42 -> 1,  int i = 42 -> 42
  pointer: has a value
  pointer: null
nullptr compared with nullptr: 1,  with a pointer: 0
typeof(x) y = 14
constexpr LANES = 4, elements in the array = 4
  pass nullptr in variadic arguments ...

We organise it in one table. On the left is the shape up to C17, in the middle C23.

The headers still exist and including them is harmless — the principle that the standard does not break old code (chapter 79’s gets story) was kept here too. But newly written code has no reason to include them.

97.2 bool — what does it prevent#

C long had no true-false type. It was imitated with int, and every project had typedef int BOOL; and #define TRUE 1 rolling about. C99 brought in _Bool while <stdbool.h> attached a pretty name to it, and C23 raised that to a keyword.

What differs between bool and int is not the name but the conversion rule.

  • Every nonzero value is narrowed to 1. The example’s bool b = 42; printing 1 shows it. int i = 42 stays 42.
  • So comparing two truths is true. The classic bug of the int-imitation days vanishes here.

Counter-example. Comparing truth with 1

int a = isupper('A');      /* any nonzero value, depending on the implementation */
int b = isupper('B');
if (a == b) { … }          /* both are true, yet the values may differ, so the test can be false */
if (a == 1) { … }          /* worse */

As seen in chapter 82, the classification functions of <ctype.h> promise only “a nonzero value”. To compare truths, narrow to truth values rather than values.

bool a = isupper('A');     /* normalised to 1 here */
bool b = isupper('B');
if (a == b) { … }          /* safe */

Q. What format is used when printing a bool with printf?

A. There is no dedicated format. A bool goes over as a variadic argument and is promoted to int by the default argument promotions (chapter 67), so %d is used — the example did so. Printing words a human can read with %s and the ternary operator is a common practice too.

The place to beware is the scanf side. There being no format that takes a bool directly, it must be read into an int and then assigned. And sizeof(bool) is usually 1, but the standard does not promise it is 1 — do not assume this value when calculating a struct layout (chapter 47).

Two remaining traps of bool. First, using bool in a bit-field works fine even with a width of 1, but the layout is implementation-defined (chapter 47). Second, an array of bool uses one byte per element — it is not compressed into bits like C++‘s vector<bool>. To compress into bits, write the masks by hand (chapter 29) or use the tools of <stdbit.h>.

97.3 nullptr — not a renaming#

Chapter 4 distinguished the three nulls. NULL is a macro, and its definition is 0 or ((void *)0) depending on the implementation. This freedom bore real accidents.

Accident 1 — the size goes out of step in variadic arguments. A variadic function does not know the arguments’ types and so reads the bits as they came (chapter 67). On an implementation where NULL is defined as 0, writing execl("/bin/ls", "ls", NULL) sends an int 0, and on a machine where pointers are 8 bytes the upper 4 bytes remain as rubbish. The function, failing to recognise the end of the list, runs away. That is why old code had to write (char *)0. nullptr is always of pointer size, so it does not have this problem.

Accident 2 — whether it is an integer or a pointer blurs. On an implementation where NULL is 0, foo(NULL) is indistinguishable from passing the integer 0. In code that branches by type with _Generic (chapter 67), this ambiguity becomes an accident as it stands. nullptr has a type of its own called nullptr_t, so the branch is clear.

Accident 3 — going out of step with C++. C++ brought in nullptr first, in 2011, for the same reasons. There were places in headers crossing the two languages (chapter 60) where NULL’s meaning divided, and C23’s adopting the same word narrowed that gap.

A few rules to pin down. nullptr converts to any object pointer type and to a function pointer too (chapter 68). Two nullptrs, and a nullptr and any pointer, can be compared with == and !=. Converted to bool it is false. But it cannot be compared with an integer variable and does not convert to an integer — nullptr == n (with n a long variable) is subject to diagnosis; nullptr == 0 is allowed and true, since 0 is a null pointer constant. The language has, in effect, cut the old intuition that “a null pointer is the same thing as the integer 0”.

A common misconception. “Using nullptr reduces null-dereference accidents”

It is a different kind of problem. What nullptr prevents is accidents coming from the way null is written (size going out of step, type ambiguity), not accidents of dereferencing null. Confirming whether a pointer is null is still a human’s part (chapter 37), and reducing that burden is the part not of the language but of design — data structures that do not make nulls in the first place, conventions that report failure through the return value (Part XIV).

97.4 The remaining promotions and the new words#

static_assert — checks a condition at compile time and, if it is broken, translation fails. The example’s first line is that. It differs in character from the run-time assert (chapter 90) — this one is a tool asking “does this code hold on this machine”, used for pinning assumptions about type sizes, alignment and struct layout into the code. In C23 the message may be omitted.

alignas, alignof — the words for handling in the language the alignment seen in chapter 4. They are used to lay things out to fit a cache line (chapter 13’s avoidance of false sharing) or to meet an alignment the hardware requires.

thread_local — makes a variable that exists separately per thread. It is a tool for avoiding the problem of sharing seen in chapter 95 by not sharing. errno is in fact implemented this way (chapter 90).

constexpr — as seen in the example, it makes a real constant. A const int is not a constant expression and so could not be used for an array size or a case label (chapter 24), and that place long belonged to #define. constexpr reclaims that place with a typed name — this chapter’s theme of macros being promoted into the language is repeated here too.

typeof — takes an expression’s type down as it is. What had been used as a GCC extension for over thirty years became standard. It is especially handy when declaring a temporary variable inside a macro.

In practice. The story of the underscored names — why _Bool looks like that

Why was it not called bool from the start? Because if the standard makes a new keyword, all existing code already using that word as a name breaks. The world had mountains of code containing typedef int bool; or struct bool { … };.

So the standard uses names reserved so that users cannot use them (chapter 63’s table) — names beginning with one underscore and a capital letter. _Bool, _Static_assert, _Alignas, _Atomic (chapter 95) and _Generic are all products of this rule. And headers laid pretty names on top as macros, so that only those who included them used the short names. Nothing breaks in old code that did not include them.

C23’s promotion is the judgement that “enough time has passed that the short names may now be used”. Even so the underscored names are still alive, and the two names point at the same thing. It is a case where the standard’s habit of not breaking old code remains even in the names — the same character as chapter 79’s gets story, and a decision in the opposite direction.

97.5 Attributes — writing down intent the type cannot carry#

Where the promoted words reclaimed the ground of values and types, the attributes C23 brought in fill a different one — “do not throw this result away”, “the fall-through here is deliberate”: meaning that no type can hold. Until C23 such things could only be said through per-compiler extensions (__attribute__((warn_unused_result))).

examples-en/macro-to-keyword/attributes.c

/* C23 attributes - writing down intent the type system cannot carry */
#include <stdio.h>
#include <stdlib.h>

/* (1) nodiscard - a function whose result must not be thrown away.
   Put it on a function that reports failure by value and the standard
   recommends a diagnostic for a call that forgets the check; gcc and clang warn. */
[[nodiscard]] static int checked_add(int a, int b, int *out)
{
    if (b > 0 && a > 2147483647 - b) return 0;   /* overflow: failure */
    *out = a + b;
    return 1;
}

/* (2) maybe_unused - for things some build configurations do not use */
static void log_line([[maybe_unused]] const char *tag, const char *msg)
{
#ifdef VERBOSE
    printf("  [%s] %s\n", tag, msg);
#else
    printf("  %s\n", msg);
#endif
}

/* (3) noreturn - this one never comes back; the caller's next line is dead */
[[noreturn]] static void die(const char *why)
{
    printf("  fatal: %s\n", why);
    exit(EXIT_FAILURE);
}

static const char *classify(int n)
{
    switch (n) {
    case 0:
        printf("  zero, and it keeps going\n");
        [[fallthrough]];          /* (4) falling through on purpose */
    case 1:
        return "small";
    default:
        return "large";
    }
}

int main(void)
{
    int sum = 0;

    if (checked_add(2000000000, 2000000000, &sum))
        printf("  sum: %d\n", sum);
    else
        printf("  overflow refused\n");

    if (checked_add(2, 3, &sum))
        printf("  sum: %d\n", sum);

    log_line("main", "attributes carry intent, not types");
    printf("  classify(0) = %s\n", classify(0));
    printf("  classify(9) = %s\n", classify(9));

    if (sum != 5) die("checked_add lost a value");
    return 0;
}

Output

  overflow refused
  sum: 5
  attributes carry intent, not types
  zero, and it keeps going
  classify(0) = small
  classify(9) = large

The syntax is two brackets — [[name]], or [[name(argument)]]. It goes in front of whatever it decorates, down to a single parameter. The standard defines seven.

The first five came over from C++; the last two are C23’s own. Those two describe a function’s properties so the optimiser knows it need not make the same call twice, which puts them in a different family from the other five.

97.5.1 What an attribute does — measured#

An attribute does not change what the code does. It changes the diagnosis. Break three of them and the two compilers on this machine say this.1

gcc:   ignoring return value of 'check', declared with attribute
       'nodiscard' [-Wunused-result]
       'old_check' is deprecated: use check instead [-Wdeprecated-declarations]
       'unsequenced' attribute ignored [-Wattributes]

clang: ignoring return value of function declared with 'nodiscard' attribute
       [-Wunused-result]
       'old_check' is deprecated: use check instead [-Wdeprecated-declarations]
       unknown attribute 'unsequenced' ignored [-Wunknown-attributes]

The last line of each compiler’s output is the one that matters. ★ Neither compiler implements [[unsequenced]] yet, so both simply ignore it. Being in the standard is not the same as being in the compiler (the gap chapter 19 described shows up here too). And yet the program still runs correctly — thanks to the next rule.

97.5.2 Unknown attributes are ignored#

The standard requires an implementation to ignore an attribute it does not know. That is also why the attribute grammar admits “any tokens at all as long as the brackets balance” (appendix E). That single line is what makes attributes portable — a compiler extension had to be wrapped in #ifdef, whereas an attribute can simply be written and only the compilers that know it will listen.

Extensions are written with a prefix — [[gnu::packed]], [[clang::overloadable]]. Naming the owner up front keeps them clear of the standard’s own names.

Counter-example. Using an attribute instead of a contract

[[unsequenced]] is a promise that the function depends on nothing outside, not a check. Break it and the compiler, believing the promise, may delete or merge calls — so a false promise is a quietly false program, exactly the character of contracts in chapter 55. Someone has to confirm “is that really so” before writing it.

[[nodiscard]] is the opposite. Breaking it changes no meaning; at most a diagnostic appears. So [[nodiscard]] pays to add whenever in doubt, and [[unsequenced]] only when you are certain.

97.6 How to move existing code over#

There is no need to change it all at once. Fix an order and there is almost no risk.

  1. First settle the C edition (-std). Check whether -std=c23 (or c2x) can be used, and whether it works on all the target platforms. If even one does not, go to the shell strategy of number 5 below.
  2. Clear away your own BOOL, TRUE, FALSE. Delete the project header’s typedef int BOOL; and change it to bool. While doing so, also look for places that were comparing values (the counterexample above) — it is rather a place where bugs come to light.
  3. Change NULL to nullptr. Mechanical substitution finishes most of it, but check two places by hand. Variadic calls (a real bug is mended here), and code that used NULL like the integer 0 (a compile error arises here — which is a good thing).
  4. Switch _Static_assert, _Alignas and _Thread_local to the names without underscores. They are different notations for the same thing, so there is no risk. Then tidy away the now unnecessary <stdbool.h> and <stdalign.h> includes.

  5. If old editions must be supported too, put the shells in one place. The same as what was done in chapter 96.

    #if __STDC_VERSION__ < 202311L
#  include <stdbool.h>
#  define nullptr ((void *)0)      /* not a complete substitute — see the caution below */
#  define static_assert _Static_assert
#endif

    This nullptr shell does not go as far as imitating the type. In code doing _Generic branching or type checking it may behave differently from expectations, so if there is such code it is right to raise the edition rather than use the shell.

Q. For a project that must keep compiling with an old standard, is this chapter somebody else’s story?

A. No — two things remain. First, the ability to read. New code and libraries have begun using these words, so when a constexpr or a nullptr appears you must know its meaning. Second, what to mend now. Places passing NULL into variadic arguments with the cast left out, places comparing truth with == 1, places making constants with #define and losing the type — these are already dangerous under the old standard too. C23’s words merely have the language block that danger for you; the danger itself was there all along.
