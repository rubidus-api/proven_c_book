Looking back

Chapter 9 said that printing terminals naturally worked by line buffering — waiting until a line’s worth had gathered before striking the paper. Does today’s printf still carry that habit?

A. It does — when standard output leads to a terminal, output usually gathers in an internal buffer until it meets a \n and then flows out a line at a time. In chapter 20’s demonstration, the characters of printf("Hello, ") appearing on screen only when the second call’s \n arrived was exactly this. Half a century after the circumstances of the paper typewriter disappeared, its rhythm lives on as software’s default — the commotion this habit causes in practice (“my output isn’t showing!”) and how to govern it are met when we take up input and output properly.

The need for this chapter, and its context

The last piece of part 4, and where its goal is met. Output comes last because printf uses all three preceding chapters at once — it happens inside a statement (chapter 20), with constants as arguments (chapter 21), in the shape of a call (chapter 22). So when this chapter ends, hello world has only two lines of debt left.

By the end of this chapter

printf faced head on — the frame called a format string, the blanks %d and %s, and matching the format against the arguments. By the end of this chapter Part IV’s goal is achieved: the whole of hello world, apart from two lines still on credit, becomes sentences we can read.

23.1 What output is — how a program speaks to the outside#

Computation happens inside a program, and the result is useful only once it gets out — printed on a screen, written to a file, or handed to another program. A program sending values outward is output.

chapter 9 said that C’s input and output are streams — bands along which characters flow line by line — and chapter 16 said every program is given one band called standard output. The standard puts it like this.

“ At program startup, three text streams are predefined and are already opened — standard input (for reading conventional input), standard output (for writing conventional output), and standard error (for writing diagnostic output).1 ”

All the output in this chapter is characters sent down that standard output. If the far end of the band is a screen, it appears on the screen; if the shell has redirected the band to a file (./prog > out.txt), it is written to the file. The program does not know which, and need not — that is the point of the stream design. So output comes down to one question: how to turn a value into characters. Inside the machine the integer 42 is bits; what goes down the band is the characters 4 and 2. The tool for that conversion is printf.

23.2 printf — output with a format#

The name printf is short for print formatted — “print it as the format says.” The first argument (chapter 22) is the format string, and the remaining arguments are the values fitted into the format’s placeholders:

printf(format string, value1, value2, ...)

The format string is a frame. Ordinary characters flow straight out, and only the places beginning with % — a conversion specification — are treated as blanks, into which the following value is fitted, turned into characters. This book’s minimal set is three:

  • %d — turns an integer value into decimal characters and fits it in (decimal).
  • %s — fits a string in as it is (string).
  • %% — not a blank; used when you want to print the percent character itself.

Here is the demonstration. Two values go into two blanks in order:

examples-en/output/fmt.c

#include <stdio.h>

int main(void)
{
    printf("The answer to %s is %d.\n", "life, the universe and everything", 6 * 7);
    return 0;
}

Output

The answer to life, the universe and everything is 42.

A string literal went into the %s slot and the value of the expression 6 * 7 into the %d slot, completing the sentence. The format is the template, the arguments go in order — that is the whole of reading printf. (Conversion specifications have many side branches such as field widths, but they are introduced one at a time as needed; the full list is reference material in the appendix.)

Q. Why is what was printed sometimes not visible at once — the program seems to hang and then everything pours out together?

A. Because of the buffering we saw earlier. When output goes to a terminal it flows by lines, but when it goes to a file or another program (chapter 9’s redirection) it gathers until a larger lump has filled and then goes out all at once — a performance trick that reduces round trips. So a program printing progress, once joined to a pipe, appears to “hang and then print in a rush.” When it must go out at once you can flush the buffer with fflush(stdout), and when a program exits normally what remains is flushed automatically — but if it dies suddenly the contents of that buffer vanish, which is the common reason the log just before an accident is missing.

23.3 Kinds of blank — a slot per kind of value#

%d and %s carry you a fair way, but each kind of value has its own blank. Learn the common ones first.

examples-en/output/convert.c

/* The common conversion specifications, and lining things up with width and
   precision. Part IV has not met variables yet, so every argument here is a
   constant or an expression. */
#include <stdio.h>

int main(void)
{
    puts("[a different blank for each kind of value]");
    printf("  integer   %%d  -> %d\n", 42);
    printf("  real      %%f  -> %f\n", 3.14);
    printf("  character %%c  -> %c\n", 'A');
    printf("  string    %%s  -> %s\n", "hello");
    printf("  hex       %%x  -> %x\n", 255);
    printf("  percent   %%%%  -> %%\n");

    puts("\n[width — reserve the columns and things line up]");
    printf("  |%d|%d|\n", 7, 1234);
    printf("  |%6d|%6d|   <- six columns, right aligned\n", 7, 1234);
    printf("  |%-6d|%-6d|   <- a minus means left aligned\n", 7, 1234);
    printf("  |%06d|          <- a 0 fills the blanks with zeros\n", 42);

    puts("\n[precision — how many places after the point]");
    printf("  %%f    -> %f      <- six places by default\n", 2.0 / 3.0);
    printf("  %%.2f  -> %.2f          <- rounded to two\n", 2.0 / 3.0);
    printf("  %%8.2f -> |%8.2f|      <- width and precision together\n", 2.0 / 3.0);
    printf("  %%.3s  -> %.3s        <- on a string: 'how many characters'\n", "abcdef");

    puts("\n[making a table]");
    printf("  %-8s %6s\n", "item", "count");
    printf("  %-8s %6d\n", "apple", 3);
    printf("  %-8s %6d\n", "banana", 12);
    printf("  %-8s %6.1f\n", "weight", 4.25);

    puts("\n[but width counts BYTES — Hangul does not line up]");
    printf("  %-8s %6d\n", "사과", 3);
    printf("  %-8s %6d\n", "바나나", 12);
    puts("  one Hangul syllable is 3 bytes in UTF-8, so eight columns");
    puts("  are not eight characters.");

    puts("\n[the other windows for output]");
    puts("  puts prints one string and the newline for you");
    putchar(' '); putchar(' '); putchar('p'); putchar('c'); putchar('\n');
    fprintf(stdout, "  fprintf(stdout, ...) is the same as printf\n");
    fprintf(stderr, "  fprintf(stderr, ...) goes out on the error band\n");
    return 0;
}

Integer, real, character, string — chapter 21 taught four ways of writing a constant, and here is one blank for each of the four. The remaining conversions (unsigned integers, pointers, sizes) arrive with the types that need them, and the full list is in appendix B.

23.4 Lining things up — width and precision#

A blank can also say how wide and how precise. It pays off immediately when making a table.

Remember the reading order and it never confuses: after % come alignment (-, 0) → width → dot and precision → the conversion letter.

A common misconception. “Give it a width of eight and eight characters fit”

It counts bytes. The last table in the convert.c listing shows it — the English table is neat and the Hangul one is not. One Hangul syllable is three bytes in UTF-8 (chapter 8), so the eight columns %-8s reserves hold barely two Hangul characters.

Lining up a Hangul table in a terminal means counting characters and padding by hand, and even that raises another question: how many cells does one character occupy on screen (East Asian characters take two)? Chapter 87 meets this problem again.

23.5 Output has more than one window#

Besides printf there are three more, each for a different place.

The last matters. A program has two bands going out (chapter 9) — standard output (stdout), where results flow, and standard error (stderr), where error messages flow.

printf("result: %d\n", 42);                   /* standard output */
fprintf(stderr, "cannot open the file\n");    /* standard error */

They are separated because of redirection (chapter 9). Send the results to a file and the error messages must still reach the screen; pipe the results to the next program and error messages must not be mixed in. “Results to standard output, words for a human to standard error” is the discipline of a program that behaves like a tool (the same grain as chapter 59’s exit status).

Q. Why did the stderr line come out at the top of the output of the convert.c listing?

A. Because standard error is not buffered. Standard output, as we saw earlier, gathers in its buffer before flowing; standard error sends at once — an error message must survive even if the program dies a moment later.

So when both bands are captured into one file (as this book’s listing verification does) the order they came out in can differ from the order they were written in. That is design, not accident, and worth knowing when reading logs.

23.6 Matching — the contract between format and arguments#

A format string is a contract. The number and kinds of blanks promise the number and kinds of arguments that must follow. Write two %d and two integer values must follow; a %s slot must receive a string.

Break the promise — put a string in a %d slot, or supply too few arguments — and it is outside the contract: undefined behaviour (the concept met in chapter 6 appears in a function’s manual too). Fortunately modern compilers catch most of these mismatches through the warnings switched on in chapter 18 (-Wall) — printf’s format checking is among the oldest and most dependable of the warning features.

In practice. When a format string became a weapon — the format string vulnerability

This matching contract appears in the history of security too. Wanting to print text a user typed, some programs put the input into the format string slot, as in printf(user_input). If the input is ordinary text there is no problem, but when a malicious user sends in % signs — printf interprets them as blanks and starts rummaging through memory looking for arguments that do not exist. Attacks that peeked into or wrecked a program’s insides using this technique were epidemic in the 2000s and earned their own name, the “format string vulnerability.” The correct code is printf("%s", user_input) — putting the input in as an argument, not as the format. Do not mix data into the frame — this principle is a refrain of security in general.

A common misconception. “printf is the function that prints to the screen”

Practically it is mostly true, but strictly it is not — printf is the function that lets characters flow onto the standard output stream (chapters 9 and 16). If the end of that band is a terminal it appears on screen; turn the band towards a file with the operating system’s facility (redirection) and the same program writes to a file. A program does not know where its output goes, and does not need to — that indifference is the reason for the long life of the stream design. It is entirely thanks to this that one program serves, without being changed, for the screen, for a file, and as another program’s input.

23.7 Closing Part IV — rereading hello world#

Time to meet Part IV’s goal: reading hello world completely. Here are the six lines of chapter 16 again.

#include <stdio.h>

int main(void)
{
    printf("Hello, world!\n");
    return 0;
}

Reading it: #include is a preprocessing directive pasting in the roster of the stdio toolbox (chapters 17 and 20), main’s block binds a list of statements (chapter 20), the expression statement of the printf call lets text flow onto standard output with a string literal as an argument (chapters 21, 22 and 23), and \n breaks the line (chapter 9). What looked like an incantation at first meeting can now be read almost completely.

Exactly two lines remain on credit — the int and (void) of int main(void), and return 0. Both are unravelled only once you know the world of declarations, that is, how to make names and types yourself, and that is the next part. At the end of it the debt is settled in full — and then, at last, we get to take input too.
