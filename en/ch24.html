Looking back

Chapter 3 said memory is lockers with numbers (addresses). But no address has appeared even once in the C code we have written — so how has the program been using the lockers?

A. Through names. To declare a variable in C is to “take some locker slots and attach a human-readable name to them.” The numbers (addresses) are managed by the compiler and we call by name — a name is a nickname people use for an address. This chapter teaches how to make that name; meeting the real address behind the nickname again is Part VII (chapter 36).

The need for this chapter, and its context

Here is why part 5 is called “how names are made”. Up to part 4 only other people’s names were used — now we make our own. Variables come before functions because a function’s parameters and return value are, in the end, variables; and above all, pinning down = correctly here is what prevents the misunderstanding that would otherwise run all the way to chapter 35.

By the end of this chapter

Part V’s subject is “how names are made.” The first step is declaring a variable — choosing a type and a name, storing a value, and changing it. One new operator joins: assignment =. And this chapter’s most important sentence is that this = is not the equals sign of mathematics.

24.1 What a variable is — a named slot#

So far our programs have computed a value and printed it at once. printf("%d\n", 2 + 3); makes 5, prints it, and forgets it. But most work does not end like that. We keep a number that was typed in to use it later, build up a total little by little, count down the times left. We need a place to hold the intermediate results of a computation.

A variable is that place. A few slots of memory are taken and given a name, and the value goes in and comes out through that name. The word “variable” comes from the fact that the value held can change — if a variable in mathematics is “a number not yet fixed”, a variable in a program is “a slot holding this value now that may change later”. In chapter 3’s corridor of lockers, it is a name tag stuck on a few lockers.

Strictly speaking, the C standard does not define the term “variable”. The standard calls a slot in memory an object (its definition comes in chapter 36) and the name stuck on it an identifier. “Variable” is the everyday word for “a named object”. What the standard does define exactly is the declaration that makes the name.

“ A declaration specifies the interpretation and properties of a set of identifiers. A definition of an identifier is a declaration for that identifier that for an object, causes storage to be reserved for that object, …1 ”

Keeping the two words, declaration and definition, apart saves confusion later. A declaration announces “this name is such-and-such”, and a definition is the kind of declaration that actually provides the slot. The int apples = 12; of this chapter is both — it announces the name and takes the slot. Declarations that only announce, without taking a slot, appear in chapter 60, where a program is split over several files.

24.2 Declaration — type, name, and a first value#

The syntax of a variable declaration is a shape we have already brushed past several times:

int apples = 12;

Read it in three parts — the type (int), the name (apples), and the initialisation (= 12). The meaning: “take a slot that holds an integer, call it apples, and put 12 in it as its first value.”

The type promises two things. First, a set of values — int is a container for signed integers — on common machines 32 bits wide, roughly ±2.1 billion in chapter 6’s two’s-complement world. Write double and you get chapter 7’s 64-bit floating-point container. Second, an agreement about operations — what may be done to that name (integer arithmetic or approximate arithmetic) comes from the type. Chapter 3 said “what knows about the lump is the side doing the reading”; in C, the type is exactly that reading eye.

The name is yours to choose, within the frame the grammar fixes — made of letters, digits and underscores, and not starting with a digit. A good name is for people, not for the grammar: apples is kinder than a to yourself half a year later.

Initialisation is not a mere practice but a rule of this book. Always put a first value in when you declare. The slot of a variable declared without initialisation holds whatever rubbish bits happened to be left there (chapter 3 — a slot is always full of something), and reading that is a common way into an accident. Formal treatment is in chapter 57, but the habit starts now.

24.3 Assignment — the side effect that changes state#

The value of a declared variable is changed by assignment (=). The operator that chapter 21 said would join when needed finally joins. Here is the demonstration:

examples-en/variables/var.c

#include <stdio.h>

int main(void)
{
    int apples = 12;              /* declared and initialised at once */

    printf("apples: %d\n", apples);
    apples = apples + 3;          /* the new value = the value now + 3 */
    printf("apples: %d\n", apples);
    return 0;
}

Output

apples: 12
apples: 15

Reading the third statement apples = apples + 3; correctly is the core of this chapter. The order is: ① evaluate the right-hand expression apples + 3 (read the current value 12 and obtain 15), ② put that value into the slot of the left-hand name (the 12 that was there is overwritten and gone). That is, = is not “equals” but an instruction: “calculate the right and put it in the left.” The value changing — this is the side effect foreshadowed in chapter 21, the second one we meet after output: assignment changes a variable’s state.

A common misconception. “x = x + 1 is a nonsensical equation — no number equals itself plus one”

By the eye of mathematics, entirely right — read as an equation it has no solution. The root of this misconception is the reuse of the = symbol. C’s = is not an equals sign but a put instruction, so x = x + 1 is “add 1 to x’s current value and put the result back into x” — a perfectly sensible command to increase x by one. The x on the right is the value when read (the old value) and the x on the left is the place to put it (the slot) — this distinction, the same name read as a value or as a location depending on its position, is a fundamental of reading C. Incidentally, the real comparison asking “are they equal?” is handled by a different symbol (==, chapter 31) — the symbols were separated precisely because of this confusion.

24.4 const — the promise not to change#

For a value that will never change, attach const to the declaration:

const int max_floor = 63;    /* the value of this name will not change */

Assign to a name marked const and the compiler blocks it as an error. This is less a lock than documentation — telling both the compiler and the next reader that “this value does not vary.” The more of a piece of code that stays unchanged, the easier it is to read and the fewer accidents it has — so modern practice is close to “declare it const first, and take that off only for what must change.” This book’s examples follow that instinct.

Q. In the discussion of types you said int is “roughly ±2.1 billion” — does that mean the exact size differs by machine? Where did chapter 6’s 8-bit and 16-bit stories go?

A. An accurate observation. int is a type for which the standard sets only a minimum (“at least this much”) and leaves the concrete size to the platform — in today’s mainstream environments 32 bits is the de facto standard. Chapter 6’s 8-bit and 16-bit containers, and the types for “when you want the size pinned down exactly” (int32_t and the like), are organised in chapter 28 when the whole family of integer types is introduced. In this part int alone is enough — by the spiral principle, the family reunion happens when it is needed.

We have made a name, held a value and learned how to change it. But two lines remain in the credit ledger carried since chapter 16 — int main(void) and return 0. Both belong to the grammar of functions. Having given a name to a value, in the next chapter we give a name to work — how to make a function yourself, and the complete settling of the ledger.
