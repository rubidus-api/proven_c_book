8 Characters and text — scars in the standard

What to know first

chapter 7, Representing numbers · a representation is an agreement, and agreements leave scars

Looking back

Chapter 7 said the decimal point is not in the bits but in an agreement. Then what about letters — is the shape “가” inside the bits?

A. No; the principle is the same. Bits have neither shape nor sound. All there is is numbers, and there is a separate agreed numbering table saying which number is which letter. To store a letter is to store a number, and text is a sequence of numbers. This chapter is the story of those tables.

The need for this chapter, and its context

The third rung of the ladder of representation (the chapters that put numbers and characters into bits in turn), and the chapter of Part II that lands hardest for a Korean reader. The history of characters left scars on C’s syntax: trigraphs, locales and wide characters are all such scars. See the cause before you meet them, and later they read as leftovers rather than as strange rules. So characters go here.

By the end of this chapter

How to put letters into the lockers — that a character is, in the end, a number; what history that numbering table (the character code) went through on its way to Unicode and UTF-8; and the scar that history left in C’s syntax (trigraphs). For a reader who writes Korean this chapter is unusually vivid.

The questions this chapter answers

  1. Isn’t EBCDIC a museum piece? Do we still have to worry about this?
  2. Are trigraphs still used?
  3. If you had to reduce what a programmer should take from these traps to one principle, what would it be?
  4. Why does a beginner need to know this messy history now? Is it not enough to use UTF-8 only?

8.1 A character is a number#

There is only one way to store “A” in a machine — make an agreement that “A shall be number 65” and store the number 65. Such a table of agreements, the correspondence between letters and numbers, is called a character set or character code.

The problem is that there were several such tables. Every company and every country made its own. The same number meant a different letter in different tables, and when two machines with different tables exchanged text the letters came out garbled. The rest of this chapter is the history of that tangle, and every turn of that history left its mark on C and computing today.

8.2 ASCII and EBCDIC — two tables#

Both names are abbreviations: ASCII is the American Standard Code for Information Interchange, and EBCDIC is the extended binary coded decimal interchange code.

Two families of tables established themselves in the 1960s. IBM’s mainframe world used a table called EBCDIC — grown out of punched-card codes, so its layout looks strange today (the letters are not numbered consecutively, among other things), but in IBM’s world it was law.

On the other side, centred on the communications industry, came ASCII. It used seven bits — a small table of 128 slots — to hold uppercase and lowercase English letters, digits, punctuation, and the control characters that are invisible on screen. A control character is not a letter but an instruction to a device — “advance the paper one line”, “sound the bell” — and their story comes in the next chapter (streams). And sitting at slot 0 of this table is the NUL character whose face we learned in chapter 4. It means “no character at all”, and C later adopted it as the mark for the end of a string (chapter 43).

8.2.1 What “the alphabet is not consecutive” does to code#

That phrase, “its layout looks strange”, must not be passed over — it decides the fate of a line of C. Everyone writes this line at least once.

if (c >= 'A' && c <= 'Z') { … }        /* is it an uppercase letter? */

On ASCII it works, because A is 0x41 and Z is 0x5A and the 26 slots between them are exactly the alphabet. But that it works is a fact about the table, not a rule of the language.

EBCDIC is different. This book measured the actual table (code page 037).

That the alphabet comes in three pieces is a trace of its growth from punched-card codes. So the range from 'A' to 'Z' holds 41 slots, of which only 26 are letters. We counted what sits in the other 15.

★ That is, on EBCDIC the if (c >= 'A' && c <= 'Z') line from earlier answers “yes, an uppercase letter” for a closing brace and a backslash. No compile error, no warning, no odd value. It is simply, quietly wrong.

A common misconception. “Surely a '0' ~ '9' range test is safe everywhere”

★ This one is safe — and it is the only consecutive run the standard guarantees.

“ In both the source and execution basic character sets, the value of each character after 0 in the preceding list of decimal digits shall be one greater than the value of the previous. (§5.2.1) ”

The standard writes this for the ten digits, and there is no such sentence for the letters. That is evidence that the people who wrote the standard knew about EBCDIC — they did not make a promise they could not keep.

So the idiom c - '0', turning a digit character into its value, is right everywhere, while c - 'A', taking a letter’s position in the alphabet, is not.

8.2.2 Which is why there are libraries — what an abstraction does#

Here a thesis this book will repeat makes its first appearance. Do not write the table’s circumstances into your code; ask.

if (isupper((unsigned char)c)) { … }   /* right, whatever the table */

That is exactly what the classification functions of <ctype.h> do. They do not test “at least 0x41 and at most 0x5A” — they know what counts as uppercase in the character set this implementation uses. A C implementation on an EBCDIC machine ships a test that knows about the three pieces; one on an ASCII machine may use a simple range check. Either way the calling code does not change by a single character.

What an abstraction does is not add a feature. It confines what varies to one place.

★ And the story does not end at character classification. The same logic recurs throughout this book — counting a string’s length (chapter 43), deciding sort order (chapter 84’s strcoll), counting characters (chapter 87). All of them come down to stripping out the assumption that the table I know is the whole world.

Q. Isn’t EBCDIC a museum piece? Do we still have to worry about this?

A. Honestly — your code will most likely never run on an IBM mainframe. EBCDIC survives on the z/OS line and still runs in the core systems of banks and insurers, but for most readers of this book it is a world they will not meet.

Still, there are two reasons to raise it here.

First, it is the cleanest specimen of “an assumption written into the code”. Once you have seen it actually break, you acquire the habit of asking what assumptions are written into my code right now. That habit pays off even if you never meet EBCDIC — the accidents ahead (the signedness of char, the byte count of UTF-8, judgements the locale changes) all have the same shape.

Second, it explains why the standard is worded so stingily. “Only the digits are consecutive” looks over-cautious at first sight, but that caution has a name and a face. A good many of the standard’s odd-looking clauses point this way, at a machine that once really existed.

ASCII became the winning table — nearly every character code today carries ASCII inside it. But 128 slots were tight even for English and nowhere near enough for the world’s writing systems. Here the history of the scars begins.

8.3 ISO 646 — national variants and C’s trigraphs#

The first stopgap was ISO 646, the international edition of ASCII. The idea went: “keep one table, but allow each country to replace a few less important slots with its own letters.” The slots designated for replacement happened to include symbols such as [ ] { } \ | #.

The result was a disaster for programmers. Open C code on a Danish terminal and Danish letters appeared where the braces should be. Same number, different table, different letter printed.

In practice. The ₩ sign — ISO 646’s scar in Korea

Korea is a party to this history too. The Korean table (KS X 1003) replaced the backslash \ with the won sign ₩. On Korean computers of that era file paths looked like C:₩Program Files₩... — and, astonishingly, this scar is still visible. Even on Korean-language Windows today some fonts draw the backslash code as ₩. Same number, same bits, and the table (the font) draws ₩. This book’s refrain, “what is stored and how it is read are separate things”, is something Korean readers have witnessed on screen every day.

C was standardised amid this confusion (chapter 13). Since C had to be usable in countries where braces could not be displayed, C89 provided a grotesque detour — the trigraph. Write ??< and it was read as {; write ??/ and it was read as \ — a three-character cipher. A scar of the character-code wars, carved into the grammar of the language.

Q. Are trigraphs still used?

A. No — and their end is a symbolic moment in recent C history. As the Unicode era arrived, trigraphs lost their reason to exist and survived only as a trap in which a string like ??! was unexpectedly transformed. C23 removed trigraphs from the standard. A scar carved in 1989 was erased only in 2023 — which also shows how much slower a standard is at removing something than at adding it.

8.4 Many eight-bit tables, and Hangul#

Once the byte settled at 8 bits (chapter 2), the ISO 8859 family extended the table to 256 slots — the first 128 identical to ASCII, the second 128 holding the letters of one language region (Latin-1 for Western Europe, and so on). But since the upper 128 were used differently per region, the problem of garbled letters when you picked the wrong table remained.

And there were writing systems for which 256 slots were nowhere near enough. Hangul, Han characters, kana — East Asian scripts run to thousands and tens of thousands. The solution was multi-byte encodings using several bytes per character (Korea’s EUC-KR among them — EUC is extended Unix code). With lengths varying per character and methods varying per country, a Korean document read with the wrong table would break into a parade of meaningless symbols — the so-called “broken characters” — and that was daily life for Korean computer users of that era.

8.5 Unicode and UTF-8 — one table, a clever way of holding it#

Start with what the name “UTF-8” stands for. UTF stands for Unicode transformation format, and the 8 means that it works in units of eight bits — one byte.

In the end there was only one fundamental solution. Put every character in the world into one table. That is Unicode, from the 1990s. Each character gets a unique number (a code point), written as U+AC00 (가). The table has more than a million slots.

The remaining problem was how to hold those large numbers in bytes. Spending 4 bytes on every character is wasteful and, above all, incompatible with the mountains of existing ASCII text. The answer was the variable-length encoding UTF-8 — characters in the ASCII range stay 1 byte as they are, and everything else takes 2–4 bytes. Thanks to the clever design by which an existing ASCII file is already valid UTF-8, UTF-8 has become effectively the only standard for the web and for source code today. It is what this book’s examples and C23’s u8"" strings use as well (chapter 43).

A common misconception. “One character is one byte”

This misconception is left over from the intuitions of the ASCII era, and it is especially dangerous when learning C, because C’s char type is, despite the name, not a “character” but a byte (chapter 43). In UTF-8 the English A is 1 byte but the Hangul 가 is 3. The two characters of “안녕” take six bytes. Character count and byte count are different quantities, and code in which the distinction has collapsed will certainly cause an accident when handling Hangul.

8.6 The two character sets C keeps apart — source and execution#

So far this has been the world’s story of character sets. Now for how C handles them. The core is one sentence — C treats the character set the source code is written in and the character set of the running program as two different things.

Start with the standard’s exact names (§5.2.1).

The standard does not say the source and execution character sets must share an encoding. Section 5.2.2 splits them explicitly — the execution character set may also contain multibyte characters, and those are not required to have the same encoding as for the source character set. And §5.2.1 drives in one more nail: the values of the members of the execution character set are implementation-defined.

8.6.1 Where source characters cross into the execution character set — translation phases 1 and 5#

The place the two sets meet is pinned down in the translation phases (chapter 65).

The standard’s text for phase 5 has a second sentence, left out of the table, and it matters most — where there is no corresponding member, it is converted, in an implementation-defined manner, to some member other than the null character. That is: it quietly becomes a different character. Not an error.

A common misconception. “The letters I typed in the source go into the executable unchanged”

For the basic character set — letters, digits, symbols — effectively yes. But an extended character such as Hangul is converted once, in phase 5. Write the source in UTF-8 and, if the execution character set is EUC-KR, EUC-KR bytes are what get embedded — chapter 18 measures exactly this.

So “what encoding the source file is in” and “what bytes the program emits” are different questions. Treat them as one and you will never narrow down which link to fix when Korean text breaks.

8.6.2 The more precise name C23 added — the literal encoding#

C23 added §6.2.9, “Encodings”, tidying up one more name.

If the “execution character set” is which characters exist, the “literal encoding” is what byte values represent them. The standard requires only that the literal encoding and the wide literal encoding both map the whole basic execution character set, and leaves the rest to the implementation.

Platform note. C++ renamed all of this

C++20 and C++23 reworked the terminology for the same concepts. C++ uses translation character set in place of “source character set” and pins it to Unicode, while calling the execution side ordinary literal encoding and wide literal encoding — C’s literal encoding with “ordinary” added.

So when reading both standards together, keep in mind that the vocabulary diverges — C has no term “translation character set” yet. C23 (N3220) §5.2.1 still says source character set and execution character set, and only §6.2.9 adds the name literal encoding.

8.6.3 Prefixes that nail the encoding down#

There is a way to fix an encoding regardless of the execution character set — the literal prefixes (§6.4.5).

Where the bytes must not change — protocols, file formats, a test’s expected value — write u8"…". Two characters that turn “the implementation decides” into “the standard decides.” The fuller story of wide characters comes in chapters 85–86.

8.7 Same letter, several representations — the security terrain hidden in text#

Unicode’s unification of the table did not end the problems. If anything, as the table grew and the representations multiplied, new traps appeared. It is terrain any program that handles text meets eventually, so let us survey it. There is a single root — if the same thing can be written in two or more ways, the side checking it and the side interpreting it can disagree.

① Normalization — Hangul’s NFC and NFD. The letter “각” can be written two ways in Unicode: as one composed syllable (NFC, the single code point U+AC01) and as a sequence of jamo (NFD, the three code points ᄀ+ᅡ+ᆨ). They look identical, but the byte sequences are entirely different — so a naive byte comparison answers “각 ≠ 각”. For Korean users this is not a textbook story: because macOS stored file names in the NFD family, it was common for Hangul file names crossing to another OS to appear with the jamo undone, or for names to go wrong inside archives. The solution is to normalise to one form at the boundary — and in a security context the order of that normalisation is decisive (see the second rule in the Q&A below).

② Overlong encodings — the back door UTF-8 once left open. By the UTF-8 rules in the maths box above, / (U+002F) is the single byte 2F. But early implementations generously accepted the same character written “long”, in 2 bytes (C0 AF) or 3 — an overlong representation. This led to a classic attack: the security check looked only for 2F to filter out path traversal (../), while the file system interpreted the overlong C0 AF as / too. A disagreement between checking and interpreting — that was what lay behind the directory-traversal vulnerability that swept IIS servers in 2001. Today’s standard therefore declares overlong forms illegal and requires decoders to reject them.

③ The ghost of a vanished encoding — UTF-7. UTF-7, made to send Unicode through 7-bit channels (early email), represents other characters using ordinary-looking ASCII letters (+ADw- becomes <). In the days when browsers guessed encodings automatically, attackers used this property to get through filters — a string that looks harmless when checked and resurrects as a tag the moment the browser interprets it as UTF-7. UTF-7 was effectively retired because of these incidents, and today’s norm has hardened into do not guess the encoding; state it.

④ Traps in Unicode itself — homoglyphs and direction controls. A large table also means there are different letters that look identical. Latin a and Cyrillic а are indistinguishable on screen — using this to build a fake domain that looks exactly like the real one is a homograph attack (which is why browsers show suspicious mixed-script domains back in their original notation). More cunning are the directional control characters: Unicode has invisible characters that reverse the display order of text, making it possible for the order in which a human reads the source and the order in which the compiler reads it to differ — “Trojan Source”, published in 2021, used this technique to show that code looking perfectly fine to a reviewer could compile with different logic. Compilers began warning about such characters afterwards.

⑤ When layers stack — escaping and multiple interpretation. To display < as a letter on the web you write &lt; (HTML escaping). Stack several such layers and accidents follow — decode once-escaped text again in another layer and the original symbol comes back; conversely, check but forget to escape and the input becomes code. The format-string vulnerability of chapter 23, SQL injection in databases and XSS on the web are all the same pattern — getting data mistaken for the frame (the code). C’s trigraphs were an early case of the pattern: if ??/ happened to appear inside a string, the preprocessor turned it into a backslash, creating an escape the programmer never wrote (one of the reasons C23’s removal of trigraphs is welcome).

Q. If you had to reduce what a programmer should take from these traps to one principle, what would it be?

A. Do not let the representation change between checking and interpreting. As practical rules it unfolds into three — first, do not guess the encoding; state it (pin UTF-8 at the input/output boundary). Second, normalise and decode first, and check afterwards — reverse the order and the overlong and UTF-7 accidents come back. Third, do not mix data into the frame — a value always goes where values belong (the printf("%s", input) idiom of chapter 23 is the smallest application of this principle). All three come from this book’s refrain that representation and interpretation are separate.

8.8 Sequences of characters — ways of holding a string#

Now that we know how to hold one letter, a last question remains. When a sequence of letters — a string — goes into the lockers, how do we know “where does this string begin and end?” Chapter 3’s refrain returns: memory does not know the boundaries of a lump; what knows is the agreement of the reader. There are several such agreements, so let us look at the main approaches.

Method 1 — write the length in front (length-prefixed). Attach a number meaning “this many characters follow” in front of the string. The Pascal family used it, so it is also called a Pascal string. Asking for the length needs no counting (read the number and you are done), and any byte at all — even character 0 — can be held as content. In exchange, the size of the length field has to be fixed in advance — old Pascal held the length in one byte, so a string could not exceed 255 characters (chapter 2’s container story, again).

Method 2 — plant a marker at the end (NUL-terminated). Instead of writing the length, plant a special character at the end of the sequence — the NUL character of value 0 whose face we learned in chapter 4. This is the method C chose. Its virtue is extreme simplicity — you need only the starting point, and pointing anywhere in the middle of the sequence makes “from there to the NUL” a string. The price is threefold: to know the length you must count all the way to the NUL; you cannot hold a NUL in the content; and above all, forget to plant the marker and the reader runs on into someone else’s territory. That last price has caused more accidents than any other in C’s history, and chapter 43 is the scene.

Method 3 — manage length and capacity together. The dynamic strings of modern languages usually manage three values as one bundle: [where the content is, the current length, the capacity of the container] — length queries are immediate, appending needs no new allocation within the capacity, and when it runs out the content moves to a larger container. C++‘s std::string and Rust’s String have this structure, and proven’s string handling, which we meet later, follows the same approach by treating length explicitly (Part XIV).

In practice. The magic of fifteen bytes — small string optimisation in the MS STL

Real implementations of method 3 have a clever double use of space. In Microsoft’s implementation of the standard library of neighbouring C++ (MS STL), std::string does not borrow a big warehouse (dynamic memory) for a short string — specifically 15 bytes or fewer (plus one byte for the terminator) — but simply holds it inside the body of the string object itself. The technique is called SSO, small string optimisation. Why 15? Because besides its length and capacity fields the object holds a 16-byte slot laid over the pointer; for a short string that slot is the content buffer, and 16 bytes less one for the terminator comes out to exactly that size. The effect is explained by what chapter 12 teaches: most real-world strings are short, and those now travel attached to the object with no warehouse round trip (allocation), moving together on the same cache line. Other implementations (the GCC and Clang standard libraries) use the same technique with different numbers — a modern textbook case of “the choice of representation is speed.”

There are still more ways to represent a string — representations for editors that manage a large document as a tree of pieces (ropes), views that point at [start, length] without copying the original, and so on: each use has a representation suited to it. One thing to remember: the shape a string takes in memory is not one thing but a choice made by a language and a library, and that choice determines the character of its performance and safety. The trade-offs of C’s choice (NUL termination), and how it must be handled, are faced head on in chapter 43.

Q. Why does a beginner need to know this messy history now? Is it not enough to use UTF-8 only?

A. For anything new, UTF-8 alone is enough — that is today’s practice and this book’s premise. But the history is needed for two reasons. First, old encodings still flow through the world’s files and systems, so when you meet broken characters you must be able to diagnose “ah, the wrong table.” Second, C itself is a product of this history — the name char, NUL termination, the remains of trigraphs — so knowing the history makes all of C’s strange corners read as wounds with a story. There is nothing to memorise. “A character is a number; there were many tables until Unicode unified them; and UTF-8 won as the way to encode them” — those three sentences are enough.

The next chapter is the last rung on the ladder of representation. Now that we can hold letters, it is the story of letters flowing — why a computer’s input and output is shaped as “characters going past one line at a time”, an answer that lies in the age of paper cards and typewriters.
