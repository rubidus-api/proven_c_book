46 Dynamic memory

What to know first

chapter 45, Lifetime and storage duration · the limits of automatic lifetime
chapter 5, The regions of memory · the warehouse (the heap)

Looking back

Chapter 45 taught automatic lifetime (dies with the function) and static lifetime (lives for the whole program). Then memory that is “sized according to input and must live only as long as needed” — in which of the two does it go?

A. Neither fits. We need memory whose size is settled at run time and whose lifetime is decided by the program’s logic — so there is a third place: allocated storage duration, the warehouse commonly called the heap. The rule of this place differs decisively from the other two — the programmer directly orders its birth and its death.

The need for this chapter, and its context

This is the last chapter of Part VII, and it completes the picture of memory. The heap comes last not because it is hardest but because it is what can be put off longest — the preceding ten chapters all ran without it. So by the time you arrive, the question “why allocate and free memory by hand at all?” has formed on its own.

By the end of this chapter

Part VII’s last place — memory whose size is settled at run time and which is kept alive as long as you wish. malloc and free, the notion of ownership, and this world’s three typical accidents (leak, double free, use after free). Here the picture of memory is complete.

46.1 What dynamic memory is — memory allocated at run time#

Until now the size and lifetime of every object were written in the source. int a[100]; has its size fixed at compile time; as a local variable it vanishes when its block ends, and as a global it lives until the program ends (chapter 45). But three needs cannot be met that way.

The answer is to allocate memory at run time, as much as needed, for as long as needed. This is called dynamic memory allocation. The region where allocated memory lives is commonly called the heap (one of chapter 5’s four regions), and the standard gives dynamically allocated memory the fourth storage duration, allocated storage duration (chapter 45). The standard defines that lifetime in this sentence.

“ The lifetime of an allocated object extends from the allocation until the deallocation. Each such allocation shall yield a pointer to an object disjoint from any other object. … If the space cannot be allocated, a null pointer is returned.1 ”

This one sentence holds every rule of this chapter. The lifetime is decided by the programmer, not the language — it begins when the caller allocates it and ends when the caller frees it. Never free it and it never ends (a leak); use it after freeing it and you touch a lifetime that has already ended (use after free). And allocation can fail. Leaks, use after free, failed allocation: unlike with local variables, the compiler looks after none of these three for you — that is the weight of dynamic memory.

46.2 Allocating with malloc, releasing with free#

It takes two functions. malloc(number of bytes) allocates that many contiguous bytes from the heap (once, like reserving space in a warehouse) and returns their starting address; the caller owns that block and free(address) releases it back.

examples-en/dynamic-memory/dyn.c

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int count = 5;
    int *scores = malloc(count * sizeof *scores);   /* borrowed from the warehouse */

    if (scores == nullptr) {                        /* borrowing can fail */
        printf("allocation failed\n");
        return 1;
    }

    int sum = 0;
    for (int i = 0; i < count; i += 1) {
        scores[i] = (i + 1) * 10;
        sum += scores[i];
    }
    printf("total: %d\n", sum);

    free(scores);                                   /* what is borrowed is returned */
    return 0;
}

Output

total: 150

The demonstration has three practices built in.

Compute the size as sizeof *pointer. count * sizeof *scores is “the size of one element × the count”, asking for the size through the target rather than a type name — so the line needs no fixing later if the type changes.

Allocation can fail. malloc returns a null pointer when the heap cannot supply the requested space — so check before writing (chapter 37’s rule becomes practice here). Write without checking and the program dereferences null and crashes.

Release what you allocate. Forget free and those slots stay tied up until the program ends — a memory leak. It does not show in a short program, but in a long-running server it seeps away little by little and eventually eats the machine.

A common misconception. “Memory from calloc comes with its pointers initialised to null”

What calloc promises is one thing: every bit is set to zero. That is not the same as “a null pointer” or “0.0” — chapter 37’s distinction between spelling and representation catches you here too.

On today’s mainstream machines all three — all bits zero, the null pointer and 0.0 — coincide, so no accident follows. Still, code that allocates an array of pointers with calloc and says “they are all null, so a check is enough” is standing on that coincidence — better to know it. Where portability matters, fill them with nullptr in a loop after allocating, or mark “empty” by something other than zero in the first place.

46.3 How to write a malloc call — an old argument#

There are several ways to write the same allocation, and the C world has argued for thirty years about which is right. Find a piece on this subject online and it is usually heated, because both sides have a case. So measure, then decide.

examples-en/dynamic-memory/malloc_style.c

/* Three ways of writing a malloc call — how they differ. */
#include <stdio.h>
#include <stdlib.h>

struct node { int id; double weight; };

int main(void)
{
    /* -- the recommended form: the type name never appears -- */
    struct node *a = malloc(4 * sizeof *a);
    if (!a) return 1;

    /* -- the C++-compatible form: the type name twice -- */
    struct node *b = (struct node *)malloc(4 * sizeof(struct node));
    if (!b) { free(a); return 1; }

    /* -- the compromise: cast, but take the size from the target -- */
    struct node *c = (struct node *)malloc(4 * sizeof *c);
    if (!c) { free(a); free(b); return 1; }

    printf("all three reserve the same size: %zu, %zu, %zu bytes\n",
           4 * sizeof *a, 4 * sizeof(struct node), 4 * sizeof *c);

    puts("\n[sizeof *p does not read p — an unevaluated operand]");
    struct node *nul = NULL;
    printf("  even with p null, sizeof *p computes as %zu\n", sizeof *nul);
    puts("  because the size comes from the TYPE, not from the value.");

    puts("\n[write the name twice and the two can drift apart]");
    puts("  struct node *p = (struct node *)malloc(n * sizeof(struct gadget));");
    puts("  ^ the type name is in two places, so fixing only one is possible.");
    puts("  written as sizeof *p, that accident CANNOT BE WRITTEN.");

    puts("\n[a danger both forms share — overflow in the multiplication]");
    size_t huge = (size_t)-1 / sizeof(struct node) + 1;
    printf("  huge * sizeof *a wraps around to %zu\n", (size_t)(huge * sizeof *a));
    puts("  -> malloc can SUCCEED with a tiny size. Check the count first, or"); 
    puts("     use calloc(count, size), which checks the multiplication itself.");

    free(a); free(b); free(c);
    return 0;
}

46.3.1 Four reasons for form 1, taking the size from the target#

First, when the type changes there is only one place to fix. This is the biggest reason. The Linux kernel’s coding style puts it this way — spelling the type name out “hurts readability and introduces an opportunity for a bug when the pointer variable type is changed but the corresponding sizeof that is passed to a memory allocator is not”.

Think of the common act of changing an int * into a struct node *. Form 1 needs only the declaration changed and the size follows; form 2 needs two places changed, and forget one and it still compiles, allocating too small a block.

Second, the type name never appears, so it cannot drift. This goes one step beyond “only one place to fix” — in form 1 there is no way to write it wrongly.

Third, sizeof *p does not read p. At first sight it looks like dereferencing a pointer that has not been allocated yet. It is not: the operand of sizeof is not evaluated (chapter 52). The listing confirms it — sizeof *p still gives the right size with p null, because the size comes from the type, not the value.

Fourth, the cast used to hide bugs. Before the standard and in the C89 era, calling malloc without including <stdlib.h> made the compiler assume “a function returning int”. Putting that int into a pointer draws a diagnostic — and the cast blurs that diagnostic. Reproduced by measurement:

Honesty requires adding that this fourth reason has nearly lost its force today. C99 removed implicit function declarations, and in C23 it is an outright error — measured, error: implicit declaration of function 'malloc' appears with or without the cast. “The cast hides a bug” is now a historical explanation, not a present reason. When a piece still wields it as the clincher, check which decade it is describing.

46.3.2 The case for form 2, naming the type and casting — CERT MEM02-C#

The other side has a standard behind it too. The SEI CERT C Coding Standard’s MEM02-C is titled “Immediately cast the result of a memory allocation function call into a pointer to the allocated type”, and its rationale is this — “casting the result of malloc() to the appropriate pointer type enables the compiler to catch subsequent inadvertent pointer conversions”.

The claim holds. Compile CERT’s own example and the difference is plain.

It is true that the cast turns a warning into an error. But the third row shows the heart of the argument — form 1 needs no diagnostic, because there is no mistake to diagnose. And CERT itself rates this recommendation severity low, likelihood unlikely, priority P3.

46.3.3 Form 3, the compromise, and the “C++ compatibility” reason — is it real?#

The most frequently heard reason for the cast is “because it must build with a C++ compiler too”. C++ does not allow an implicit conversion from void * to another pointer type, so without a cast it genuinely fails to compile — measured, error: invalid conversion from 'void*' to 'int*'.

Three points need weighing before that reason is accepted.

First, C++ does not recommend malloc in the first place. The way to obtain memory in C++ is new, and more properly containers and smart pointers. So “a malloc call that also builds as C++” means making code that C++ does not recommend conform to C++ syntax. It is worth asking what that buys.

Second, the compatibility is not actually obtained. This is decisive. This book handed a C++ compiler a modern C file with the cast dutifully applied:

That is, the cast does not get the file into C++. The ordering constraint on designated initialisers, _Generic, variable length arrays, restrict, compound literals, flexible array members — the two languages have diverged steadily since 1989, and C23 and C++23 are further apart than ever (chapter 117). What one cast buys is not compatibility but the illusion of it.

Third, what is really shared is the header, not the .c file. The realistic place where C and C++ meet is a header (extern "C", chapter 64) — and headers do not call malloc. The calls live in implementation files, and those are compiled by a C compiler.

Q. Is there no place, then, where the cast is right?

A. There is — but where there is an actual circumstance, not “just in case”.

  • Projects that really do build .c files as C++. Rare, but they exist — some embedded toolchains, old MSVC practice, builds that pull C code wholesale into a C++ translation unit. There it is a requirement, not a choice.
  • Under a convention that follows CERT. As chapter 117 shows again, where a rulebook governs, the rulebook wins.

In such cases, prefer form 3, (T *)malloc(n * sizeof *p) — satisfy C++ with the cast while keeping form 1’s safety by taking the size from the target. Tested, this form compiled in both C and C++. If one of the two must go, give up writing the type name twice.

Counter-example. The real danger shared with or without the cast — overflow in the multiplication

The cast argument tends to obscure another issue: the multiplication in n * sizeof *p can overflow.

p = malloc(n * sizeof *p);   /* with a large n the product wraps */

As the listing showed, when the wrapped result is a tiny number malloc succeeds — and writing n elements into that tiny block brings the heap down. The hole is equally open with or without the cast, and it has become a real vulnerability more than once. In Ruby’s security advisory of 18 November 2026 as well, integer overflows in both string case-conversion output sizing (GHSA-87fm-7w84-j2px) and regular-expression compilation sizing (GHSA-3p8q-wmhx-vm2w) produced undersized allocations and heap buffer overflows.2

Three ways to close it.

  • Check the count first — if (n > SIZE_MAX / sizeof *p) return NULL;
  • Use calloc(n, sizeof *p) — the standard requires it to check the multiplication. In the test, calloc refused the overflowing request (zeroing is a bonus and a cost).
  • Use checked arithmetic — C23’s <stdckdint.h> (chapter 96).

This is a far more valuable argument than whether to write a cast.

Q. So which does this book use?

A. Form 1. p = malloc(n * sizeof *p);

The reason in one line — a form that cannot be written wrongly is better than a form that catches you when you write it wrongly. A cast is a device that turns a mismatch into a diagnostic; form 1 removes the mismatch. In the language of chapter 13’s ladder, better than rung 3 (let the build tell you) is a design where the state never arises.

This is not meant as a rule to enforce. In a codebase that must build .c as C++, or under a convention that follows CERT, forms 2 and 3 are the right choice. Choosing knowingly differs from inheriting a habit — and the commonest mistake in this debate is not which form you pick but attaching the cast without knowing why, because that is how you were taught.

46.4 The alignment of the address returned — because it does not know what will go in#

examples-en/dynamic-memory/alloc_cost.c

/* The alignment of the address malloc returns, and the price of borrowing and returning */
#include <stdint.h>
#include <stddef.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define N 300000

static double seconds_since(struct timespec t0)
{
    struct timespec t1;
    timespec_get(&t1, TIME_UTC);
    return (double)(t1.tv_sec - t0.tv_sec) + (double)(t1.tv_nsec - t0.tv_nsec) / 1e9;
}

static void *volatile sink;      /* holds the allocation so optimisation cannot erase it */

int main(void)
{
    /* ── (1) alignment: not knowing what will be put in it, it gives the strictest ── */
    printf("alignment of max_align_t = %zu bytes\n", alignof(max_align_t));

    size_t misaligned = 0;
    void *p[8];
    for (int i = 0; i < 8; i++) {
        p[i] = malloc(1);                    /* even asking for a single byte */
        if ((uintptr_t)p[i] % alignof(max_align_t) != 0) misaligned++;
    }
    printf("of 8 one-byte requests, ones breaking the default alignment: %zu\n", misaligned);
    printf("address gap between two neighbouring blocks: %td bytes (for a request of 1)\n",
           (char *)p[1] - (char *)p[0]);
    for (int i = 0; i < 8; i++) free(p[i]);

    /* ── (2) the price: the same work three ways ── */
    struct timespec t0;
    unsigned long long acc = 0;

    timespec_get(&t0, TIME_UTC);
    for (int i = 0; i < N; i++) {           /* borrow and return every time */
        char *b = malloc(64);
        if (!b) return 1;
        b[0] = (char)i;
        acc += (unsigned char)b[0];
        sink = b;
        free(b);
    }
    double t_alloc = seconds_since(t0);

    char *reused = malloc(64);
    if (!reused) return 1;
    timespec_get(&t0, TIME_UTC);
    for (int i = 0; i < N; i++) {           /* borrow once and keep using it */
        reused[0] = (char)i;
        acc += (unsigned char)reused[0];
        sink = reused;
    }
    double t_reuse = seconds_since(t0);
    free(reused);

    timespec_get(&t0, TIME_UTC);
    for (int i = 0; i < N; i++) {           /* put it on the stack instead */
        char b[64];
        b[0] = (char)i;
        acc += (unsigned char)b[0];
        sink = b;
    }
    double t_stack = seconds_since(t0);

    printf("\n%d iterations\n", N);
    printf("  malloc + free each time : %7.4f s  (%5.1f ns each)\n", t_alloc, t_alloc / N * 1e9);
    printf("  borrowed once, reused   : %7.4f s  (%5.1f ns each)\n", t_reuse, t_reuse / N * 1e9);
    printf("  a stack array           : %7.4f s  (%5.1f ns each)\n", t_stack, t_stack / N * 1e9);
    printf("\n(total %llu — a value used so the computation is not erased)\n", acc);
    return 0;
}

The first part of the example answers this question: having allocated a mere one byte with malloc(1), may the address sit just anywhere?

It may not. Because malloc hands out the block without knowing what will be stored in it. A double may be placed there, or a pointer, or a large struct. So the standard promises this — an address returned by the malloc family satisfies the alignment suitable for any basic type. The name given to that “strictest basic alignment” is max_align_t, and on this machine it is 16 bytes (chapter 4’s alignment rule made flesh).

Two things follow.

First, allocating small does not mean the block is small. In the example eight one-byte allocations gave neighbouring blocks 32 bytes apart. The gap comes from the space left over to satisfy alignment and the management information (size, status) the allocator attaches to each block. It means a program that allocates countless small pieces uses far more memory than it requested, and that is why the arena and pool approaches we see later were born (chapter 99).

Second, stricter alignment must be requested separately. SIMD (single instruction, multiple data) instructions or hardware DMA (a device reading and writing memory directly, without going through the CPU) sometimes require 64-byte or 4096-byte alignment, and for that there is C11’s aligned_alloc(alignment, size). Two rules must be kept — the alignment must be a power of two, and in C11 the size had to be a multiple of the alignment (a later edition lifted it — the C23 text has no such requirement). What it returns is still freed with free, as usual.

Platform note. The name of aligned allocation differs by platform

The standard’s aligned_alloc came in relatively recently (C11), and before that each platform used a different function — POSIX’s posix_memalign, Windows’s _aligned_malloc (and its partner _aligned_free; on Windows this must not be freed with free). When you meet these names in old code, read them as “an allocation with a stated alignment.”

46.5 The price of two cheap-looking lines, malloc and free — why allocation is expensive#

The latter part of the example repeats the same work three ways, 300,000 times, and measures the time. Allocating and freeing every time is noticeably slower than reuse or the stack — a little over ten nanoseconds per round on this machine. The value itself differs by machine and allocator, but a difference of several times to tens of times is typical (turn optimisation on and the reuse side gets faster still, widening the gap — the output above is this book’s example build, which is unoptimised).

Why is it expensive? malloc looks like the one line “give me slots” but is in fact one round trip to the warehouse management office.

  1. Find a free piece of the right size. The allocator manages returned pieces in lists by size and picks a suitable one when a request comes. Searching the list, cutting a large piece when needed, putting the remainder back in the list — all of it is data-structure manipulation.
  2. Write management information. The size and status must be written per block so that free can later know “how many bytes this was.” So allocation involves writing.
  3. Ask the operating system when the warehouse runs short. When the warehouse is empty it obtains more address space with a system call (brk or mmap). That means going into the kernel and back, which is far more expensive. Fortunately it does not happen often — the allocator takes plenty and cuts it up.
  4. With several threads, locks appear. The warehouse ledger is a shared resource, so contention between threads slows it (chapter 95’s story of races). That is why modern allocators keep a small cache per thread.
  5. The cache is cold. A freshly obtained address is usually not in the cache, so the first access is slow (chapter 12’s ladder). Conversely a reused buffer is already in the cache — one reason the reuse side is fast in the example.

So a practical rule follows. Do not allocate inside a hot loop. Allocate once in advance and reuse, put what has a known size on the stack, or allocate many at once and cut them up. The last is the arena, the subject of chapter 99 and Part XIV.

A common misconception. “free gives memory back to the operating system”

Mostly it does not. free is writing in the allocator’s ledger that “this piece may be used again”, not returning it to the operating system. So it is normal for a program’s memory usage in the task manager to stay the same after releasing a large piece of data — the allocator is holding it for the next request (large blocks are sometimes returned).

This fact explains two things. First, the common misunderstanding of “I freed the memory, so why does it not go down?” Second, the phenomenon of a long-running server holding memory even with no leak — pieces scattered so that a large lump cannot be formed: fragmentation. Chapter 99 faces it head on.

46.6 Allocating in one dimension, using it as two#

Chapter 39 showed real multidimensional arrays such as int m[3][4]. But when the size is settled at run time that syntax cannot be used, and so the commonest shape in practice is to allocate one flat block and index it along two axes.

The heart of it is one line of arithmetic. Allocate rows × cols slots at once and find slot (i, j) as i * cols + j. That is exactly the layout of a real two-dimensional array (row-major, chapter 40) — so the performance is the same and the cache behaves the same way (chapter 12).

examples-en/dynamic-memory/flat2d.c

/* Allocating in one dimension and using it as two — the commonest shape in practice.
   The subscript arithmetic is shut inside one macro instead of written by hand. */
#include <stdckdint.h>
#include <stdio.h>
#include <stdlib.h>

/* The subscript macro: every argument wrapped in parentheses (chapter 65), and the
   product raised to size_t. i and j are evaluated once, so side effects are safe. */
#define AT(p, cols, i, j)  ((p)[(size_t)(i) * (size_t)(cols) + (size_t)(j)])

/* The size computation can overflow — if it does, no allocation is attempted (ch. 52, 80). */
static int *alloc_grid(size_t rows, size_t cols)
{
    size_t cells, bytes;
    if (ckd_mul(&cells, rows, cols))          return NULL;
    if (ckd_mul(&bytes, cells, sizeof(int)))  return NULL;
    return malloc(bytes);
}

int main(void)
{
    const size_t rows = 3, cols = 4;
    int *g = alloc_grid(rows, cols);
    if (!g) { puts("allocation failed"); return 1; }

    /* ── (1) filling and reading — one macro does the subscripts ─── */
    for (size_t i = 0; i < rows; i++)
        for (size_t j = 0; j < cols; j++)
            AT(g, cols, i, j) = (int)(i * 10 + j);

    printf("a 3x4 held in row-major order:\n");
    for (size_t i = 0; i < rows; i++) {
        printf("  ");
        for (size_t j = 0; j < cols; j++)
            printf("%3d", AT(g, cols, i, j));
        printf("\n");
    }

    /* ── (2) the memory is one continuous run ─────────────────────── */
    printf("\nsweeping the same memory in one dimension: ");
    for (size_t k = 0; k < rows * cols; k++)
        printf(k ? " %d" : "%d", g[k]);
    printf("\n(the same layout as a real int m[3][4] — row-major)\n");

    /* ── (3) the common accident: row and column swapped ──────────── */
    printf("\nAT(g, cols, 1, 2) = %d   (row 2, item 3)\n", AT(g, cols, 1, 2));
    printf("AT(g, cols, 2, 1) = %d   (row 3, item 2 — a different slot)\n", AT(g, cols, 2, 1));

    /* ── (4) an overflowing size request is refused ───────────────── */
    int *huge = alloc_grid((size_t)-1 / 2, 8);
    printf("\nan absurd size request: %s\n", huge ? "allocated" : "refused, the computation overflowed");
    free(huge);

    free(g);
    return 0;
}

Three things need care here.

First, do not scatter the subscript arithmetic by hand. Write p[i * cols + j] all over the code and if one place forgets cols it quietly reads a different slot. Wrap it in one macro, as the example does, and there is one place to fix. When writing the macro, keep chapter 65’s rules — wrap every argument in parentheses, and compute the product in size_t to avoid overflow.

#define AT(p, cols, i, j)  ((p)[(size_t)(i) * (size_t)(cols) + (size_t)(j)])

Second, the size computation itself can overflow. rows * cols * sizeof(int) is a product of three numbers, easy to overflow, and an overflow means allocating a small buffer and using it as a large array — the worst kind of accident. The example checks with ckd_mul (chapters 56 and 96) first and does not even attempt the allocation if it overflows.

Third, nail down the order of rows and columns in the documentation. AT(g, cols, 1, 2) and AT(g, cols, 2, 1) are different slots. Half the mistakes come from here, so name the parameters rows and cols plainly and write the order down.

Q. Could an array of pointers (int **) be used instead, keeping the m[i][j] syntax?

A. It can, and it is a common method — allocate each row separately and hold their addresses in an array. The price is high, though.

The memory is scattered. With rows far apart, chapter 12’s locality breaks and the cache hit rate falls. There are many allocations. One malloc per row, as many failure paths, and as many calls to free, in reverse order. There is one more indirection. m[i][j] follows an address twice.

And decisively, int[3][4] and int ** are different types. Pass the name of a real two-dimensional array to a function taking int ** and it is a compile error; force it through with a cast and it is outside the contract — because, as chapter 39 showed, int m[3][4] decays to int (*)[4], not to int **. This misunderstanding is the most frequent accident with multidimensional arrays.

In short — a real two-dimensional array when the size is fixed; a one-dimensional allocation plus a subscript macro (or a VLA (variable-length array) parameter, chapter 39) when the size is settled at run time; and int ** when the rows have genuinely different lengths (a ragged array).

46.7 Ownership — who is responsible for giving it back#

The address malloc gave can be copied into several variables and can travel between functions. And yet free must be called exactly once — from which comes a core discipline of C programming: naming, at any moment, the one party responsible for releasing that memory — the notion of ownership. C has no syntax that enforces ownership — so ownership is expressed in comments, names and conventions (“this function transfers ownership of the returned pointer”, and so on). Modern languages lifted ownership into the type system (Rust’s ownership, C++‘s smart pointers) to make the machine enforce this discipline — the concern of the neighbouring languages seen in chapter 1 arose exactly here.

In practice. The three typical accidents — leak, double free, use after free

Accidents with dynamic memory come with three faces. A leak is forgetting to give back — a slowly fatal disease. A double free is calling free twice on the same address, which wrecks the warehouse ledger so that every allocation after it is contaminated. The most dangerous is use after free — continuing to use the address of a slot that was given back. It is chapter 45’s dangling pointer reproduced in the heap, and since the warehouse soon hands that slot to another request, an attacker can put their own data in that place. In the lists of severe vulnerabilities of browsers and kernels, use-after-free is still near the top today, which is why systems programming as a whole has moved in the direction of “let the language enforce ownership.” The defence in C is discipline plus tools — the practice of assigning nullptr to a pointer right after free, and chapter 18’s sanitizers.

Neither is a cure-all, though. Assigning nullptr stops reuse and double free through that one variable only; any other alias holding the same address is left as it was — take it as a local defence that works only when there are no aliases. ASan catches use-after-free and double free very well, but detecting leaks needs LeakSanitizer to be on with it, and that depends on the platform and the settings (a default build for Linux x86-64 usually enables both).

Q. Is it then best to avoid dynamic memory as far as possible?

A. That really is the first strategy, and the reason this book has come this far without malloc — data of known size is fastest and safest kept in automatic variables (the stack), where there is nothing to release and the three accidents are sealed off at the source. In embedded and safety-critical fields, conventions banning dynamic allocation outright are common. But data whose size is determined at run time (a list supplied by the user, the contents of a file) needs the warehouse in the end — and then the practical answer is to make ownership clear, check with tools, and use well-made components that manage allocation and bounds together, like chapter 44’s proven.
