1 Setting the scene

The need for this chapter, and its context

For someone starting out today, C is a language that needs a great deal of explanation. It has survived half a century and is still in service, and the world changed enough in that time that without knowing why it looks the way it does, every rule reads as arbitrary. So the first chapter sets out the situation C finds itself in and how this book is meant to be read.

By the end of this chapter

What programming is, what kind of language C is and where it currently stands, and why a new introduction to C is needed right now. This chapter also explains how the book was written and how it is meant to be read.

The questions this chapter answers

  1. If there is that much old-standard code about, is it not more practical to learn the old idiom first?
  2. Then would it not be better to start with Rust or Zig instead?
  3. If it is a book promoting a library, does the content not lean that way?

1.1 What is programming#

A computer is a machine that does what it is told. The difficulty is in the telling. A computer does not understand human speech; it moves only when it receives brutally simple instructions in order. Programming is the work of turning what we want into a list of such simple instructions, and the agreed notation for writing that list down is a programming language.

There are hundreds of languages. Some sit close to the human side and are comfortable to write; others sit close to the machine and let you handle it down to its details. C, the subject of this book, is the leading example of the latter — the language of systems, which has held the machine-side seat for half a century.

1.2 Where C is#

C is not easy to spot. Other languages stand at the front of flashy apps and websites. Lift the lid on them, though, and C is nearly everywhere underneath.

In practice. A day spent on top of C

The alarm goes off on your phone in the morning — on Android, the core of that operating system (the Linux kernel) is written in C. You send a message and the radio module’s firmware, written in C, goes to work. You open the web and a server and a browser exchange data — the encryption library and transfer tool doing it (OpenSSL, curl) are built in C. SQLite, which the app uses to store things (which its developers describe as the most widely deployed database in the world), is written in C too. The braking system in a car, the control panel of a washing machine, a pacemaker: in embedded devices too, C is one of the commonest choices. Even when you run machine learning from Python, a large part of the engine actually doing the arithmetic underneath is C (and its neighbours). Learning C means becoming able to read and write this invisible layer.

1.3 The world of C is changing a great deal right now#

So why a new introduction now? If the language is old, surely an old book will do. It will not — the landscape around C looks quiet but is changing a great deal, and that change is where this book starts.

First, several eras coexist inside C as it stands today. C is governed by an official specification, the standard, and it has come through C89 (1989), C99, C11 and C17 to the current C23. The trouble is that old standards never retire. Industry is still full of code written exactly as it was in the C89 days, many textbooks are written in that era’s idiom, and alongside them C23 has brought new vocabulary such as bool and nullptr into the standard. Dialects from eras more than thirty years apart live together under the single name “C”.

Q. If there is that much old-standard code about, is it not more practical to learn the old idiom first?

A. Code you write takes the current standard as its basis; the old standards are needed for reading. The day will come when you have to read old code — which is why this book covers history and the stories behind old idioms throughout. But there is no reason for code you write today to be in the old idiom. The newer standards are the result of decades of field experience filling in the traps of the older ones. The earlier you are in your learning, the more you gain by starting from today’s safest idiom; the old idiom is quite enough as background knowledge of “why they wrote it that way.”

Second, neighbouring languages are encroaching on C’s territory. C++, which started under the same roof, has gone through revisions at a rapid pace and become an enormous language — vastly expressive, but grown large enough that people say hardly anyone knows all of it. From another direction a new generation of systems languages has appeared. Rust promises to seal off, at the language level, the memory accidents C has long suffered; Zig marches under the banner of “succeed C, but simpler and more honest.” Each is pushing into ground C used to hold alone. Rust code beginning to enter operating system kernels was a symbolic moment.

Third, under that pressure C itself is showing signs of change. C23 was the largest revision in recent memory, and the standards committee continues work on tightening the rules for pointers (provenance) and on the safety discussion. C is a slow-moving language, but the direction is clear — towards clearer contracts and safer defaults.

A common misconception. “C is an old language, so learning it will soon be pointless”

It is a plausible worry — the new languages are arriving in force. But the evidence points more the other way. As we saw above, the world’s infrastructure stands on C, and this layer is so expensive to replace that it moves only on the scale of decades. Even the new languages are born with the ability to talk to C (a C interface) as a condition of survival — C is close to a lingua franca of the systems world, so whether you write Rust or Zig, at the boundaries of a system you will have reason to read and understand C. As neighbouring languages multiply, the need to read C does not shrink — the places where those languages meet C, if anything, grow.

Q. Then would it not be better to start with Rust or Zig instead?

A. Honestly: it depends on your goal. If the goal is to build one safe application right now, other choices are good too. But if the goal is to understand how a computer actually works from the ground up, C is very good teaching material. The layer between C and the machine is thin, so learning C turns out to be the same thing as learning about the machine, memory and the compiler. Even that thin layer holds a contract, though — the “abstract machine” shown in chapter 15: C is not a language that touches hardware directly but one that meets it through that contract. And that understanding is capital you can carry with you into Rust or Zig unchanged. This book is here to supply that capital in today’s idiom.

1.4 Why this book was made#

The changes described above are the first reason this book was made. With several standards coexisting, neighbouring languages competing, and C itself changing, what is needed now is an introduction that starts from today’s C (C23) and today’s practice. So the table of contents was rebuilt from scratch. Instead of listing grammatical items in order, the book starts with the basics of the machine and meets C in the order in which the concepts become necessary.

The second reason is best stated plainly. The author builds and publishes a C library called proven. proven aims to provide, in verified form, the fundamentals where C programming most often goes wrong — handling strings, processing input, converting numbers. Many of C’s famous traps go off in this layer of fundamentals, and the standard library, for historical reasons, carries those traps as they are. The later parts of this book (from Part VII on) show why the traps are genuinely dangerous and then use proven, mostly in Part XIV, as the basis of examples for how they can be blocked. This book is also meant to make that library known — but it was written to help readers who have no need for proven, too. First the concepts are learned properly in standard C alone; once the problems of the established coding style and libraries are understood, proven is learned as an answer to them. Even if you never use proven, the new style and ways of working learned along the way will serve you well.

Q. If it is a book promoting a library, does the content not lean that way?

A. The structure is built to prevent it. The first forty-odd chapters do not use a single line of proven — they proceed purely on the basics of computing and standard C. proven appears only after the text itself has made plain “why a tool like this is needed”, and even then the standard approach is shown first and proven offered as a comparison. The C knowledge in this book stands entirely on its own without proven.

1.5 How to read this book#

This is a book to be read. That sounds obvious, but as a promise from a programming book it is unusual.

The body is written to be read front to back. So it has no instructions to “try it yourself”. You do not need to be sitting at a computer — on a sofa, on the train, you can read it from front to back. The examples in the body are demonstrated on the page from beginning to end, and the results of running them are printed on the page as well. Those results are not decoration but the real thing: every example in this book carries the output obtained by a machine actually compiling and running it.

Practice happens at the end of each part. Every part ends with an exercise chapter, and the answers are gathered at the back in “Answers to the exercises”. Having finished a part, try its exercises and compare with the answers (how to use them is in the preface, “A request to learners”). Most exercises show wrong code and ask what is wrong and why — they train an eye for what is wrong. Walking you step by step through building one program to the end from an empty file is something the existing good C primers do well. This book’s place is beside them — the reading side, the one that explains why C is shaped as it is.

It proceeds by question and answer. Throughout the text, the question a reader might have just formed is asked on the spot and answered immediately. It is best to pause for a moment when you meet a question and try to answer it yourself before reading on, but reading straight through is fine too — the exchange is part of the explanation.

It does not ask you to memorise. Anything worth remembering comes back at the head of a later chapter under the name “looking back”, where you meet the previous chapter’s material again as a slightly deeper question. That is this book’s revision device. It is fine to have forgotten — the answer is right next to it. The exercises at the end of each part do the same work — they do not check what you memorised; they make you bring out and use what you learned.

A chapter handles one question. Each chapter takes up one question, treats it until no misunderstanding is left, and moves on — so some chapters are short and some are long. Large subjects pass by several times across several chapters, spiral-fashion, a little deeper each time. Not everything is said in one chapter, so if you are left curious about something, that is usually deliberate — you will meet that curiosity again a few chapters later.

Now we begin. The first step is not C but the computer itself — why C looks the way it does only makes sense once you have seen the machine it was born on. The four remaining chapters of this part draw what that machine and its memory look like: the computer as three parts (chapter 2), the numbers stamped on memory’s cells (chapter 3), the odd corners of those numbers (chapter 4), and the four regions the address space divides into by purpose (chapter 5). None of them contains any C syntax; they only draw pictures.
