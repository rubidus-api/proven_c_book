돌아보기

103장 까지의 sumcsv 는 한 파일 sumcsv_io.c 184줄 안에 들어 있다. 한 사람이 읽고 고치기에 그리 길지도 않은데, 왜 굳이 sumcsv.h·parse.c·sum.c· main.c 네 파일과 Makefile 로 쪼개고 입출력 정답 파일까지 스물네 개나 만드는가?

답. 한 줄 입력 계약이 호출 가능한 부품이 되는 순간부터 입출력(stdin/stdout)과 계산(parse/sum)은 서로 다른 속도로 바뀐다. 파일이 하나일 때는 sum_line 만 단위 시험하거나 다른 도구가 가져다 쓸 틈이 없고, fprintf 와 파싱 규칙이 뒤섞인다.

★ 파일을 나누면 헤더의 변화를 make 가 놓칠 위험이 새로 생긴다(118장에서 정면으로 다룬다). 그래서 다중 파일 프로젝트는 「파일 나누기 + 헤더 의존 추적 + 입출력 전체를 고정한 골든 시험 + 고치기 전 실패 확인」이 한 묶음으로 따라다닌다.

이 장의 필요성과 맥락

이 장은 103장 에서 완성한 한 줄 합산기를 작지만 완성된 C 프로젝트로 세우는 자리다. 60장 의 번역 단위 분리와 18장 의 엄격한 빌드 옵션을 실물에 적용하고, 뒤의 제15부 118장·119장 에서 큰 팀 규모로 넓혀 다룰 -MMD -MP 와 골든 시험·자동 시험을 작은 코드베이스에서 먼저 손에 익힌다.

이 장이 끝나면

이 장을 마치면 공개 인터페이스 sumcsv.h, 번역 단위 셋(parse.c·sum.c· main.c), 의존을 추적하는 Makefile, 8건의 입출력/종료 코드 골든 시험, 그리고 고치기 전 판으로 먼저 실패를 확인하는 검증까지 한 번의 run.sh 로 돌려 확인한다.

이 장에서 답할 질문

  1. 테스트가 통과한 run.sh 끝에서 sumcsv-buggy 와 tests/tmp 를 지우는 까닭은 무엇인가?
  2. 1판 프로젝트에서 main.c 를 LINE_CAP = 4096 으로 두었다. 헤더·소스 분리 뒤에 바꾸고 싶다면 어디만 고치면 되는가?

104.1 한 파일에서 네 파일로 — 계약과 구현 가르기#

먼저 헤더 sumcsv.h 가 바깥에 약속하는 경계부터 본다.

#ifndef SUMCSV_H
#define SUMCSV_H

#include <stddef.h>
#include <stdint.h>

typedef enum {
    SUMCSV_OK = 0,
    SUMCSV_ERR_EMPTY,
    SUMCSV_ERR_EMPTY_FIELD,
    SUMCSV_ERR_BAD_NUMBER,
    SUMCSV_ERR_RANGE,
    SUMCSV_ERR_OVERFLOW,
    SUMCSV_ERR_TRAILING,
} sumcsv_err_t;

/* 한 줄 합산 결과와 오류 위치(바이트 오프셋) */
struct sumcsv_res {
    sumcsv_err_t err;
    int64_t      sum;
    size_t       pos;
};

const char *sumcsv_err_str(sumcsv_err_t err);

[[nodiscard]]
sumcsv_err_t sumcsv_parse_i64(const char *start, const char **out_rest,
                              int64_t *out_val);

[[nodiscard]]
struct sumcsv_res sumcsv_sum_line(const char *line);

#endif

두 함수 모두 반환값을 무시하면 컴파일러가 경고하도록 [[nodiscard]] 를 달았고, sumcsv_sum_line 은 sumcsv_err_t 열거형, 합계 sum, 막힌 바이트 오프셋 pos 세 가지를 구조체 값으로 묶어 돌려준다. 문자열 포인터가 아니라 열거형 코드라 호출자가 기계적으로 갈래를 탈 수 있고, sumcsv_err_str 로 사람 읽는 문구로 바꾼다.

네 파일이 각각 맡는 일은 다음과 같다.

104.2 헤더 의존을 놓치지 않는 Makefile 과 자동 시험#

파일이 여럿이 되면 Makefile 은 컴파일 옵션만이 아니라 .h 의존까지 기록해야 한다. 05-project/Makefile 은 핵심 열아홉 줄이다.

CC     ?= gcc
CFLAGS  = -std=c23 -Wall -Wextra -Werror -MMD -MP
OBJS    = main.o parse.o sum.o
DEPS    = $(OBJS:.o=.d)

all: sumcsv

sumcsv: $(OBJS)
  $(CC) $(CFLAGS) -o $@ $(OBJS)

%.o: %.c
  $(CC) $(CFLAGS) -c -o $@ $<

test: all
  sh ./run.sh

clean:
  rm -f sumcsv sumcsv-buggy $(OBJS) $(DEPS)

-include $(DEPS)

-MMD -MP 는 컴파일러가 .c 를 읽으면서 열어 본 헤더 목록을 .o 와 나란히 .d 파일에 적어 내게 한다. -include $(DEPS) 가 그 규칙을 읽으므로 sumcsv.h 의 열거형 순서나 구조체 멤버가 바뀌면 그것을 포함한 main.o·parse.o·sum.o 가 모두 빠짐없이 다시 지어진다(118장에서 이 규칙이 빠졌을 때 실제로 터지는 버퍼 넘침 사고를 본다).

이제 이 프로젝트를 빌드하고 8개 골든 시험과 실패 확인 검사를 한꺼번에 돌린다.

examples/sumcsv/05-project/run.sh

#!/bin/sh
# 05-project: 여러 파일 빌드 + 골든 시험 8건(stdout/stderr/종료코드) + 고치기 전 회귀 시험 실패 확인.
set -eu
cd "$(dirname "$0")"
CC=${CC:-gcc}
make -s CC="$CC" clean all
mkdir -p tests/tmp

fail=0
for input in tests/in/*.txt; do
    name=$(basename "$input" .txt)
    rc=0
    ./sumcsv < "$input" > "tests/tmp/$name.out" 2> "tests/tmp/$name.err" || rc=$?
    printf '%s\n' "$rc" > "tests/tmp/$name.rc"
    if cmp -s "tests/expected/$name.out" "tests/tmp/$name.out" &&
       cmp -s "tests/expected/$name.err" "tests/tmp/$name.err" &&
       cmp -s "tests/expected/$name.rc"  "tests/tmp/$name.rc"; then
        printf '  PASS golden %s\n' "$name"
    else
        printf '  FAIL golden %s\n' "$name"
        fail=1
    fi
done

$CC -std=c23 -Wall -Wextra -Werror -o sumcsv-buggy main.c parse.c sum_buggy.c
brc=0
./sumcsv-buggy < tests/in/06_trailing_comma.txt > tests/tmp/bug.out 2> tests/tmp/bug.err || brc=$?
printf '%s\n' "$brc" > tests/tmp/bug.rc
if cmp -s tests/expected/06_trailing_comma.out tests/tmp/bug.out &&
   cmp -s tests/expected/06_trailing_comma.err tests/tmp/bug.err &&
   cmp -s tests/expected/06_trailing_comma.rc  tests/tmp/bug.rc; then
    printf '  FAIL regression-before: buggy binary unexpectedly passed\n'
    fail=1
else
    printf '  PASS regression-before: buggy caught by 06_trailing_comma (rc=%d, out=%s)\n' \
        "$brc" "$(tr -d '\n\r' < tests/tmp/bug.out)"
fi

if cmp -s tests/expected/06_trailing_comma.rc tests/tmp/06_trailing_comma.rc; then
    printf '  PASS regression-after: fixed passes 06_trailing_comma (rc=%s)\n' \
        "$(tr -d '\n\r' < tests/tmp/06_trailing_comma.rc)"
fi

make -s CC="$CC" clean
rm -rf sumcsv-buggy tests/tmp
exit "$fail"

실행 결과

  PASS golden 01_basic
  PASS golden 02_spaces_crlf
  PASS golden 03_negatives
  PASS golden 04_empty
  PASS golden 05_empty_field
  PASS golden 06_trailing_comma

  PASS golden 08_overflow
  PASS regression-before: buggy caught by 06_trailing_comma (rc=0, out=30)
  PASS regression-after: fixed passes 06_trailing_comma (rc=1)

104.3 출력 셋을 함께 굳히는 골든 시험과 고치기 전 실패 확인#

run.sh 가 확인하는 시험은 두 층이다.

첫째는 골든 시험 여덟 건(01_basic   08_overflow)이다. tests/in/*.txt 입력 하나마다 기대하는 표준 출력(.out), 표준 오류(.err), 종료 코드(.rc) 파일 셋을 모두 cmp -s 로 맞대어 본다. 정상 입력(01_basic, 02_spaces_crlf, 03_negatives)은 .err 가 0바이트이고 .rc 가 0 이어야 통과하며, 실패 입력 다섯 건(04_empty   08_overflow)은 .out 이 정확히 0바이트이고 .err 문구와 .rc=1 이 일치해야 통과한다. stdout 만 비교했더라면 오류 상태에서 부분 출력이나 잘못된 종료 코드를 흘리는 결함을 놓친다.

둘째는 고치기 전 실패 확인(regression-before → regression-after)이다. sum_buggy.c 는 후행 쉼표(at_eol(skip_ws(p))) 검사를 일부러 뺀 옛 판이다. run.sh 는 먼저 sumcsv-buggy 를 빌드해 06_trailing_comma.txt 에 대고 돌려 실제로 실패함(rc=0, out=30)을 확인한 뒤, 고친 바이너리 ./sumcsv 가 같은 입력을 rc=1 로 막는 것을 확인한다. 고쳤던 결함이 나중에 다시 살아나는 현상을 회귀(regression — 고쳤던 결함이 되돌아오는 것)라 부르며, 119장 에서 이 회귀 시험 순서를 팀 전체의 시험 규율로 정식으로 다룬다.

흔한 오해. “골든 시험은 표준 출력(.out)만 비교하면 된다”

명령줄 도구에서 계약은 stdout·stderr·종료 상태 세 줄의 짝이다. 06_trailing_comma 에서 sumcsv-buggy 는 stderr 에 아무것도 안 적고 stdout 에 30 을 내며 0 으로 끝난다. 반대로 어떤 버그는 stderr 에 메시지를 내고 stdout 에도 쓰레기 숫자를 흘리거나, 메시지는 맞는데 종료 0 을 돌려주기도 한다. 세 파일(.out·.err·.rc)을 함께 비교해야 스트림 분리 계약까지 지켜진다.

문. 테스트가 통과한 run.sh 끝에서 sumcsv-buggy 와 tests/tmp 를 지우는 까닭은 무엇인가?

답. 시험이 남긴 임시 산출물이 다음 시험이나 다른 도구의 작업 폴더를 오염시키지 않게 하기 위해서다. 시험 입력(tests/in)과 기대 결과(tests/expected)는 고정된 준비물로 남고, 실행 중에 만든 임시 파일은 깔끔히 치운다.

문. 1판 프로젝트에서 main.c 를 LINE_CAP = 4096 으로 두었다. 헤더·소스 분리 뒤에 바꾸고 싶다면 어디만 고치면 되는가?

답. 줄을 읽는 정책은 main.c 에만 들어 있고, sumcsv.h 와 parse.c·sum.c 는 널로 끝나는 한 줄 문자열 const char * 만 받는다. 그래서 입출력 버퍼 방식을 고정 배열에서 동적 버퍼로 바꾸더라도 파서와 합산 모듈은 건드리지 않거나 별개로 시험할 수 있다.

복습 정리

sumcsv 1판이 멀티파일 구조와 자동 시험까지 갖추어 끝났다. 이제 1판을 닫는 마지막 물음이 남는다 — 여러 줄, 열 번호 선택, 따옴표 감싼 필드, 임의 길이 줄이라는 새 요구가 들어올 때 순수 C 코드에는 어떤 부담이 쌓이는가. 다음 장이자 이 부의 마지막 장(105장)에서 직접 2판을 짜며 그 비용을 잰다.
