# RFC-0002: 책 구성 (장 체계)

- Status: Accepted
- Date: 2026-08-04 (rev.b 2026-08-04: 4장 최소 도구 상자·5장 선언 신설, 구조체·공용체 후행 확정, 5부 18장으로 재편)
- Scope: 부(Part)와 장(Chapter)의 체계, 각 장의 역할과 RFC-0001 장치 매핑.
- 전제: RFC-0001 교수 설계 (읽기 전용 문답형). 기존 C 입문서 목차 답습 금지 (R05).
- 사용자 확정 골격: **1장 배경설명 → 2장 전산의 기본과 배경지식 → 3장 헬로 월드와 개발환경 구축 → 4장 최소한의 도구(프로그램 구조·수식·입출력 함수 사용) → 5장 선언(변수·함수)**. 구조체·공용체는 후반부(12장)로 미룬다. 3장은 특정 플랫폼을 제시하되 일반적인 내용을 주로 삼고, 일반적인 컴파일 과정을 바탕으로 gcc·clang 등을 기반으로 설명한다.

## 1. 구성 원리

기존 입문서의 "문법 항목 순서"(자료형→연산자→제어문→함수→배열→포인터…)를
따르지 않는다. 대신 **개념의 의존 순서**를 따른다: 각 장은 앞 장까지의
개념만으로 완전히 설명 가능해야 하고, 다음 장의 심화 문답이 소환할 거리를
남겨야 한다. 문법은 개념이 필요로 하는 시점에 그 개념의 표기법으로
등장한다.

여기에 rev.b에서 두 가지 원리를 추가한다.

**사용이 정의보다 먼저다**: 독자는 먼저 남이 만든 것을 읽고 쓰는 법(4장:
호출·수식·입출력)을 익히고, 그다음에 스스로 이름을 만드는 법(5장: 선언)을
배운다. 언어 습득의 자연 순서(듣기·읽기 → 말하기·쓰기)와 같다.

**나선형 최소 집합** [사용자 확정]: 한 장에 한 주제를 다 넣으려는 유혹을
버린다. 처음에는 **최소 집합**만 설명하고, 뒤 장들이 필요해지는 시점마다
**덧붙여 가며 규모를 불린다**. 같은 주제를 여러 번, 매번 조금 더 깊게
지나간다(나선형). 심화 문답(RFC-0001 §3.2)이 이 재방문의 공식 통로다.
대표 적용 — 연산자 배분 계획:

| 시점 | 덧붙는 연산자/수식 요소 | 동기 |
|---|---|---|
| 4장 | 기본 산술 최소 집합: `+ - *`, 괄호, 리터럴, 호출 | 수식=값 개념 확립 |
| 5장 | 대입 `=` | 변수가 생겼으므로 |
| 6장 | `/ %`(정수 나눗셈의 진실), 비트 연산, 형변환의 첫걸음 | 정수 의미론 |
| 7장 | 비교 `== != < …`, 논리 `&& \|\| !`, 증감 `++ --`, 복합 대입 | 조건·루프가 요구 |
| 8장 | 조건 연산자 `?:`, 쉼표의 함정 | 함수·수식 스타일 |
| 9장 | `& *`(주소·역참조), `sizeof` | 포인터가 요구 |
| 12장 | `. ->`, 복합 리터럴 | 구조체가 요구 |

연산자 전체 표는 부록 참조 자료로 만들고, 본문은 위 배분을 따른다.

축은 세 가지다:

- **수학적 기반** (R07): 모든 개념은 정확한 수학적 착지점을 갖는다.
- **기계 현실**: C는 기계를 숨기지 않는 언어다. 메모리·비트·컴파일 과정이 이야기의 배경이 아니라 주인공이다.
- **안전 우선**: 오류 처리와 계약(proven의 관점)을 뒤로 미루지 않고, 개념이 등장하는 순간부터 함께 다룬다.

## 2. 부·장 체계

### 제1부 — 바탕 (컴퓨터와 계산)

**1장. 배경설명** [사용자 확정]

프로그래밍이란 무엇인가, 왜 C인가(깊은 역사는 2장이 하드웨어 이야기에
엮어 다룬다), 이 책의 읽는 법(문답을 따라 읽으면 된다는 것, 실습을 시키지
않는다는 것). 심화 문답 없음(첫 장). 실제 사례: C가 오늘날 실제로 어디에
있는가(운영체제, 임베디드, 인터넷 기반시설).

**2장. 전산의 기본과 배경지식** [사용자 확정 — 내용 궤적·서사 구조·비중 확정]

책에서 **상당한 분량**을 차지하는, 제1부의 중심 장이다. 이후 모든 장이
심화 문답으로 소환할 배경지식의 저수지 역할을 한다. 통상 입문서가 본문
중간중간에 흩뿌리거나 부록으로 미루는 배경(하드웨어 현실, 표준의 역사,
문자와 수의 표현)을 여기에 전면 배치한다.

**이중 트랙 서사**: 전산의 기본을 C 언어 역사와 절 단위로 엮어서 전개한다.
장의 관통 명제 — "C의 역사는, 기계가 복잡해질수록 언어가 기계의 별명에서
**추상 기계의 계약**으로 정밀해져 온 역사다". 각 절이 [기계 이야기 ↔ 그
시점의 C 역사] 쌍으로 진행된다.

**역사 서술 원칙 (기능적 역사)**: 고리타분한 연대기 나열(발명가·연도·세대
구분 암기류)은 뺀다. 역사는 **지금의 C를 설명하는 데 필요한 만큼만**,
"오늘의 이 모양이 왜 이런가"에 답하는 형태로만 등장한다. 위 이중 트랙과
아래 (6)(9)의 역사가 전부 이 원칙을 따른다.

1. **단순한 기계 모델 ↔ C의 탄생**: CPU·메모리·클록 — 기계는 클록에 맞춰
   단순한 단계를 반복할 뿐이라는 계산 모델. 정보의 표현(비트, 이진법).
   그 단순한 기계(PDP-11 시대)의 정직한 별명으로 태어난 언어: B에서 C로,
   Unix와 K&R. 수학 박스: 위치 기수법, 2^n.
2. **워드와 메모리 주소 ↔ C의 원형**: 메모리는 번호 붙은 칸(바이트)의
   열이다. **워드**란 무엇인가 — 기계가 한 번에 다루는 자연스러운 크기,
   바이트와 워드의 관계, "32비트/64비트 컴퓨터"라는 말의 실제 의미,
   레지스터·버스 폭과의 관계. 주소라는 착상. 워드가 여러 바이트라면 메모리에
   어느 쪽부터 놓이는가 — **리틀 엔디안과 빅 엔디안**(그림으로 두 배치를
   대조, 네트워크 바이트 순서라는 합의, 파일·통신에서 실제로 문제가 되는
   사례). 대표 오개념: "메모리를 읽으면 적힌 순서대로 수가 보인다".
   주소에 얽힌 특수 지식 세 가지 — **0번 주소의 특별함**(플랫폼마다 다르다:
   보호 모드 OS에선 접근 금지 페이지, 임베디드에선 인터럽트 벡터 테이블
   등 멀쩡한 메모리인 경우도 있다), **정렬 제한**(워드는 아무 주소에서나
   읽을 수 없다 — 정렬된 주소, 위반 시 플랫폼별 결과: 느려지거나 버스
   폴트), **하위 주소 비트의 활용**(정렬 덕에 항상 0인 하위 비트에 정보를
   숨기는 태그 포인터 기법 — 실제 런타임·GC 사례). C의 타입과 포인터가
   이 기계상을 그대로 반영했다는 것 (9장 포인터·12장 표현/패딩·정렬의 씨앗).
3. **속도의 기계장치 ↔ 표준의 탄생(C89)**: 다층 캐시, 파이프라인, 분기
   예측 — 단순한 모델이 무너지는 곳. 기계와 컴파일러가 다양해지자
   방언이 난립했고, 프로그래머와 구현 사이의 **계약**으로서 ANSI C(C89)가
   태어났다. 실제 사례: 캐시 친화/비친화 코드의 실측 속도 차, 분기 예측
   실패 비용.
4. **컴파일러 최적화 ↔ 추상 기계의 정밀화(C99·C11)**: 컴파일러는 소스를
   그대로 번역하지 않는다 — "관찰 가능한 결과가 같다면" 마음껏 재배열·
   제거·변형한다. 그 자유의 근거가 표준의 **추상 기계(abstract machine)**
   이고, C99·C11이 이를 정밀화해 왔다(엄격한 앨리어싱, 메모리 모델)
   (15장 UB의 씨앗).
5. **그래서 C는 추상적인 언어다 ↔ 현재(C17·C23)와 최신 흐름**: C는
   기계어의 별명이 아니라 추상 기계의 언어이며, 그래서 추상적으로
   접근해야 한다 — 실제 하드웨어(3)와 최적화(4)가 그 사이에서 자유롭게
   움직이기 때문이다. 대표 오개념: "C는 하드웨어를 직접 조작하는 언어다".
   최신 흐름: **포인터 프로버넌스(provenance)** 등 포인터 제한이 점점
   명시적·엄격해지는 방향 (9장·15장의 씨앗).
6. **문자와 텍스트 ↔ 표준 속의 흉터**: 문자 셋과 인코딩의 역사 —
   **EBCDIC**, **ASCII**, **ISO 646**(7비트 국가 변형: 나라마다 `{ } [ \`
   자리가 다른 글자였다), 그 흉터가 C에 남긴 **삼중자(trigraph)·
   이중자(digraph)**, 그리고 C23에서 삼중자가 마침내 제거되기까지 —
   문자셋 역사가 곧 C 표준 역사의 한 단면임을 보인다. 이어서 **ISO 8859
   Latin 계열**, 멀티바이트 인코딩의 혼란, 유니코드의 등장, **가변 길이
   인코딩**과 UTF-8. 수학 박스: 코드 포인트 공간의 크기, UTF-8 바이트 구조.
7. **수의 표현 ↔ IEEE 754라는 계약**: 정수 너머의 수를 기계에 담는 두 가지
   방법 — **고정소수점**(위치를 약속으로 정한다; 임베디드·금액 계산의
   현실)과 **부동소수점**(과학적 표기법의 기계판). 벤더마다 다르던 부동
   소수점이 **IEEE 754**(1985)로 통일된 역사 — (3)의 C89와 같은 시대,
   같은 이유의 "계약"이다. 형식의 구조(부호·지수·가수), 유한하고 근사하는
   수의 세계. 수학 박스: IEEE 754 형식, 표현 가능한 수의 집합 (13장 실수
   장이 이 절을 심화 문답으로 회수해 C의 float/double 실무로 간다).
8. **CPU와 GPU ↔ C는 어느 기계의 언어인가**: 같은 트랜지스터로 만든 두
   가지 다른 답 — CPU는 **지연시간**을 줄이는 기계((3)의 캐시·분기 예측·
   파이프라인이 전부 이를 위한 장치임을 회수)이고, GPU는 **처리량**을
   위한 기계다(수천 개의 단순한 코어, 같은 연산을 데이터 더미에 한꺼번에).
   실제 사례: 그래픽에서 범용 계산(GPGPU)·AI로 온 역사, CUDA·OpenCL이
   C의 방언으로 태어난 이유. C의 추상 기계는 CPU상(像)이라는 것 — 관통
   명제와 접속하며 장을 닫는다.
9. **스트림의 기원 ↔ 펀치카드·라인프린터·프린터 터미널**: 컴퓨터의
   입출력이 왜 "문자가 한 줄씩 흐르는 것"인가 — **펀치카드**(한 장 = 한
   레코드/한 줄, 80컬럼의 유래), **라인프린터**(줄 단위 출력), **프린터
   터미널**(텔레타이프: 종이에 찍히는 대화, `tty`라는 이름과 개행 문자
   `\n`·캐리지 리턴의 유래, 행 버퍼링이 자연스러웠던 이유)이 그 답이다.
   화면 터미널은 프린터 터미널의 흉내라는 것. 이 물리적 계보가 C의
   **스트림** 모델(문자의 흐름, 표준 입력/출력, stdio)로 이어졌다 —
   3장의 헬로 월드(`printf`)와 4장 입출력이 회수하는 씨앗.

오개념: "컴퓨터는 수학을 잘한다"(유한하고 근사한다 — (7)에서 절반을
해소하고 13장이 마무리), "C는 하드웨어 직접 조작 언어다"(→추상 기계).
이 장은 의도적으로 크다. 집필 중 비대해지면 (1)~(5)(8) 기계 편 /
(6)(7)(9) 표현·입출력 편으로 2개 장 분할을 허용한다 (§4). 분할해도
이중 트랙(기계↔역사) 서사는 유지한다.

**3장. 헬로 월드와 개발환경 구축** [사용자 확정]

첫 프로그램을 지면에서 시연하고, 소스가 실행 파일이 되기까지의 **일반적인
컴파일 과정**(전처리→컴파일→어셈블→링크)을 중심에 둔다. 도구는 gcc와
clang을 기반으로 설명한다. 개발환경은 특정 플랫폼 하나를 예시로 제시하되
(플랫폼 선정은 §4 미결), 내용은 어느 플랫폼에서든 통하는 일반론을 주로
삼는다. 심화 문답: 2장의 추상화 계층 위에서 "컴파일러는 몇 층에서 몇 층으로
내려가는 번역인가", 그리고 2장 (9)를 회수해 "`printf`가 찍는 곳은 왜
'화면'이 아니라 '표준 출력 스트림'인가".

### 제2부 — 언어의 뼈대 (읽기, 그다음 쓰기)

**4장. 최소한의 도구 상자 — 구조, 수식, 입출력** [사용자 확정]

다음 진행을 위한 최소한의 것들. 새 개념의 "정의"가 아니라 이미 있는 것의
**사용법**을 다룬다 — 독자가 작은 프로그램을 읽고 변형 시연을 따라올 수
있게 만드는 장이다.

- **프로그램의 구조**: 3장의 헬로 월드를 해부한다 — `#include`라는 준비,
  `main`이라는 약속된 출발점, 문장과 블록, 세미콜론, 주석. "위에서
  아래로 한 문장씩"이라는 실행 모델(2장 (1) 계산 모델의 회수).
- **수식(expression)**: 값, 리터럴, 연산자, 평가라는 개념 — "수식은
  계산되어 값이 된다". **기본 산술연산 최소 집합만** 다룬다: `+ - *` 와
  괄호(나선형 최소 집합 원리, §1의 배분표). 나눗셈은 정수의 진실(버림·
  나머지)이 필요하므로 6장으로 미루고, 여기서는 예고만 한다. 우선순위는
  전부 외우게 하지 않는다 — 괄호 관행.
- **함수 사용**: 함수를 "만드는" 법이 아니라 **부르는** 법 — 호출, 인자,
  반환값. `printf`가 바로 함수 호출이었다는 것.
- **최소 입출력**: `printf`의 서식(필요한 만큼만: `%d`, `%s`, `\n`),
  입력의 기초 한 가지(안전한 입력의 어려움을 예고 — 10장·17장 proven의
  씨앗). 2장 (9) 스트림을 심화 문답으로 회수.

**5장. 선언 — 이름을 만드는 법** [사용자 확정]

4장까지는 남이 만든 이름을 썼다. 이제 스스로 이름을 만든다.

- **변수 선언**: 선언 = 컴파일러에게 이름과 타입을 약속하는 문장. 변수 =
  이름 붙은 기억 장소(2장 (2) 주소의 회수 — 이름은 주소의 사람용 별명).
  타입 = 값의 집합 + 연산의 약속. 초기화 우선 관행, `const`.
  대입 = 상태 변화 — 수학의 등호와 다르다(대표 오개념: `x = x + 1`).
- **함수 선언과 정의**: 원형(프로토타입) = 함수의 계약 서명, 정의 = 몸통.
  매개변수와 반환. 선언과 정의의 구별이 왜 필요한가(컴파일러는 위에서
  아래로 읽는다 — 3장 컴파일 과정의 회수, 16장 다중 파일의 씨앗).
- **스코프 첫걸음**: 블록 안의 이름은 블록 밖에서 보이지 않는다.

구조체·공용체 같은 **타입을 만드는 선언은 여기서 다루지 않는다** —
메모리 모델을 갖춘 뒤(12장)로 미룬다 [사용자 확정].

**6장. 정수 — 유한한 수의 세계**

5장에서 선언한 정수 변수의 **값의 수학**. 비트 폭, 부호 없는 정수 =
모듈러 산술(수학 박스: mod 2^n 합동), 부호 있는 정수 = 2의 보수, 오버플로.
실제 사례: 오버플로가 일으킨 실제 사고. 4장에서 예고한 나눗셈을 여기서
정식으로 — `/ %` 와 버림·나머지의 수학(수학 박스: 몫·나머지 정리), 비트
연산. C 표기: 정수 타입들, C23 `_BitInt`·`<stdint.h>` 우선 관행. 심화
문답: 2장 (2) 워드·4장 수식 회수.

**7장. 흐름 — 결정과 반복**

조건과 반복을 2장 (1)의 계산 모델과 연결한다(기계는 단순한 단계를 반복할
뿐). 불리언(C23 `bool`), 비교와 논리 연산자(4장 수식의 확장), `if`/`switch`,
루프 3형제, 루프 불변식의 착상(수학 박스). 심화 문답: 2장 (3) 분기 예측
회수 — "if 는 공짜가 아니다". 코드 시연은 직전 장 예제의 변형으로만 진행.

**8장. 함수 — 이름 붙은 계산**

5장의 함수 선언을 의미론으로 심화한다. 함수 = 수학적 함수와 절차의
사이(부수효과라는 개념), 인자 전달 = 값 복사(대표 오개념: "변수를
넘긴다"), 스코프와 수명의 정식 취급, 재귀의 첫 만남. 계약의 착상:
전제조건·후조건 — proven식 사고의 씨앗(14장 회수).

### 제3부 — 기억 (메모리의 현실)

**9장. 메모리 모델 — 객체, 주소, 포인터**

2장 (2)의 "워드와 주소"를 C의 객체 모델로 정식화한다. 포인터 = 주소를
값으로 다루는 것 — 그러나 2장 (5)에서 심은 대로 포인터는 정수가 아니며
프로버넌스를 갖는다(심화 문답으로 회수). **널 삼형제의 구별**: 널
문자(`'\0'`, 값이 0인 문자)·널 포인터(아무 객체도 가리키지 않는 포인터
값)·`NULL` 매크로와 C23 `nullptr` — 이름이 닮아 뒤섞이는 대표 오개념.
소스의 정수 상수 0은 널 포인터 상수라는 **계약**이지만, 널 포인터의
**내부 표현**은 0이 아닐 수 있다(역사적·특수 플랫폼) — 2장 (2)의 "0번
주소의 특별함"을 심화 문답으로 회수해, 임베디드에서 0번지가 유효 메모리인
경우와 널 검사의 관계를 짚는다. 정렬과 포인터(2장 (2) 회수: 왜 `char*`는
아무 데나 가리켜도 되는가). 그 밖의 대표 오개념 다수 배치(포인터≠배열,
포인터=정수, 미초기화). 그림(이중 부호화) 집중 사용.

**10장. 연속된 기억 — 배열과 문자열**

배열, 경계, 버퍼 오버런(실제 사례: 역사적 보안 사고), 문자열 = 바이트 열 +
약속(NUL 종단). 2장 (6)의 인코딩 지식을 심화 문답으로 소환해 C의 문자열
현실(char = 바이트, UTF-8 리터럴, `u8""`)과 접속한다. 4장에서 예고한
"안전한 입력의 어려움"이 여기서 실체를 드러낸다. proven 등장: 경계
검사되는 문자열 처리가 왜 필요한가.

**11장. 수명과 저장 기간**

자동/정적/동적 저장 기간, `malloc`/`free`, 소유라는 개념, 댕글링·이중 해제
(실제 사례). proven의 안전한 할당 관행. 심화 문답: 8장 스코프·수명 회수.

**12장. 자료의 모양 — 구조체, 공용체, 표현** [사용자 확정: 후행 배치]

이제야 타입을 만든다 — 5장에서 미뤄 둔 "타입을 만드는 선언". 구조체,
패딩과 정렬(2장 (2) 회수 — 기계 현실), **공용체**(같은 기억을 다른 눈으로
읽기 — 엔디안 관찰 시연, 2장 (2) 회수; 타입 퍼닝의 주의), 표현과 추상의
분리, 리스트·테이블 같은 자료구조의 첫걸음.

### 제4부 — 정밀 (수학과 오류)

**13장. 실수 — 근사의 수학**

2장 (7)의 고정소수점·부동소수점·IEEE 754를 심화 문답으로 회수하고, C의
float/double 실무로 간다: 부동소수점 = 유한 이진 유리수의 부분집합, 반올림
모드, 누적 오차(실제 사례), 비교의 함정(대표 오개념: `0.1 + 0.2`). proven의
정확한 float 처리(파싱·포매팅)가 실제로 어려운 문제임을 사례로.

**14장. 오류와 계약**

오류는 예외가 아니라 값이다(C의 방식), 반환값 검사, proven식 계약: 입력
검증·불변식·실패의 명시적 전파. 심화 문답으로 8장의 전제조건을 소환.

**15장. 정의되지 않은 동작 — C의 어두운 계약**

UB란 무엇인가(수학 박스: 부분 함수), 왜 존재하는가 — 2장 (4)(5)의 컴파일러
최적화·추상 기계를 심화 문답으로 회수하면 답이 이미 절반 나와 있다. 엄격한
앨리어싱·프로버넌스의 정식 취급, 대표 UB 목록과 회피 관행, 새니타이저와
도구(지면 시연). 실제 사례: UB가 일으킨 실제 결함.

### 제5부 — 구성 (프로그램에서 소프트웨어로)

**16장. 여러 파일 — 분할과 링크**

3장의 컴파일 과정을 다중 파일로 확장. 헤더와 소스, 번역 단위, 내부/외부
연결, 링크 오류 읽는 법. 심화 문답으로 3장 링크 단계와 5장 선언/정의
구별을 소환 — 헤더 = 선언의 묶음이라는 착지.

**17장. 라이브러리 — 표준과 proven**

표준 라이브러리 지형, 왜 보강이 필요한가, proven 라이브러리의 설계
철학(검증된 기본기)과 실제 사용. 지금까지의 예제를 proven 위에서 재구성.

**18장. 모던 C 관행 총정리**

C23 기능 정리(이 책에서 이미 자연스럽게 써 온 것들의 회고), 현대적 C
스타일, 더 나아갈 길(도구, 커뮤니티, 표준 문서 읽는 법). 전권 회고 심화
문답으로 마무리.

## 3. RFC-0001 매핑 요약

- 모든 장: 선행조직자 + 심화 문답(2장부터) + 오개념 ≥1 + 실제 사례 ≥1 + 필요시 수학 박스 (RFC-0001 §5 템플릿).
- 씨앗-회수 구조: 2장 워드·주소·엔디안·0번지·정렬·태그 포인터→9장·12장, 2장 최적화·추상 기계·프로버넌스→9장·15장, 2장 인코딩·유니코드→10장, 2장 고정/부동소수점·IEEE 754→13장, 2장 스트림의 기원→3장·4장(printf·입력), 3장 컴파일 과정→5장(선언/정의)·16장, 4장 입력 예고→10장·17장, 8장 계약→14장. 심화 문답이 이 다리들을 소환한다. 2장이 배경지식의 저수지이므로 회수 다리의 절반 이상이 2장에서 나온다.
- proven은 10장에서 처음 등장해 17장에서 전면화된다. 그 전 장들은 표준 C만으로 설명한다(도구를 늘리지 않아 인지부하 관리).

## 4. 미결

- 3장의 예시 플랫폼 선정: 후보는 (a) Windows + WSL/MSYS2, (b) Linux 데스크톱, (c) 둘 다 짧게. 일반론 위주 원칙은 확정, 예시 하나를 무엇으로 하느냐만 남음.
- 4장 "입력의 기초 한 가지"의 구체 선택: `scanf` 최소 사용 vs 줄 읽기 우선. 안전성 서사(10장·proven)와의 접속을 기준으로 표본 집필에서 결정.
- 장 개수·분할 조정: 집필하며 장이 비대해지면 분할한다 (예: 2장, 9장 포인터).
- 부록 구성 (설치 상세, ASCII/UTF-8 표, 연산자 우선순위 등 참조 자료).

## 5. 대안 검토

- **문법 항목 순서** (전통 목차): R05로 배제. 개념 의존 순서가 입문자의 인지부하에 유리하다.
- **프로젝트 관통형** (하나의 프로그램을 책 전체에서 키워 가는 구성): 실습을 시키지 않는 이 책과 충돌하고, 장 간 결합이 강해 읽다 끊기면 복구가 어렵다. 대신 "직전 예제의 변형" 원칙으로 연속성만 취한다.
- **proven 처음부터**: 앞 장부터 proven을 쓰면 "C를 배우는가, 라이브러리를 배우는가"가 흐려진다. 표준 C 먼저, proven은 필요가 증명된 시점(10장)에 도입.
- **선언 먼저, 사용 나중** (전통: 자료형·변수 선언부터): rev.b에서 배제. 선언을 먼저 배우면 "무엇을 위해 이름을 만드는가"가 공중에 뜬다. 4장에서 사용의 필요를 겪은 뒤 5장에서 선언을 배우면 동기가 선다.

## 6. 자연스러움 검토 (rev.b 자체 점검)

의존 순서 전수 점검 — 각 장이 앞 장까지의 개념만 쓰는가:

- 3장 헬로 월드가 `printf`를 설명 없이 쓴다 → 의도된 선행 노출이다. 3장의 목적은 컴파일 과정이고, `printf` 자체는 "주문"으로 두었다가 4장이 해부한다. 4장 선행조직자가 이를 명시해야 한다.
- 4장 수식이 변수 없이 성립하는가 → 성립한다. 리터럴과 함수 호출만으로 수식을 정의하고, 변수는 5장에서 "수식에 넣을 수 있는 이름"으로 합류한다. 오히려 "수식=값이 되는 것"이 변수 없이 더 깨끗하게 선다.
- 4장 입출력이 변수 없이 성립하는가 → 출력은 성립(`printf("%d", 40 + 2)`). **입력은 저장할 곳이 필요하므로 4장에서는 예고만 하고, 실제 입력 시연은 5장(변수 선언 직후)에서 완결한다.** 이것이 5장의 동기 부여 장치도 겸한다(입력을 받으려면 이름 붙은 기억 장소가 필요하다).
- 5장 선언이 4장까지로 성립하는가 → 성립. 타입 이름(`int` 등)은 5장에서 처음 정식 등장하되, 3~4장 예제에 이미 보였으므로 낯설지 않다.
- 6장 정수가 5장 없이 성립하는가 → 불가(변수에 담긴 값의 이야기) — 순서 정당.
- 7장 흐름이 6장 정수 뒤인 이유 → 루프 카운터·비교가 정수 의미론(오버플로 포함)을 전제. 정당.
- 8장 함수 심화가 7장 뒤인 이유 → 함수 몸통 예제에 조건·반복이 필요. 정당. 5장(함수 선언)과 8장(함수 의미론)의 분리는 "사용→선언→의미론"의 3단 접근으로, 한 장에 몰기보다 인지부하가 낮다.
- 9~12장(포인터→배열·문자열→수명→구조체·공용체) → 구조체가 포인터·수명 뒤에 오므로, 구조체 포인터·동적 자료구조를 12장에서 바로 다룰 수 있다. 공용체의 엔디안 시연은 2장 (2)의 회수로 자연스럽다. [사용자 확정: 구조체·공용체 후행]
- 13~15장(실수→오류·계약→UB) → 실수 비교의 함정(13)이 오류 서사(14)의 도입 사례가 되고, 14의 계약이 15의 "어두운 계약"과 대구를 이룬다. 정당.
