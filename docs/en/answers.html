Answers to the exercises

The answers to the exercises gathered at the end of each part. An answer does not stop at one line: it says why the mistake is easy to make, what is right, and whether the ground is a chapter, a clause of the standard, or an observation on one machine.

Part I#

Answer 1-1. (to the exercise) What is inside the machine are physical states such as high or low voltages and charged or empty cells. 0 and 1 are names people give those states so as to read them — an interpretation (chapter 2). The distinction matters because “what is stored” and “how to read it” come apart. The same 32 bits read as an integer are one number, read as a floating-point value a quite different number, and read as four characters something else again (chapter 7, chapter 8). Bits carry no meaning written on them — the meaning is given by the type that reads them.
Answer 1-2. (to the exercise) Not backwards; the agreed order of storing differs. The machine is little-endian — it puts the lowest-order byte (78) at the lowest address. Looking at memory slot by slot, the number appears in the reverse of the order you would write on paper. A memory dump is not a number written on paper (chapter 3). When sending to another machine, fix the byte order in the format and write and read one byte at a time in that order — a big-endian machine reads the same bytes as 0x78563412 (chapter 50).
Answer 1-3. (to the exercise) With 𝑛-bit addresses there are at most 2𝑛 slots. With 32 bits, 232, about 4.3 billion slots — one byte each, so 4 GiB. The “4 GB limit” is a limit set by how many numbers an address can write (chapter 3). On a 64-bit machine, storage is still in bytes — a one-byte character takes one byte, and 64 bits is only the width of addresses and registers. Large values are constrained in where they may sit by alignment, though (chapter 4).
Answer 1-4. (to the exercise) On the notation layer it is right — writing the constant 0 where a pointer is expected in the source (p = 0;) gives that implementation’s null pointer value. On the representation layer there is no guarantee — nothing promises that the bits stored afterwards are all 0, and machines whose null pointer’s internal representation was not 0 really existed (chapter 4). So code that assumes “the bits are 0, so it is null” (pointers filled with 0 by memset, an array of pointers from calloc) stands on a coincidence. This split is treated formally in chapter 37.
Answer 1-5. (to the exercise) An address that is a multiple of 4 always ends in the two bits 00 in binary (three bits for a multiple of 8). A tagged pointer takes for granted that those bits are always 0 because of alignment, puts a small piece of information (such as a kind tag) there, and clears it before use. If a misaligned pointer gets mixed in, or the clearing is forgotten before a dereference, it follows the wrong address — so this is not a technique the standard guarantees but one that leans on that machine’s alignment (chapter 4 formally, chapter 38).
Answer 1-6. (to the exercise) The global given 7 is in the initialised static region (the 7 is in the executable). The global array with no initial value is in bss — the static region that starts at zero. The local variable is on the stack (the function’s workbench). The string literal is in a read-only region. The malloc block is on the heap. bss writes only one number in the executable — “fill this much with zeros” — and the filling is done when the program starts, so a table of a million slots does not enlarge the file (chapter 5). This picture is a common layout, not a promise of the standard — what the standard speaks of is not regions but storage durations (chapter 45).
Answer 1-7. (to the exercise) It is right only for the static region — global and static variables without an initialiser start at 0 (null for pointers). That 0 is not free; someone fills it in when the program starts (the start-up code that zeroes bss). Local variables on the stack are different — uninitialised, their values are not fixed, and code that reads them is a regular source of bugs that “work in debug and fail in release” (3-7). The same goes for a block from malloc on the heap (calloc fills the bits with 0) (chapter 5).
Answer 1-8. (to the exercise) Half right. What decides the speed is not the amount but which region is used and how. Values used briefly and cleared away on the workbench (the stack) are nearly free however many there are, while allocating from the warehouse (the heap) and freeing again and again is noticeably slow even in small amounts. And the same amount scattered or gathered makes a difference of several times because of caches (chapter 5, chapter 12). A feel for memory grows not from “how much” but from “where, and in what order”.

Part II#

Answer 2-1. (to the exercise) The unsigned one becomes 0 — coming back round within the type’s range is what the standard promises (the remainder modulo the maximum plus one). The signed one is outside the contract — at -O0 on a common machine it may be seen to “wrap” to −128, but that is only an observation, and the compiler may optimise on the assumption that such an overflow never happens. “Integers wrap” lumps the two together and leads you to expect signed overflow to wrap too — what wraps is the unsigned integer; signed overflow must not be expected to (chapter 6). Note also that adding 8-bit values is really done after promotion to int (chapter 30).
Answer 2-2. (to the exercise) At the moment of overflow, the CPU’s adder by default only raises an internal signal (a flag); it does not stop the program or report anything. C is the same — unsigned numbers wrap silently, and signed numbers go outside the contract. Neither raises an “error”. So watching for overflow is the programmer’s job — checked arithmetic such as C23’s ckd_add helps with it (chapter 6 chapter 96).
Answer 2-3. (to the exercise) It did not calculate wrongly. 0.1 is a recurring fraction in binary, so the “0.1” inside the machine is a different number very close to 0.1. Floating point can hold only finitely many numbers, and one it cannot hold is rounded to its nearest neighbour. That small difference accumulates over ten additions until the last bit differs from 1.0 — floating point is not an exact number but a faithful approximation (chapter 7). Values that must be exact, like money, are handled as integers of the smallest unit (won, cents). If real numbers really must be compared, set a tolerance that fits the problem (chapter 54).
Answer 2-4. (to the exercise) The digit check. The standard guarantees only one thing: the values of the decimal digits '0' to '9' are contiguous (§5.2.1). There is no such sentence for the alphabet. In the EBCDIC table, which grew out of the punched-card era, letters were not numbered contiguously, so values that are not letters fall between 'a' and 'z'. So leave the letter check to isalpha from <ctype.h> (passing the value as unsigned char) (chapter 8, chapter 82).
Answer 2-5. (to the exercise) For text using only ASCII letters, one character is one byte. In UTF-8 a character is 1 to 4 bytes — 「안」 and 「녕」 are 3 bytes each, so 「안녕」 is 6 bytes (one more for the NUL end marker when held as a string). In CP949, the old Korean Windows default, a Korean character was 2 bytes — the same character takes a different number of bytes depending on which table it was written in. And how many columns it takes on screen is another question again (chapter 8 chapter 43).
Answer 2-6. (to the exercise) The characters were in the output stream’s buffer. Output gathers in the buffer and goes out in a chunk, so the moment of writing and the moment the characters reach the device differ. Without a newline they may stay in the buffer even where output goes out line by line. The operation that says “send it out” is flushing — fflush(stdout) (chapter 9). Many implementations flush output before reading input, but if the prompt must show, flush it yourself. Flushing is an output operation — using it on input is outside the contract (5-10).
Answer 2-7. (to the exercise) Two different processes from the same program (the executable on disk). A process is one instance of a running program, each with its own memory, state and lifetime (chapter 10). And fork is not C standard — it is a POSIX function. The C standard says remarkably little about processes: a program starts, main runs, and it ends leaving an exit status. There is no standard way to create a process or run another program; system alone is specified, only as “execute a command string”.
Answer 2-8. (to the exercise) Wrong. The two do different jobs. An interrupt is a doorbell — it announces “something has come, look now”. Asking is opening the door to see who it is — what has come is known only by reading the device’s state. Without a doorbell you have to keep opening the door (polling); with only a doorbell and no opening the door, you never learn who came. So real code uses both: the interrupt says when to look, and asking says what has come (chapter 11).
Answer 2-9. (to the exercise) The picture “the same cost wherever it reads” is wrong. In fact touching the neighbourhood just touched again and touching a far place for the first time differ in cost by tens to hundreds of times — because a cache sits in between. A C 2-D array lays rows out contiguously, so sweeping in row order uses each line brought into the cache to the end, while sweeping in column order jumps far away for every element and brings in a new line (chapter 12 the row stride is chapter 40).
Answer 2-10. (to the exercise) Reserving and using are different. An allocation is usually a reservation of virtual address space, and physical memory is attached only to the parts (pages) first touched. So a successful 1 GiB allocation leaves RAM usage almost unchanged, and it rises when the whole area is swept. That is why VIRT (numbers reserved) and RES (actually attached) differ so much in Linux’s top (chapter 12). So in some environments “the allocation succeeded” does not mean “all that memory can be used”.
Answer 2-11. (to the exercise) Branch prediction. The CPU guesses the answer at a fork in advance and loads the following instructions into the pipeline — free if right, and if wrong it pays the penalty of emptying what it loaded. In a shuffled array, “above/below” is random every time, so about half the guesses are wrong. In a sorted array the answer stays on the same side for long stretches and nearly every guess is right. The order of the data decided the speed of the same code — an if is not free (chapter 13). Such numbers are observations measured on that machine, and the difference can vanish if the compiler turns the branch into a branch-free instruction.
Answer 2-12. (to the exercise) It did not. What the compiler must keep is the observable result, and writing zeros to a buffer never read again is a dead store that contributes nothing to it — it may be deleted (chapter 14, “The vanished eraser”). Several compilers really did delete this wipe quietly, and software shipped with passwords left in memory became the subject of security advisories. Prevent it with a device that explicitly says “do not delete this write” — C23’s memset_explicit, Annex K’s memset_s, or a platform’s explicit_bzero.
Answer 2-13. (to the exercise) In the compiler’s eyes, no code inside the loop changes that slot. So it reads the value once into a register and from then on looks only at the register — however the device changes memory, the program goes round forever looking at the old value. The abstract machine does not know “something outside this program can change memory”, so the programmer has to say so. For a device register, add volatile — “perform this access for real every time”. For a value changed by another core, use not volatile but a C11 atomic type — volatile promises nothing about ordering or visibility between threads (chapter 14 chapter 95).
Answer 2-14. (to the exercise) The right half is history and distance — early C was close to a simple machine, and C is still the language that takes you closest to the hardware. The wrong half is “directly” — between today’s C code and the hardware stand an editor (the compiler) and a contract (the standard), and shortcuts written with a naive sense of “direct manipulation” break before the compiler’s discretion (the vanished eraser, the polling loop that froze). The accurate sentence: C is not a language that manipulates hardware directly, but one that lets you meet the hardware through the contract of an abstract machine (chapter 15).

Part III#

Answer 3-1. (to the exercise) The newline \n is missing. printf sends out exactly the characters it is given — it does not end the line for you. When the program finishes, the shell prints its next prompt where the cursor was, so the prompt sticks to the end of an output line that was never finished. Write "hello, world\n". How the line became the unit of output is in chapter 9 reading the first program line by line is chapter 16’s “Reading it line by line”.
Answer 3-2. (to the exercise) The shell looks for executables only in the directories listed in PATH, and Unix-like systems by long custom leave the current directory out of PATH for safety — put it in, and a program named ls planted in some directory would run when you typed ls there. So you write “this one, here” as ./hello. cmd.exe looks in the current directory first, so hello alone works; PowerShell, for the same reason as Unix, wants .\hello.exe (chapter 16, “Running the executable you made”).
Answer 3-3. (to the exercise) It does not build. Since C99, calling a function with no declaration — the “implicit declaration” — is no longer part of the language, and such a call is a violation that requires a diagnostic. On this machine both gcc 14.2 and clang 19.1 report implicit declaration of function 'printf' as an error (older compilers only warned and built it anyway — which is why there is old code that “warned but ran”). The runner that stopped is the second one, compilation. The declaration that says what printf is lives in the header <stdio.h>, and pasting it into the source is the first runner’s job, preprocessing (chapter 17).
Answer 3-4. (to the exercise) Compilation is satisfied by a declaration (an advance notice). int helper(void); promised “such a function exists somewhere”, so the compiler translates the call and leaves the address blank. Filling that blank with the real thing is the job of the fourth runner, the linker, and since no object file has a body for helper, the linker stops. A different worker raising the error means a different kind of message — first sort out which of the four runners fell (chapter 17 the formal treatment is chapter 60).
Answer 3-5. (to the exercise) -E prints the preprocessed text (C source with the headers pasted in and the macros expanded) — through the first runner. -S produces the assembly source hello.s — through the second. -c produces the object file hello.o — through the third; it is not linked yet, so the place for printf is still blank. With none of these options the build runs through the fourth runner and an executable comes out (chapter 17).
Answer 3-6. (to the exercise) -g only adds debug information (variable names, types, line numbers); it does not change the machine instructions generated — the executable gets bigger but runs at the same speed. What slows a program down is the -O0 (optimisation off) that usually comes with it. They are separate switches, so -O2 -g works. In practice the shipped build is also built with -g, and the debug information is split into a separate file and kept. The shipped executable stays light, and a crash report from the field can still be decoded with that information (chapter 18).
Answer 3-7. (to the exercise) s is never initialised. The value of an uninitialised automatic variable is not determined (the formal treatment is in chapter 56); at -O0 that stack slot happened to hold 0, and that is all. When optimisation changes the layout, the accident is gone — the commonest root of “it works in debug and fails only in release” (chapter 18). Fix it with int s = 0;. On this machine, with -Wall -Wextra, clang 19.1 warned at every optimisation level, while gcc 14.2 said nothing at -O0 and gave may be used uninitialized only at -O2 — no warning does not mean no problem.

Answer 3-8. (to the exercise) With -DNDEBUG every assert disappears entirely. The bad age that the debug build caught now flows straight into the release build. assert is a device for catching the programmer’s mistakes (things that must never happen), not for checking outside input. A user’s input can always be wrong, so check it with an ordinary if and report failure to the caller as a value (chapter 18 contracts are treated formally in chapter 55).

bool checked_age(int v, int *out)
{
    if (v < 0 || v >= 200)
        return false;           /* failure --- *out is left as it was */
    *out = v;
    return true;
}
Answer 3-9. (to the exercise) The source was not changed, so link ① (the bytes of the source file) is the same. What remains are ② (what encoding the compiler read the source as), ③ (the bytes planted in the executable) and ④ (what table the terminal reads those bytes with). Try two things. Redirect the output to a file and look at its bytes in hex — if the bytes are the same on both machines, the culprit is ④, the terminal. If they differ, it is ② or ③, that is, the two machines’ compiler settings differ (chapter 18, “When Korean text breaks — the chain of encodings”). All four links produce the same symptom, “the characters break”, so narrowing down which link comes first.
Answer 3-10. (to the exercise) One is “does that compiler still exist?”. The classic icc that the saying is about was removed by Intel in oneAPI 2024.0; what you get now is the LLVM-based icx. The other is “what was it measured with?”. The period when automatic vectorisation showed a large gap is over, and the few per cent gained by changing compilers is usually far smaller than the several-fold gained by laying data out to suit the memory ladder (chapter 19, chapter 12). If a switch is proposed, ask first to see numbers for the two builds measured on the same code, the same input and the same machine.

Part IV#

Answer 4-1. (to the exercise) It prints 9. An integer constant that starts with 0 is octal, so 010 is 8. The habit of padding with a leading zero is what walks into this trap. 08 does not build, because the digit 8 does not exist in octal (chapter 21, “Integer constants”). Unless octal is really wanted, as for file permissions (0755), do not put a 0 in front.
Answer 4-2. (to the exercise) As C you get the size of int (4 on a common 64-bit machine); as C++ you get 1. In C the type of an integer character constant is int (§6.4.4.5); in C++ it is char. The value is the same — “the character stored in a char and converted to int”, exactly what you expect; only the type is wider. Writing only C you will hardly ever be hurt, but in a header that both languages read, a sizeof or _Generic that branches on it shows the difference (chapter 21).
Answer 4-3. (to the exercise) In C, const int is only a promise — “I will not change it through this name” — and not a constant expression (a place where C and C++ part ways). An array size at file scope has to be a constant expression, so gcc stops with variably modified 'table' at file scope. Inside a block it would get through, but as a variable-length array, not a constant one. C23 writes the fact that the value is fixed at translation time with constexpr — constexpr int n = 10;. Older code has filled the same place with enum { n = 10 }; or #define (chapter 21, “How it differs from const”).
Answer 4-4. (to the exercise) It does not build (an error in both gcc 14 and clang 22). The initialiser of a constexpr must be exactly representable in the target type — the -1 that an ordinary initialisation would have converted quietly is a constraint violation here (C23 6.7.2; the standard uses exactly this pair as its example). Say what you mean with constexpr unsigned int m = -1U;, or use UINT_MAX from <limits.h> (chapter 21, “The value has to fit exactly”).
Answer 4-5. (to the exercise) In many fonts the lower-case suffix l looks almost the same as the digit 1, so 10l reads as 101. A suffix changes the type, not the value, so misreading it changes the meaning a good deal. Write it in capitals, as custom has it — 10L (chapter 21).
Answer 4-6. (to the exercise) The smallest int, INT_MIN. In two’s complement the smallest negative number has no positive partner (chapter 6), so there is no int to hold its absolute value. The standard says that when the result cannot be represented, the behaviour of abs is undefined — not even “a negative number comes out” is promised (chapter 22). If that input can arrive, handle x == INT_MIN separately before the call, or compute the result in a wider type (llabs and long long).
Answer 4-7. (to the exercise) Put a semicolon after an expression and it becomes an expression statement — “evaluate it and throw the value away”; discarding is something the grammar allows. printf returns the number of characters it sent out, and a negative value if an output or encoding error occurred (§7.23.6.3). Usually the side effect of printing is the point and the count can go, but in a program whose output is the product itself (a converter writing to a file) discarding it means missing that failure (chapter 22 the three failures of writing a file are in chapter 78).
Answer 4-8. (to the exercise) The width counts bytes, not characters. One Korean character is 3 bytes in UTF-8, so the eight places of %-8s hold barely more than two of them (chapter 23, chapter 8). On top of that a Korean character takes two columns in a terminal, so lining them up means counting characters and screen width yourself and adding the padding (chapter 87).
Answer 4-9. (to the exercise) The error sentence went to standard output. Redirection sends only standard output to the file, so the error sentence is mixed into the results file and nothing is left on the screen. What you say to a person goes to standard error — fprintf(stderr, "cannot open %s\n", path);. And report the failure in the exit status too (chapter 23, chapter 59).
Answer 4-10. (to the exercise) The first line gives a double to a %d — make them agree with printf("%f\n", 3.5) or (int)3.5. The second has two placeholders and one argument. All three are outside the contract, that is, undefined behaviour, and the format checking in -Wall usually catches the first two (gcc 14.2 on this machine flagged the first line under -Wformat). The third puts text a user sent in the format string’s place. If that text arrives with % in it, printf goes rummaging through memory for arguments that do not exist — the road of an attack that earned its own name, the “format string vulnerability”. Keep the input as an argument: printf("%s", user_text) or fputs(user_text, stdout) (chapter 23).

Part V#

Answer 5-1. (to the exercise) C’s = is not a statement that two things are equal but an order: “compute the right-hand side and put it into the slot on the left”. So x = x + 1; means “add 1 to the value x has now and put it back in x” — a side effect that changes state (chapter 24, “Assignment”). An equation in mathematics must hold regardless of time, but an assignment has an order: read the right first, then write the left. The operator that asks whether two things are equal is a different one (==, chapter 31). The mathematical intuition is not wrong; the symbol means something else.
Answer 5-2. (to the exercise) Assigning to a name marked const is a constraint violation, so the compiler stops with an error. const is less a lock than a document: it tells the compiler and the next reader “this value does not change”, and catches code that breaks the promise at translation time. Hence the habit of “declare it const first and take it off only where something has to change” (chapter 24). const does not mean “the value is fixed at translation time”, though — that difference is 4-3 and chapter 21.
Answer 5-3. (to the exercise) It is a correct observation on common desktop and server machines, not something the standard promises. The standard sets only a minimum range for int: at least 16 bits (in C23, at least −32,768 to 32,767). The actual width is the implementation’s choice, and INT_MAX from <limits.h> and sizeof(int) give that machine’s answer. Small microcontrollers with a 16-bit int are still around. Where the width is part of the contract (file formats, communication), use a type that puts the width in its name, such as int32_t from <stdint.h> (chapter 28).
Answer 5-4. (to the exercise) The compiler reads a file from top to bottom. When it meets square(12) inside main, there is no declaration of square yet, so in C23 it is an error as a call with no declaration, an implicit declaration (the same reason as 3-3). There are two fixes: move the definition of square above main, or write the prototype int square(int n); near the top. Gather prototypes into a header and the definition can even live in another file — that is what a header file is for (chapter 25, “Declaration — only the signature, in advance”).
Answer 5-5. (to the exercise) inline is a request, not an order. The standard words it as advice to the effect of “make calls as fast as possible” and states that an implementation ignoring it still conforms. Today’s compilers expand functions without inline when it pays and leave functions with it alone when it does not. The real worth of inline is permission: “this definition may appear in several translation units” — with that permission a function body can live in a header (chapter 25, “inline is a request, not an order”).
Answer 5-6. (to the exercise) In C’s inline model, an inline definition with neither static nor extern is only an inline definition; it does not produce an external definition (the real body the linker connects). With optimisation on, the compiler expands the call and no real body is needed, but at -O0 it does not expand it and goes to call the real body, which the linker cannot find (on this machine gcc 14.2 and clang 19.1 both stop at -O0, and gcc built it at -O2 — that the optimisation level decides the outcome is itself a warning sign). Fix it with one of the two forms used in practice: write static inline int twice(int x) in the header, so each translation unit has its own copy, or keep the header and put extern inline int twice(int x); in one .c file to make one real body (chapter 25, “So in practice an inline function takes only two forms”).
Answer 5-7. (to the exercise) 2, then 1. The inner block’s x hides the outer x — inside that block, x means the inner one. The outer x was neither removed nor changed; it was only out of sight for a while, and once the block closes the name shows it again. Scope is a property of the name; how long an object lasts (lifetime) is a different question (chapter 25, “Scope”; the full picture is chapter 62).
Answer 5-8. (to the exercise) fgets keeps the newline. If the user types yes and presses Enter, the buffer holds "yes\n", which is not equal to "yes". Remove the newline before comparing — the one line line[strcspn(line, "\n")] = '\0'; removes it if it is there and does nothing if it is not. Whether a line longer than the buffer came in is told by whether it ends in a newline — if the buffer filled with no newline, the line was cut and the rest is still waiting in the input (chapter 26, “The contract of fgets”). The discipline of not passing off cut input as success is set up formally in chapter 44.
Answer 5-9. (to the exercise) %d takes only the characters that fit the shape of a decimal integer and leaves the first character after the input item unread (§7.23.6.2). If the user typed 42 and Enter, only 42 is taken and the newline stays in the input buffer. The fgets that follows sees that newline as the end of a line and at once returns an empty line — it looks as if input was skipped, but what happened is that this read ate what the last one left behind (chapter 26, “What stays in the input buffer”).
Answer 5-10. (to the exercise) The “flush” of fflush is an operation defined for output streams, so fflush(stdin) is outside the contract. On some implementations it does something plausible and on others nothing at all. Clear leftover characters by reading and discarding them — a short loop that reads one character at a time until a newline. Better still is two-stage reading, which never makes such a place: fetch the whole line with fgets, then interpret it with sscanf inside your own buffer, and if the interpretation misses, it is your own buffer that gets overwritten, not the stream buffer (chapter 26).

Part VI#

Answer 6-1. (to the exercise) Whether char is signed is the platform’s choice. On x86 Linux it is signed, so storing 0xFF (255) gives −1, while the 0xFF on the right of the comparison is the int 255, and the two are not equal (gcc 14.2 on this machine warned under -Wextra that the comparison is always false). Where char is unsigned, as on ARM Linux and many embedded toolchains, it comes out true — which makes it more dangerous. Follow the rule: hold bytes in unsigned char (chapter 27).
Answer 6-2. (to the exercise) The intermediate result lo + hi can exceed INT_MAX. The result (the middle position) is plainly in range, but the sum overflows on the way, and signed overflow is outside the contract. It is a famous bug that went unnoticed for close to twenty years after Programming Pearls and sat in the Java standard library for about nine (chapter 28). Compute lo + (hi - lo) / 2 and no intermediate value overflows. Worry about the container for every intermediate step of an expression, not just the result.
Answer 6-3. (to the exercise) -3 -1. C’s division truncates toward zero (the standard has said so since C99). And the remainder is fixed so that (a / b) * b + a % b == a always holds, so with a quotient of −3 the remainder is −1. That is a different choice from the “non-negative remainder” common in mathematics (−7 = 2 × (−4) + 1). Code that picks an array slot with the remainder of a negative number (a[k % n]) makes a negative index right here — if negatives can arrive, correct it with something like ((k % n) + n) % n (chapter 29).
Answer 6-4. (to the exercise) 1 is an int, and shifting a positive signed value so that the result does not fit in an int is outside the contract. With a 32-bit int, 1 << 31 is exactly that. Shift an unsigned value: 1u << 31. C23 did make two’s complement representation mandatory, but the shift clauses did not change — shifting a negative number left is still outside the contract in C23, and shifting a negative number right is still implementation-defined. The rule stays the same across editions: shift unsigned values, by a count with 0 <= n < width (chapter 29).
Answer 6-5. (to the exercise) The first fragment prints nothing. Mixing int and unsigned int makes both unsigned int under the usual arithmetic conversions, and −1 becomes the largest unsigned value (gcc on this machine flagged it with -Wsign-compare). The second never ends. An unsigned i is always at least 0, so i >= 0 is always true, and subtracting one from 0 wraps round to the largest value. Write a counting-down loop by decrementing in the condition, as in for (unsigned i = n; i-- > 0; ), or use a signed type (chapter 30).
Answer 6-6. (to the exercise) 3, 44 and 4294967295. A cast between arithmetic types does not mean “read these bits as that type”; it means “convert this value to a value of that type”. (int)3.9 drops the fraction, giving 3; (unsigned char)300 is the remainder modulo 256, 44; (unsigned)-1 is 2³² − 1 — all three values changed. To keep the bits and only change how they are read, the routes are a union or memcpy (chapter 30, chapter 49).
Answer 6-7. (to the exercise) 300 44. Integers smaller than int are promoted to int before they take part in arithmetic, so a + b comes to 300 in int’s world — the calculation does not happen in the range of unsigned char. What looks like overflow happens when that 300 is stored back in an unsigned char, and since that side is unsigned it becomes the remainder modulo 256, 44 (chapter 30). Small types are units of storage, not units of calculation.
Answer 6-8. It is grammatical, so the compiler does not stop it. With -Wall, gcc warns “suggest parentheses around assignment used as truth value”. What was meant is x == 3.
Answer 6-9. (to the exercise) The second line. && evaluates left to right, and if the left side is false it does not evaluate the right side at all (short-circuit evaluation). (to the exercise) The condition is evaluated again on every pass. strlen(s) counts the string from start to end each time it is called, so for every character looked at the whole string is counted again — for a string of length n, roughly n² characters are read (chapter 33). Answer 6-12. (to the exercise) Argument passing in C is always a copy of the value. reset(count) only copies count’s value, 5, to be x’s first value; changing x to 0 has nothing to do with count (chapter 34). The everyday phrase “pass a variable” hides this picture. To change it there are two ways: return the new value and have the caller assign it (count = reset_value();), or pass the variable’s address as a value and have the function follow that address to write (void reset(int *x) { *x = 0; }, reset(&count); — chapter 36).
Answer 6-13. (to the exercise) i = i++;. In C, if a side effect on a scalar object is unsequenced relative to another side effect on the same object, the behaviour is undefined (§6.5.1p2). Both lines touch i twice with no order between the two. C++17 adopted the rule “in an assignment the right operand is sequenced before the left”, which defines i = i++;, but C23 still says the evaluations of the operands of an assignment are “unsequenced” (§6.5.17.1p3). It is a rare place where the same syntax is judged differently in the two languages (chapter 35). In either language, the answer is not to change the same variable twice in one statement.
Answer 6-14. (to the exercise) The invariant is “before each pass, s is 0 + 1 + … + (i − 1)”. At the start (i = 0) it is the empty sum 0, so it holds, and it stays true when the body adds i and i goes up by one. When the loop ends i is n, so s is 0 + … + (n − 1) — not 1 to n; n is missing. With for (int i = 1; i <= n; i++) the invariant becomes “1 + … + (i − 1)”, and at the end i is n + 1, giving the sum wanted. Writing down one sentence that is true before and after the loop is the cheapest way to catch an off-by-one mistake (chapter 33).

Answer 7-1. (to the exercise) int a[] in a parameter’s place is a pointer, not an array — passing an array copies only the value it decays to, the address of its first element. So sizeof a inside the function is the size of a pointer, 8, and 8 / 4 gives two passes (gcc flags it with -Wsizeof-array-argument). The function has no way of knowing the array’s length, so, as is the custom in C, take the length separately — void print_all(const int a[], size_t n), and at the call print_all(a, sizeof a / sizeof a[0]) (chapter 39, the misconception “an array is a pointer”).
Answer 7-2. (to the exercise) int grid[3][4] decays to int (*)[4] — “a pointer to a row of four ints” — not int **. The two have different memory layouts. int (*)[4] computes every cell of twelve ints in a row from one address; int ** points at “a row of pointers” and follows an address twice. Force it through with a cast and it follows a few integers mistaken for addresses, a collapse that produces no diagnostic. Write the inner dimension, as in void show(int rows, int g[][4]), or use a C99 variable-length array parameter, void show(int rows, int cols, int g[rows][cols]) (chapter 40).
Answer 7-3. (to the exercise) use.c believes “the place called msg holds an address” and reads the 8 bytes there as one. What is actually there is the characters 'A' to 'H', read in little-endian order as address 0x4847464544434241, and following it kills the program (a segmentation fault in the run this book made). The compiler sees one file at a time and the linker only connects names, so nobody warns — what is wrong is the declaration a person wrote by hand. Put the declaration in a header once (extern char msg[16];) and have the defining file include that header too; then the definition and the declaration meet in one translation unit and the compiler catches the mismatch (chapter 41).
Answer 7-4. (to the exercise) buf is a local array with automatic storage duration, so its lifetime ends when the function does. The address returned is a dangling pointer. The bits there are not wiped at once, so it prints correctly for a while, until another function uses that place for its frame and the value changes (chapter 45). There are three ways to send a result out to live longer. Have the caller supply the buffer and the function fill it (void greeting(char *out, size_t cap, const char *name)) — the commonest and safest. Allocate it dynamically, return it, and hand the duty to free it to the caller (chapter 46). Give it static lifetime with static char buf[32]; — but then every call overwrites the same buffer, and calling it from several threads is unsafe. ASan is the standard tool that catches this accident at run time (chapter 18).
Answer 7-5. (to the exercise) "hello" is read-only data baked into the program, and trying to change it is outside the contract. In a modern environment the literal sits in a write-protected area, so it usually crashes on the spot. Declare a pointer to a literal as const char *s = "hello"; — then the compiler rejects s[0] = 'H'; with an error (chapter 43, “String literals — read-only ground”). char s[] = "hello"; initialises an array with the literal — the literal’s characters are copied into your own array, which you may change as you like.
Answer 7-6. (to the exercise) sizeof greet is 7 and strlen(greet) is 6. 「안」 and 「녕」 are 3 bytes each in UTF-8, giving 6 bytes of data, and the array holds one more byte, the NUL end marker. strlen counts the bytes before the NUL; sizeof measures the whole size the array takes. On screen it is two characters — bytes, string length and characters on screen are different questions (chapter 43 how to count characters is chapter 87).
Answer 7-7. (to the exercise) break ends only the innermost level that encloses it. Leaving the inner loop, the outer loop carries on to the next row — in this book’s demo, the search went through 18 of 20 cells after finding the value. C has no labelled break. There are three ways. Move the search into a function and return the moment it is found (the cleanest). goto a label after the outer loop — leaving several levels is one of the few places goto is justified. Keep a “found” flag and test it in the outer condition too (chapter 42).
Answer 7-8. (to the exercise) atoi has no way to report failure. 8080x returns the leading 8080 and silently drops the x. abc returns 0, which cannot be told apart from a real 0. A number that does not fit in an int, such as 99999999999, is undefined behaviour. Switch to strtol and look at three things together: the return value, endptr where parsing stopped (did it read nothing, are characters left over), and errno for ERANGE (was the range exceeded). Whether leftover characters count as failure is the tool’s contract to decide — for a port number they do. And check the range 1–65535 too (chapter 44).
Answer 7-9. (to the exercise) The %s has no width. scanf writes until whitespace without knowing the buffer’s size, so a name of 8 characters or more is written past the end of name — a buffer overflow. A return value of 1 only means “one conversion succeeded”, not that the bounds were kept. Give a width one less than the buffer, as in scanf("%7s", name), or better, read the line with fgets and interpret it inside your own buffer (chapter 44, the misconception “checking scanf’s return value is enough”).
Answer 7-10. (to the exercise) The multiplication n * sizeof *p can overflow. size_t is unsigned, so it wraps when it overflows, and when the wrapped result is a small number, malloc succeeds. The moment n items are written into that small block the heap breaks — a hole that has turned into real vulnerabilities more than once (chapter 46). Ask about overflow before multiplying. In C23, take the failure with if (ckd_mul(&bytes, n, sizeof *p)) (chapter 96); before that, filter it with if (n > SIZE_MAX / sizeof *p). calloc(n, sizeof *p) checks this multiplication for overflow itself and returns null.
Answer 7-11. (to the exercise) What calloc promises is one thing: every bit of the memory it allocated is 0. It does not promise that those bits mean a null pointer, nor that they mean the floating-point 0.0. On today’s mainstream machines the three happen to coincide, so nothing goes wrong, and code that says “they are all null, so just test them” stands on that coincidence (chapter 46, chapter 37). Where portability matters, fill the slots with nullptr in a loop after allocating.
Answer 7-12. (to the exercise) It uses memory after freeing it. q is an alias holding the same address as p, so p = NULL; does not change q. Reading the freed place through q is outside the contract. p = NULL; does prevent a double free through the same name (free(NULL) does nothing), but other aliases are left as they were (chapter 46, “three classic accidents”). The real cure is to decide who owns that memory: the owner frees it, and the code’s structure keeps the promise that no other alias uses the address after that (chapter 58).
Answer 7-13. (to the exercise) Not necessarily a leak. free usually does not give memory back to the operating system; it writes in the allocator’s books “this piece can be used again”. The allocator keeps it for the next request, so unchanged usage is normal (large blocks are sometimes returned). A long-running server holding on to memory without a leak is fragmentation, the pieces scattered so they cannot form large blocks (chapter 46 head-on in chapter 99). Whether there is a leak is judged not from a usage graph but with a leak checker (ASan’s LeakSanitizer, Valgrind).
Answer 7-14. (to the exercise) '\0' is the null character — a char whose value is 0, the end marker of a string. 0 is the integer zero. nullptr (C23) and NULL are the null pointer — a pointer value that points at no object. That all three look like “0” in the source is a matter of notation; what they mean differs, so use the one that fits the place and shows the intent (chapter 37). And “a null pointer’s bits are all zero” is not a promise of the standard. The standard says only that the constant 0 written where a pointer is expected becomes that implementation’s null pointer value; it does not fix the value’s bit representation — machines with non-zero null pointers really existed (chapter 4). So a pointer member of a structure filled with zeros by memset is not promised to be null either.

Answer 8-1. (to the exercise) Padding. Each member sits at an offset that is a multiple of its own alignment, so 3 bytes are left empty before the int (after the first char). The size of a structure is rounded up to a multiple of its largest member alignment, so 3 more bytes follow the last char — laid out in an array, the next element’s int must keep its alignment too. Put the members largest first (int value; char tag; char flag;) and it becomes 8 bytes (chapter 47, “The first surprise of sizeof”). With a million elements, the difference is several MiB.
Answer 8-2. (to the exercise) Both are wrong. If there is even one initialiser, every member not written is default-initialised — numbers to 0, pointers to null (§6.7.11). So one {0} zeroes every member however many there are, and { .retries = 3 } fills the rest with 0 too. Members get garbage values only when a variable with automatic storage duration has no initialiser at all (struct config c;). In C23 the empty initialiser {} does the same (chapter 47, “Zeroing the whole thing”).
Answer 8-3. (to the exercise) memcmp compares representations — not only the members but the padding bytes too. The value of padding is not fixed, so “different” can come out even when the members are equal. If “equal” came out, the padding happened to match; that is not a contract. For the same reason a structure must not be hashed whole. The cure is a function that compares member by member (chapter 47, “Then compare them with memcmp”).
Answer 8-4. (to the exercise) Four things go wrong, independently. The values in the padding are not fixed, so bytes you never wrote go out too (sometimes leaking information). The layout differs by compiler, options and platform, so two programs built from the same source exchange different bytes. On a machine with a different byte order (endianness) the same number is read backwards. Type sizes — long, size_t, pointers, enumerations — differ between 32 and 64 bits. Adding one member in the next version also breaks the file. Fix the format byte by byte and write and read it field by field (chapter 48, “Why a struct must not be stored or sent whole”; chapter 50).
Answer 8-5. (to the exercise) What was checked is the layout of this build. Even with the same size and offsets, a build on a machine with a different byte order lays the same value out in different bytes — endianness has to be pinned down separately. And this approach is honest only when you hold both builds, as between processes on the same machine. For a party whose build you do not hold, such as the other end of a network or a version several years on, go back to field-by-field serialisation (chapter 50).
Answer 8-6. (to the exercise) Accessing a float object as a uint32_t breaks the strict aliasing rule. The compiler is entitled to assume “writing a float and reading a uint32_t are different objects”, and at -O2 it reorders the two operations on that assumption — the classic “fine at -O0, wrong at -O2”. At a misaligned address it can even die on the spot on a strict machine. Write memcpy(&bits, &f, sizeof bits);. The compiler turns that into a single register move, so it is not slow either (chapter 49, chapter 38).
Answer 8-7. (to the exercise) The order in which bits are placed (from the low end or the high end) is implementation-defined. Whether a field may straddle a storage unit, and how much padding goes in, are also the implementation’s choice. So is the signedness of a plain int x : 1;. A file format or protocol has its byte and bit layout fixed by a specification, while a bit field’s layout is fixed by the implementation, so the moment the compiler or the machine changes, fields are read from the wrong places. Extract a format’s fields yourself with shifts and masks (chapter 49, “Bit fields”; chapter 53).
Answer 8-8. (to the exercise) When n is very large. If r->pos + n overflows and wraps round to a small number, the check passes. If you have kept pos from exceeding len, compare by subtraction — if (n > r->len - r->pos). That subtraction cannot overflow (chapter 50, “Compare by subtraction, not addition”). All the more so where a number chosen by the other side, such as a length field, is involved.
Answer 8-9. (to the exercise) One is “that many bytes really follow”; the other is “count * sizeof(struct item) does not overflow”. The first rule of deserialisation is to assume every byte of the input was chosen by an enemy. Having read a count, first work out an upper bound from the bytes left — if an item takes at least k bytes, the count cannot exceed the bytes left divided by k. Ask about overflow in the multiplication with ckd_mul. That stops the attack “it said a billion items, so allocate room for a billion” (chapter 50, “Security”).
Answer 8-10. (to the exercise) A sticky error. Put a bad flag in the reading cursor and set it the first time a read goes out of range. Once the flag is set, every later get_… does nothing and returns 0. Then you check r->bad once at the end instead of after every field. Gather the range checks into the cursor’s two functions (put_bytes on the writing side, take on the reading side) — write the check separately in every function and one day one is missing (chapter 50, “Cursors”).
Answer 8-11. (to the exercise) For code that sweeps a few fields of many elements at once (updating only the positions of all particles), SoA wins — only the fields used come into the cache, and vectorisation is easy. For code that looks at all the fields of one element here and there (reading one customer’s whole record), AoS is better — one element gathers in one cache line. Code that inserts and removes elements often also favours AoS. The first thing to ask is how big the data is — if it fits in the cache (a few hundred elements), changing the layout gains almost nothing. And measure before changing it (chapter 51).
Answer 8-12. (to the exercise) It depends on size. The rule of thumb is by value up to a couple of words, by const pointer beyond that. The choice is also a matter of contract: taken by value, “the original is not touched” is guaranteed by the syntax; taken by pointer, it is only promised with const (chapter 48). How much is actually copied is decided by that machine’s calling convention (chapter 66).

If the three functions change the same global, the result depends on the order and may differ between compilers and optimisation levels. If the order matters, split the statement and take the results into temporaries in order (chapter 52, the misconception “Higher precedence means computed first”).
Answer 9-2. (to the exercise) == binds tighter than &, so it computes a & (b == c) — a ANDed with the 0 or 1 that b == c gives. So have both an absolute error (for near zero) and a relative error (in proportion to size). The tolerance comes from the problem — the precision of the measurement, the error the computation accumulates, and where the result is used decide it (chapter 54).

A warning does not stop the build, so to enforce the check, raise it to an error with -Werror (or -Werror=unused-result). Answer 9-8. (to the exercise) d->len was dereferenced first. Optimisation deletes the check. The Linux kernel’s CVE-2009-1897 had this shape, and combined with an environment where the null page could be mapped at the time, it became a privilege-escalation vulnerability (chapter 56). Answer 9-9. (to the exercise) Undefined behaviour is behaviour on which the standard imposes no requirements — anything that happens conforms, and the compiler optimises on the assumption that it does not happen (signed overflow, null dereference, out-of-bounds array access). Unspecified behaviour is where the implementation chooses among possibilities the standard allows, without having to document the choice (the order in which function arguments are evaluated). Implementation-defined behaviour is chosen by the implementation, which must document it (right shift of a negative number, the signedness of char, the width of int). Answer 9-13. (to the exercise) unreachable() (from <stddef.h>) is a device by which you promise the compiler “this path is never executed”. Answer 10-1. (to the exercise) Unix-like systems pass on a child’s exit status using only the low 8 bits. So 300 shows as 300 − 256 = 44. Windows passes the 32-bit exit code through unchanged, so it does not truncate — the same program reports different statuses on different platforms. What the standard promises portably is only 0 or EXIT_SUCCESS (success) and EXIT_FAILURE (failure). If you want to tell kinds of failure apart, choose values within 0–255 and document them (chapter 59).
Answer 10-2. (to the exercise) #include pastes the header’s text in place. When two files include it, each translation unit gets its own definition of the same function, and the linker stops with a multiple definition. A header’s job is to carry the contract (declarations), not the implementation — put int clamp(int v, int lo, int hi); in the header and the definition in one .c file. The exceptions are things each translation unit may have its own copy of: static inline functions, macros, and C23 constexpr constants (chapter 60 the two forms of inline are 5-6).
Answer 10-3. (to the exercise) A structure’s layout is baked into the caller’s code when the caller is built — its size, its members’ offsets, and any macros and inline functions using it. If only the library is rebuilt with the new layout, it and a caller built with the old layout read the same memory at different offsets, quietly using wrong values or crashing — the ABI is broken. Designing with an opaque pointer from the start prevents this. The header announces only the name struct ctx;, the shape stays hidden inside the library, and creating, using and destroying are offered only as functions. Then adding a member cannot break callers, because their code never knew the shape (chapter 61, “How to change it without breaking it”).
Answer 10-4. (to the exercise) Give a helper that need not be seen outside its file internal linkage with static — it then does not exist outside that translation unit and cannot collide. Answer 12-18. (to the exercise) It fails because the transformation is not one-to-one. In ISO-8859-1, 0xDF (ß) expands to two bytes, "SS", when upper-cased. The loop guard o < cap checks only that one byte of room remains, so whenever o == cap - 1 (for example, cap == 1 with input 0xDF, or cap == 2 with src = { 'a', 0xDF }), the branch writes the first 'S' to dst[cap - 1] and the second 'S' to dst[cap] — overflowing the buffer by one byte.

Check with subtraction before writing the two-byte branch. Raising the whole loop guard to cap - o >= 2 is another option, though it stops one byte early even when only one-byte ASCII characters remain.

size_t upcase_latin1(const unsigned char *src, size_t len,
                     unsigned char *dst, size_t cap)
{
    size_t i = 0, o = 0;
    while (i < len && o < cap) {
        unsigned char c = src[i];
        if (c == 0xDF) {
            if (cap - o < 2) break;
            dst[o++] = 'S';
            dst[o++] = 'S';
        } else if (c >= 'a' && c <= 'z') {
            dst[o++] = (unsigned char)(c - 'a' + 'A');
        } else {
            dst[o++] = c;
        }
        i++;
    }
    return o;
}

Inside while (i < len && o < cap) we already know o < cap, so o + 1 happens not to wrap here, but as a general form — especially when adding a multi-byte width o + n <= cap, or in a standalone guard written without o < cap — addition on the left can overflow size_t, wrap round to a small value, and pass the comparison. By contrast, once the invariant o <= cap is kept, the subtraction cap - o >= 2 (or cap - o < 2) can never overflow. Because breaking leaves unread input silently truncated, production code also needs an explicit signal to the caller (such as returning bool on truncation). Ruby’s November 2026 one-byte heap overflow in single-byte case conversion (GHSA-34m4-m9fh-gqp5, CVE-2026-132825) had this exact shape, and the fix changed the loop guard to to_end - to > 1 (chapter 87, chapter 57, chapter 50).

Answer 14-1. (to the exercise) A program that stops, stops where the cause is. Code that ignores failure carries the wrong value into the next calculation and the next function, and by the time the problem shows, it blows up far from its cause — and tracing back what first went wrong is much harder. And the premise “failure is rare” is wrong to begin with. Files can be missing, input has typos, disks fill, networks drop. Every place a program touches the outside world is a point of failure (chapter 106 “fail early” is chapter 55).

Answer 14-2. (to the exercise) len was increased first, so if grow fails, the buffer is left claiming “there are n more bytes of data” — where there is garbage, or memory never allocated. Even if the caller sees the failure and moves on, the buffer is already broken. Do the things that can fail first, and change the state only after they succeed:

bool append(struct buf *b, const void *src, size_t n)
{
    size_t need;
    if (ckd_add(&need, b->len, n)) return false;   /* check the size sum for overflow first */
    if (!grow(b, need)) return false;              /* on failure b is unchanged */
    memcpy(b->data + b->len, src, n);
    b->len = need;                                 /* once, at the end */
    return true;
}

This is failure atomicity — on failure the state is as it was before the call. It is the minimum that lets a long-running program recover by “dropping this request and taking the next” (chapter 108, “What remains after a failure — failure atomicity”).

Wrap the header’s declarations in extern "C" only when read by C++:

#ifdef __cplusplus
extern "C" {
#endif
int mylib_init(int flags);
#ifdef __cplusplus
}
#endif

A C compiler does not define __cplusplus, so it does not see these lines (chapter 117, “How to mix them — extern "C"”).

Answer 15-7. (to the exercise) The C code is not wrong. In C, void * converts implicitly to any other object pointer type, and leaving the cast off malloc’s result is common practice. C++ does not allow that conversion. There are more places where the two languages part ways, such as the order of designated initialisers. So “C++ is a superset of C” is wrong — the two languages are siblings, not parent and child, and correct C often does not build as C++. In a header that both read, use only the subset that is right in both (chapter 117, “Put C code into a C++ compiler”).
Answer 15-8. (to the exercise) The boundary between public and internal should have been drawn from the start — so that what is a public promise is plain to see. Without a boundary, an internal function (circumstance, not contract) gains users, and after that there is no ground for saying “but it is internal”. People do not read comments. Draw the boundary with directories — public headers in include/, internals in src/ — and build rules can even stop outside code from including headers in src/. The Linux kernel splitting the declarations exposed to user space into include/uapi/ is an example (chapter 118, “The boundary between public and internal”).
Answer 15-9. (to the exercise) A rulebook is not a definition of “good code” but a contract to pay a certain cost to reduce certain risks. Banning dynamic allocation is the right rule where memory must never run out and run time must be predictable, as in a car’s braking system; in a text editor there is no reason to keep it. Follow a rulebook where it is required, and not otherwise. But reading it is worth it anywhere — each rule comes with “why this is forbidden”, so it can be read as a list of where practice has been hurt (chapter 117, “The industry’s rulebooks”).
Answer 15-10. (to the exercise) There is no single answer. Chosen from the judgements this book kept returning to: keep warnings on and sanitisers on in test builds. Arrays travel with their lengths, and bounds are checked explicitly. Report failure as a value, check return values, and do not leave state half-changed on failure. Give memory an owner, and do not let views and pointers outlive it. Treat numbers from outside as chosen by the other side, and ask about overflow in every size calculation. Judge by “is it right on the abstract machine”, not “it ran on my computer”, and write what was measured on one machine as an observation of that machine. Leave a test that fails first for every defect you fix (chapter 121, “The practices of modern C — one sheet of guidance”).
