57 A field guide to memory errors

What to know first

chapter 56, Undefined behaviour · UB, unspecified, implementation-defined

Looking back

Chapter 46 showed the three classic accidents of dynamic memory (leak, double free, use after free), chapter 39 showed out-of-bounds access, and chapter 49 showed non-value representations. Are these different accidents, or different faces of one root?

A. One root. A C object has a size, a lifetime, a type and a provenance, and a single access stays inside the contract only if it respects all four. An overflow breaks the size, a use after free breaks the lifetime, a punning accident breaks the type, and a pointer that wanders into the neighbouring variable breaks the provenance. The names run to dozens, but the broken promise is always one of four. This chapter sorts the accidents by those four and gathers them in one place.

The need for this chapter, and its context

Memory errors have turned up in almost every chapter of this book. Scattered, they become a list of things to be careful about, and lists, once memorised, are forgotten. They are gathered here because with a classification you can ask, even of an accident you have never seen, which promise it broke. Coming straight after Part IX has faced undefined behaviour, or UB (undefined behaviour), head on, we can now also point to the sentence of the standard each accident falls under.

By the end of this chapter

The accidents are sorted into four by the promise they break — size (buffer overflow), lifetime (leaks, dangling pointers, double free), initialisation and type (indeterminate values, non-value representations, strict aliasing, alignment) and provenance (provenance, overlap). Each gets its name, what is wrong with it, its place in the standard, a case that really happened, the tool that catches it and the design that prevents it. At the end the memory-related UB is collected in one table, and what the tools cannot see is written down as well.

The questions this chapter answers

  1. If each accident has a different tool, what should be switched on first?

57.1 What a memory error is — four promises#

A memory error is an access to an object that breaks one of that object’s promises. It is also called a memory-safety bug. The standard has no such word — it simply writes “undefined behaviour” for each accident separately. So this chapter first sorts by what was broken.

Chapter 36 defined an object as “a region of memory that holds a value”. Four things attach to that region.

The four are independent. A read inside the size is still an error if the lifetime has ended, and a read inside the lifetime is still an error if the type is wrong. So when you ask “is this access right?”, you ask four times — is that byte inside the region, is the region still alive, may it be read with this type’s eyes, and did this pointer come from that region?

★ And all four share one consequence. Breaking any of them is undefined behaviour (chapter 56). There is no promise that the program dies on the spot, and no promise that a strange value comes out. That is why the demonstrations in this chapter do not run programs outside the contract and print their results; they print only what the tool called the error.

57.2 Breaking the size — buffer overflow#

A buffer overflow is writing past the end of a container. The bytes that overflow do not vanish; they overwrite whatever was next to it. Going past the end in the reading direction is called an out-of-bounds read. The off-by-one, the write that overwrites a neighbour and the read through which someone else’s memory leaks out were each shown in chapter 39. Here they are regrouped by kind and by defence.

57.2.1 What overflows — five kinds#

The fourth row is where an integer accident turns into a memory accident. n * size is size_t arithmetic, so it is not UB when it overflows; it quietly wraps around (chapter 6). As a result the allocation succeeds, and the program starts writing as if n elements fit. That is why C23′s checked arithmetic (chapter 91) belongs wherever sizes are multiplied.

57.2.2 Why it is dangerous — it is not only data that is overwritten#

An overflow does not only overwrite neighbouring variables. A function’s stack frame also stores the address to return to when the function ends (chapter 66). Overflowing a local array can reach that address, and then, at the moment the function ends, the program goes wherever the overwritten value points. If the input can decide that value, the person who sent the input decides where the program goes. That was the road the Morris worm took in 1988 (chapter 43).

This book does not cover how that road is walked. One thing is worth knowing — a buffer overflow does not end with one wrong value; it is an accident that can hand the flow of the program to someone else. That is why the defences below are stacked in layers.

57.2.3 The layers of defence#

Defence is not a single layer. The upper layers keep overflows from happening; the lower layers keep an overflow that did happen from spreading.

Two of the middle layers can be checked with one program. A program that strcpys seventeen bytes into an 8-byte container was built three ways and run.

examples-en/memory-errors/guards/overflow.c

/* Buffer overflow --- strcpy 17 bytes (including the null) into an 8-byte container.
 * The source string is chosen at run time, so the compiler cannot notice in advance. */
#include <stdio.h>
#include <string.h>

int main(int argc, char **argv)
{
    (void)argv;
    char name[8];
    const char *src = argc > 5 ? "ok" : "0123456789abcdef";
    strcpy(name, src);              /* a function that does not take the container's size */
    printf("copied %zu bytes into an 8-byte buffer\n", strlen(name) + 1);
    return 0;
}

Output

no protection              ran to the end: copied 17 bytes into an 8-byte buffer
-fstack-protector-strong   stopped: *** stack smashing detected ***: terminated
-D_FORTIFY_SOURCE=3 -O2    stopped: *** buffer overflow detected ***: terminated

The first line is the most frightening line in this section. The build without protection ran to the end without incident and calmly reported seventeen bytes in an eight-byte buffer. The nine bytes that overflowed overwrote something; it simply was not used again in this run. The build with the stack protector stopped where the function ends, because it saw the canary had changed. The _FORTIFY_SOURCE build stopped earlier — at the very call to strcpy — because the compiler knew that name has size 8 and substituted a version of strcpy that checks the size.

Platform note. The messages the two defences print are glibc’s

*** stack smashing detected *** and *** buffer overflow detected *** are printed by the GNU C library. The results above came out the same on x86-64 Linux (Debian, glibc) with GCC 14.2 and Clang 19.1. With other C libraries or operating systems the messages differ, and so do the defences switched on by default — most distributions put the stack protector and _FORTIFY_SOURCE into their default build settings, but when you call gcc yourself they are usually off.

57.2.4 Carrying the length along#

The second layer of defence is design. The trouble with strcpy(dst, src) is that dst is a single pointer, so the receiving side does not know the size of the container. Functions that take the size separately (strncpy, snprintf) expect the caller to write the size correctly. If you make the pointer, the length and the capacity into one bundle, every write passes through one of the bundle’s functions, and the checking gathers in that one place.

examples-en/memory-errors/span.c

/* A buffer that carries its length --- one shape that prevents overflow *by structure*.
 * Pass a single pointer and the receiver does not know the size of the container (strcpy's problem).
 * Pass pointer and length as one bundle, and every write is checked in the same place. */
#include <stdckdint.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct {
    char  *data;
    size_t len;     /* bytes written */
    size_t cap;     /* size of the container */
} buf;

/* Grow the container if there is no room. On failure, false --- the old contents stay as they were. */
static bool reserve(buf *b, size_t extra)
{
    size_t need;
    if (ckd_add(&need, b->len, extra)) return false;    /* refuse if the length computation overflows */
    if (need <= b->cap) return true;

    size_t cap = b->cap ? b->cap : 8;
    while (cap < need)
        if (ckd_mul(&cap, cap, 2)) return false;

    char *p = realloc(b->data, cap);    /* receive the result in another variable first */
    if (p == NULL) return false;        /* on failure b->data is still alive (C23 7.24.3.7p3) */
    b->data = p;
    b->cap  = cap;
    return true;
}

static bool append(buf *b, const char *s)
{
    size_t n = strlen(s);
    if (!reserve(b, n)) return false;
    memcpy(b->data + b->len, s, n);
    b->len += n;
    return true;
}

/* Size computation when borrowing an array of n --- if n * size overflows, a small block comes back. */
static void *alloc_array(size_t n, size_t size)
{
    size_t bytes;
    if (ckd_mul(&bytes, n, size)) return NULL;
    return malloc(bytes);
}

int main(void)
{
    buf b = {0};
    const char *words[] = {"length ", "travels ", "with ", "the ", "pointer"};
    for (size_t i = 0; i < sizeof words / sizeof words[0]; i++)
        if (!append(&b, words[i])) { free(b.data); return 1; }
    printf("%.*s\n", (int)b.len, b.data);
    printf("len %zu, cap %zu\n", b.len, b.cap);
    free(b.data);

    void *huge = alloc_array(SIZE_MAX / 2, 4);  /* the product overflows size_t */
    printf("alloc_array(SIZE_MAX / 2, 4): %s\n", huge ? "got a block" : "refused (size overflow)");
    free(huge);
    return 0;
}

Output

length travels with the pointer
len 31, cap 32
alloc_array(SIZE_MAX / 2, 4): refused (size overflow)

Three places are worth reading. reserve computes “current length + added length” with ckd_add and the size to grow to with ckd_mul — the size computation overflow (the fourth row of Table 57.2) is stopped here. The result of realloc is first received in another variable. On failure the old block stays as it was (C23 7.24.3.7); receiving straight into b->data would lose the only address of the old block at the moment of failure — a leak. The last line asks for an array of SIZE_MAX / 2 elements to show a product that overflows. Without the check, malloc would have returned a small block as a success.

The shape is not new. Length-prefixed strings (Pascal strings), the slices of other languages and C++‘s std::span are all the same idea. C simply has no such type in the standard, and it can be made from one structure as above (the proven of chapter 96 takes that road).

In practice. One == — Cloudbleed (2017)

In February 2017 Cloudflare’s HTML parser, while rewriting web pages, read past the end of a buffer and sent what it read out in responses. What leaked were HTTP headers, cookies, POST data and values used for authentication from other sites passing through the same machines. Because search engines had cached those responses, the company had to purge 770 URIs from the caches. The earliest leak went back to September 2016.

The cause was one end check in code generated by a parser generator (Ragel).

/* generated code */
if ( ++p == pe )
    goto _test_eof;

The check waits for the moment p becomes equal to the end pe. When a page ended in an unfinished tag the parser took an error path, and that path forgot the step that moves p back by one. So p reached this check already equal to pe; ++p made it pe + 1, and the “equal moment” was passed by. From then on p kept reading outside the buffer. The incident report puts it briefly — had the check been >= rather than ==, jumping over the buffer end would have been caught. The report states that the bug was not in Ragel itself but in Cloudflare’s use of it. Write end checks as “have we not gone past” rather than “have we arrived”.1

In practice. One backslash — sudo’s Baron Samedit (2021)

sudo, which lends administrator rights, had a heap buffer overflow hidden in it for nine and a half years. When running in shell mode, if an argument ended with a single backslash (\), the loop that copies arguments read the null terminator after the backslash as “an escaped character” and copied beyond it. An ordinary sudo invocation escapes backslashes beforehand and never reached this path, but invoked as sudoedit -s it turned shell mode on without the escaping. The result was a vulnerability through which any local user — even one not in sudoers — could gain administrator rights (CVE-2021-3156). The bug came in with a change of July 2011.2

The two cases share one thing: the rule for finding the end was wrong. In one it was ==; in the other, “what follows a backslash is always a character”. A design that carries the length does not search for the end — it knows it from the start.

57.3 Breaking the lifetime#

An object’s lifetime is set by its storage duration (chapter 45). An automatic object ends with its block; a dynamic object ends with free. Lifetime accidents go in two directions — touching it after it ended (dangling), and not ending what should be ended (leaking).

57.3.1 Leaks — losing the last pointer#

A memory leak is losing the last pointer to a borrowed block, so that the block can never be returned. In the standard’s eyes it is not an accident — not returning memory is not UB, and when the program ends the operating system usually reclaims everything. So in a short command-line tool it does no harm. The harm is to programs that run for a long time. In servers, daemons, editors and browsers a leak eats memory bit by bit until it finally brings the machine to a halt.

Most leaks take three shapes: overwriting (p = malloc(...) twice with no free in between), early return (an error path leaves without what it borrowed earlier), and confusion about ownership (the receiver and the giver each think “the other will return it”). The third is why the ownership rule of chapter 46 is needed.

★ “Memory grows even though nothing leaks” is a different problem. Fragmentation is covered in chapter 94.

57.3.2 Dangling pointers and use after free#

A dangling pointer is a pointer that still points at an object whose lifetime has ended. Reading or writing through it is a use after free. As chapter 46 showed, the allocator soon hands a returned slot to another request, so a use after free reads or overwrites someone else’s object that is there now.

The standard adds one more sentence here. The second paragraph of C23 6.2.4 says that “if a pointer value is used in an evaluation after the object the pointer points to (or just past) reaches the end of its lifetime, the behavior is undefined”, and goes on: “the representation of a pointer object becomes indeterminate when the object the pointer points to (or just past) reaches the end of its lifetime”.3

Neither a read nor a write is needed. After free(p), using the value of p at all — comparing it with == to another pointer, converting it to an integer to print it — is outside the contract. The bits are unchanged, but the value is no longer a “value”. The rule has a nickname — pointer zap. The reason for a sentence this strict is the same as the provenance of chapter 38. A pointer is not just a number called an address; it is a value that also carries which object it came from, and when that object disappears, half of the value disappears. The practical conclusion is simple: do not use a freed pointer again — not even to compare it. The habit free(p); p = nullptr; is worth half as much as it seems precisely because nullptr is a “value”.

57.3.3 Double free and invalid free#

The contract of free is two sentences. Passing a pointer it never gave out (the middle of a block, a stack address, an address already returned) is UB.4 The allocator keeps bookkeeping in front of and behind its blocks (chapter 94), so returning the wrong address corrupts the bookkeeping, and corrupted bookkeeping poisons every allocation after it, one by one. That is why the place where the accident happens and the place where it blows up are often far apart.

In practice. One GIF — WhatsApp’s double free (2019)

WhatsApp for Android used the decoder of the open library android-gif-drawable to preview GIFs in its gallery. The decoder reused its buffer when frames had the same size and reallocated it when they did not. A GIF that cleverly mixed frames of different sizes made the same buffer be freed twice (CVE-2019-11932). All the user had to do was open the gallery. The fixed versions are library 1.2.18 and WhatsApp 2.19.244.5

The lesson reaches people who never write C directly. Even when an app’s code is written in another language, one C library that decodes a picture decides the memory safety of the whole app.

57.3.4 The address of an automatic object that has ended#

A function’s local variable ends its lifetime when the function ends. Return its address and the receiver holds a dangling pointer from the very start.

int *make(void)
{
    int v = 7;
    return &v;          /* the compiler warns --- and the warning is right */
}

GCC and Clang both warn about this shape. Store the address in a variable once and return that, and the warning goes away but the accident stays. The same trap comes in less visible shapes — the compound literal &(struct pt){1, 2} inside a block ends its lifetime when the block ends, and an array member of the temporary object created by a call to a function returning a structure ends when that expression ends.

57.3.5 realloc — the old pointer and size zero#

realloc frees the old object and returns a new one. The new address may equal the old one, but that is chance; the old pointer and all its aliases become dangling. Going on using the old pointer in the belief that “I only grew it” is the most common realloc accident.

And one place changed in C23. realloc(p, 0) is now undefined behaviour.6 Before, implementations split between “free the block and return null” and “return a block of size zero”, and because you could not know which, both leaks and double frees happened. Rather than choosing one, the committee moved it outside the contract. To shrink to zero, call free.

In practice. The share of use after free — memory safety in numbers

Two large codebases have counted their own vulnerabilities. They count differently, so the two figures must not be merged.

  • Microsoft: in a talk at BlueHat IL in February 2019, about 70% of the CVEs it fixed each year were memory-safety problems, a share that had stayed almost the same for twelve years.
  • Chromium: an analysis of 912 high- or critical-severity security bugs affecting the stable channel since 2015 found about 70% were memory-safety problems, and half of those were use after free.7

That the figures are close is close to chance — one is all fixed CVEs, the other high-severity bugs. What the two say together is one thing: in large programs written in C and C++, the biggest security problem is not computation but memory.

57.4 Breaking initialisation and type#

57.4.1 Indeterminate values — reading a place never written#

An uninitialised automatic variable and a block just returned by malloc hold an indeterminate value (chapter 24). Reading it comes with no promise about what value comes out, and for some types the read itself is UB. The reason it is not “just some garbage value” is optimisation. The compiler treats a variable never written as something that may be any value, and may give two different answers when the same variable is read twice.

57.4.2 Non-value representations — bits that are not a value of the type#

For some types not every bit pattern is a value. For bool only 0 and 1 are values; if the place holds 2, that bit pattern is a non-value representation. Earlier standards called it a “trap representation” — reading it might spring a trap. C23 changed the name and kept the rule: reading it through an lvalue that is not of character type is UB.8 Chapter 49 met this trap when reading another member of a union. Writing the byte in with memcpy is inside the contract; the contract is left at the moment it is read as bool.

Conversely a structure or union as a whole is never a non-value representation (paragraph 6 of the same subclause). Whatever its padding bytes hold, copying a structure whole is safe. But the values of those padding bytes are unspecified, so comparing two structures with memcmp can report structures with equal values as different (chapter 47).

In practice. Fixing the warning — Debian’s OpenSSL (2006–2008)

There is a strange case in which an uninitialised read became an accident by being fixed. In 2006 a Debian maintainer saw the memory checker Valgrind report “use of uninitialised memory” in OpenSSL’s random-number code (md_rand.c). The function the warning pointed to was called from two lines.

MD_Update(&m,buf,j);              /* line 247 */
...
#ifndef PURIFY
    MD_Update(&m,buf,j); /* purify complains */   /* line 467 */
#endif

The lower line could already be switched off, with a comment saying a checking tool complained, and it really was harmless — it mixed an uninitialised buffer in as a bonus. To silence the warning, the maintainer removed the MD_Update call. But the upper line (inside RAND_add) was the one that put real entropy supplied by the caller into the random pool. With it gone, the only unpredictable input left in the pool was the process ID, and under Linux’s default settings at the time process IDs were below 32,768. As a result ssh-keygen on Debian and its derivatives could produce only 32,767 keys of each type and size. This was announced only on 13 May 2008 (DSA-1571, CVE-2008-0166).9

The lesson is not to distrust tools. The place the tool points to and the place where the accident is can differ, and removing a warning is a different job from removing its cause. Mixing an uninitialised buffer in was already outside the contract, so the right repair was to switch off only the lower line, the one that mixed it in as a bonus.

57.4.3 Strict aliasing — seen again#

Chapter 14 called strict aliasing “the act of telling the compiler something untrue as if it were true”. The rule is the seventh paragraph of C23 6.5.1. An object’s stored value may be accessed only through an lvalue matching the object’s effective type; the exceptions are the same type with signedness or qualifiers changed, a structure or union that has it as a member, and character types.10 The effective type of a declared object is its declared type; for an object with no declared type, such as a malloc block, it is the type of the lvalue last used to store into it.

How this rule meets optimisation can be seen in one short program. A function taking an int * and a float * was given the same address twice.

examples-en/memory-errors/aliasing/alias.c

/* Strict aliasing --- what happens when an int lvalue and a float lvalue designate the same place.
 * The two parameters of store_both have *different types*. The compiler may read this as "an int object
 * and a float object do not overlap" (C23 6.5.1p7) --- and on that premise not read *ip again. */
#include <stdio.h>

[[gnu::noinline]] static int store_both(int *ip, float *fp)
{
    *ip = 1;
    *fp = 0.0f;
    return *ip;             /* compiler: "a float store cannot change an int -> 1" */
}

int main(void)
{
    int x = 42;
    int r = store_both(&x, (float *)&x);    /* outside the contract: writes an int object as a float */
    printf("returned %d, x is now %d\n", r, x);
    return 0;
}

Output

-O0                        returned 0, x is now 0
-O2                        returned 1, x is now 0
-O2 -fno-strict-aliasing   returned 0, x is now 0

The build with optimisation off and the -fno-strict-aliasing build read x again after the second write and returned 0. The -O2 build returned 1 — it trusted that “writing a float cannot change an int” and did not read *ip again. Yet, as x is now 0 on the same line shows, memory already holds 0. The value the function returned and the memory say different things. GCC 14.2 and Clang 19.1 produced these three lines identically.

-fno-strict-aliasing is the option that turns this assumption off. The Linux kernel builds with it switched on in its top-level Makefile (KBUILD_CFLAGS += -fno-strict-aliasing) — kernel code has many idioms that break the rule, so it chose to give up the optimisation the rule offers. The same place also has -fno-delete-null-pointer-checks (CVE-2009-1897 of chapter 56 is the reason). An option widens the contract only for that build. Move the code to another build and the accident comes back.

57.4.4 The same bits through other eyes, inside the contract#

When the same bits have to be read as another type — looking at the bits of a floating-point number, or turning bytes received from the network into an integer — there are two roads inside the contract.

examples-en/memory-errors/pun.c

/* Two roads *inside the contract* to read the same bits as another type --- memcpy and a union.
 * A pointer cast (*(uint32_t *)&f) breaks strict aliasing. These two do not. */
#include <stdint.h>
#include <stdio.h>
#include <string.h>

static uint32_t bits_by_memcpy(float f)
{
    uint32_t u;
    static_assert(sizeof u == sizeof f, "float must be 32 bits here");
    memcpy(&u, &f, sizeof u);       /* only moves bytes --- one instruction once optimised */
    return u;
}

static uint32_t bits_by_union(float f)
{
    union { float f; uint32_t u; } pun = { .f = f };
    return pun.u;                   /* reading another member: allowed in C (C23 6.5.3.4 footnote) */
}

int main(void)
{
    const float samples[] = {1.0f, -2.5f, 0.1f};
    for (size_t i = 0; i < sizeof samples / sizeof samples[0]; i++) {
        float f = samples[i];
        printf("%5.2f  memcpy 0x%08x  union 0x%08x\n",
               (double)f, (unsigned)bits_by_memcpy(f), (unsigned)bits_by_union(f));
    }
    return 0;
}

Output

 1.00  memcpy 0x3f800000  union 0x3f800000
-2.50  memcpy 0xc0200000  union 0xc0200000
 0.10  memcpy 0x3dcccccd  union 0x3dcccccd

memcpy only moves bytes, so it breaks no type rule. With optimisation on, the compiler turns the call into a single instruction — it costs almost nothing. Reading another member through a union is allowed in C (a footnote to C23 6.5.3.4 calls this “type punning” and says only that the result may be a non-value representation).11 C++ does not allow it, so for a header shared by both languages memcpy is the safe side. The pointer cast *(uint32_t *)&f is the same accident as the aliasing demonstration above.

57.4.5 Misalignment#

Converting a pointer to a type that needs stricter alignment is UB at the moment of the conversion if the result is not correctly aligned.12 This holds even without a dereference (chapter 38).

The reason this accident lives so long is x86. x86 usually handles misaligned integer reads quietly. So code that reads *(uint32_t *)(buf + 1) from a byte buffer runs fine on x86 for years, then dies with a bus error the day it moves to a machine that demands alignment (older ARM, some RISC-V, digital signal processor DSP chips). It is not safe on x86 either — if the compiler, assuming “this is aligned”, chooses a vector instruction that requires alignment, it dies on the spot on x86 too. To take a value out of a byte buffer, use the memcpy above.

57.5 Breaking provenance — provenance seen again#

Chapter 38 showed provenance. A pointer carries, together with the number called an address, the origin “which object it came from”, and pointer arithmetic cannot leave that object’s range (up to one past the end). So even if two neighbouring variables x and y sit side by side in memory and &x + 1 == &y comes out true, changing y through &x + 1 is an error — the address is the same, the provenance is not. As that chapter showed, an optimising compiler assumes that “two pointers of different provenance do not overlap” and moves code accordingly.

Seen through provenance, the other accidents of this chapter read differently. A buffer overflow is reaching a neighbouring object with one object’s provenance, and a use after free is using the provenance of an object that is gone. On a machine whose hardware carries provenance itself (CHERI), both are stopped the same way — by the bounds and validity tag attached to the pointer (Appendix N).

There are two places where the provenance rule bites even inside one object.

  • Overlapping copies. memcpy is UB when the two regions overlap.13 When they can overlap, as when shifting elements within an array by one, use memmove. The two parameters of memcpy carry restrict — a promise that “these two do not overlap”, which the implementation trusts in choosing a fast copy.
  • The promise of restrict. If you put restrict on your own function, you promised that while the function runs, an object modified through one pointer is not reached through another (chapters 27 and 39). Breaking it is the same UB.

57.7 What the tools catch, and what they miss#

For each accident a small program was written and run with sanitizers on (chapter 18). The output below is the name the tool gave when each program ran. The demonstration is built to fail if a tool cannot name the expected error — so the table in the text is re-checked on every build. The source printed is one of them, the use after free.

examples-en/memory-errors/catalog/use_after_free.c

/* Breaking the lifetime, reading --- read a block that was already returned. */
#include <stdlib.h>

[[gnu::noinline]] static int peek(const int *p) { return *p; }

int main(void)
{
    int *p = malloc(sizeof *p);
    if (p == NULL) return 1;
    *p = 7;
    free(p);
    return peek(p);         /* the value of p is now indeterminate (C23 6.2.4p2) */
}

Most are caught by ASan (AddressSanitizer). ASan inserts a check before every memory access at build time and puts a poisoned zone (red zone) on both sides of every object. Overflows are caught by touching that zone, and use after free by keeping returned blocks in quarantine for a while and noticing the touch. Leaks are caught by LeakSanitizer, which scans at exit for blocks still reachable, and the 2 in a bool and the misalignment by UBSan.

★ The lines to notice are the two for uninit.c. ASan and UBSan do not look at uninitialised reads. The tool that does is MemorySanitizer (MSan), and on this machine only Clang had it — run the same script with Clang 19.1 and that line becomes MSan: use-of-uninitialized-value. MSan works properly only when the whole program (including the libraries it uses) is built with the same option, so in practice other tools such as Valgrind are also used to fill this gap.

The limits all the tools share are worth writing down too.

  • They see only the paths that ran. An accident on a line no test passed through is not caught.
  • They hardly see strict-aliasing violations. Build the aliasing demonstration above with ASan and UBSan and nothing is reported. This accident is found by reading the code.
  • They are slow. ASan makes execution roughly twice as slow and uses more memory. So it goes on in test builds and off in release builds. What guards release builds is the layered defence above.

A common misconception. “It ran fine on x86, so alignment does not matter”

That x86 handles misaligned reads is the kindness of that machine, not a promise of C. The same code dies on the spot on a machine that demands alignment, and on x86 too if the compiler picks an instruction that assumes alignment. In the standard’s eyes the contract is already broken the moment a misaligned pointer is formed. To take a value out of a byte buffer, use memcpy — on x86 it compiles to the same single instruction, so nothing is lost.

Q. If each accident has a different tool, what should be switched on first?

A. The first step is -fsanitize=address,undefined in test builds. It covers everything in this chapter’s tables except uninitialised reads at once. Second come warnings — switch on -Wall -Wextra and treat warnings as errors. Third come the defences of release builds — switch on -fstack-protector-strong and -D_FORTIFY_SOURCE (following the distribution’s defaults is enough). And the two things these three cannot see — strict aliasing and paths never run — are left to code review and tests.

57.8 Summary — one line per accident#

The last column leads into the next chapter. Catching accidents is the tools’ job, but keeping them from arising is the job of the design that decides who returns memory, and when. The next chapter covers that design — the habits and data structures for governing lifetime in C, and the ways other languages took this job from people and gave it to machines (reference counting and garbage collectors), with what they cost.
