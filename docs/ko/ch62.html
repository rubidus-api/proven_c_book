62 문자와 로케일 — <ctype.h>·<locale.h>·<wchar.h>

이 장이 기대는 것

9장 문자와 텍스트 · 글자와 인코딩

돌아보기

9장에서 문자는 코드표의 번호이고 인코딩은 그 번호를 바이트로 적는 방식 이라 했다. 그러면 isalpha('가') 같은 호출은 무엇을 묻는 것인가?

답. 잘못 던진 물음이다. <ctype.h>의 함수들은 한 바이트를 판정한다. UTF-8에서 “가”는 세 바이트이므로 애초에 인자로 들어갈 수 없고, 넣더라도 각 바이트를 따로 볼 뿐이다. 이 헤더는 아스키 시절의 도구이고, 여러 바이트 문자를 다루려면 와이드 문자 계열(<wctype.h>)이나 인코딩을 직접 다루는 코드가 필요하다.

이 장이 끝나면

한 글자를 다루는 함수들을 본다. 겉보기에 가장 단순한 헤더인데, C에서 가장 미묘한 함정 두 개가 여기 있다 — char를 그대로 넘기면 계약 밖 이라는 것과, 답이 로케일이라는 전역 상태에 달렸다는 것. 9장의 인코딩 이야기가 함수 차원에서 되돌아온다.

이 장에서 답할 질문

  1. 아스키만 쓰는 프로그램이라면 로케일과 와이드 문자는 몰라도 되는가?

62.1 첫 번째 함정 — char를 그대로 넘기지 않는다

examples/ch62/ctype.c

#include <stdio.h>
#include <ctype.h>
#include <limits.h>
#include <string.h>

/* ctype 함수는 int 를 받는다 — 그런데 그 int 는 char 가 아니다 */
int main(void)
{
    printf("CHAR_MIN = %d (이 기계의 char 는 %s)\n",
           CHAR_MIN, CHAR_MIN < 0 ? "부호 있음" : "부호 없음");

    /* 아스키 범위는 문제가 없다 */
    printf("isalpha('A') = %d, isdigit('7') = %d, isspace(' ') = %d\n",
           isalpha('A') != 0, isdigit('7') != 0, isspace(' ') != 0);

    /* 128 이상의 바이트가 문제다: char 로 넘기면 음수가 된다 */
    char bytes[] = { (char)0xC7, (char)0x41, 'A', '\0' };   /* CP949 '가' 의 첫 바이트 */
    printf("바이트 0xC7 을 char 로 담으면: %d\n", bytes[0]);

    /* 올바른 관용구: unsigned char 로 바꿔서 넘긴다 */
    printf("올바른 호출: isalpha((unsigned char)b) = %d\n",
           isalpha((unsigned char)bytes[0]) != 0);

    /* toupper/tolower 도 같은 규칙 */
    const char *s = "Hello, World!";
    char up[32];
    size_t i = 0;
    for (; s[i] && i + 1 < sizeof up; i++)
        up[i] = (char)toupper((unsigned char)s[i]);
    up[i] = '\0';
    printf("toupper 적용: [%s]\n", up);

    /* EOF 도 유효한 인자다 — 그래서 인자 타입이 int 다 */
    printf("isalpha(EOF) = %d (EOF 는 허용된 인자)\n", isalpha(EOF) != 0);
    return 0;
}

실행 결과

CHAR_MIN = -128 (이 기계의 char 는 부호 있음)
isalpha('A') = 1, isdigit('7') = 1, isspace(' ') = 1
바이트 0xC7 을 char 로 담으면: -57
올바른 호출: isalpha((unsigned char)b) = 0
toupper 적용: [HELLO, WORLD!]
isalpha(EOF) = 0 (EOF 는 허용된 인자)

<ctype.h>의 모든 함수는 int를 받는다. 그리고 표준이 요구하는 인자의 값은 unsigned char로 표현되는 값이거나 EOF다.

문제는 char가 부호 있는 구현이 흔하다는 데 있다(26장). 예제의 출력처럼 0xC7 바이트를 char에 담으면 −57이 되고, 그것을 그대로 isalpha에 넘기면 허용되지 않은 값을 넘기는 것이 된다 — 계약 밖이다. 실제 구현들이 대개 배열 색인으로 만들어져 있어서, 음수 인덱스로 배열 앞을 읽는 사고가 난다.

관용구는 하나다.

isalpha((unsigned char)c)
toupper((unsigned char)c)

EOF가 유효한 인자라는 점도 기억할 만하다 — 그래서 인자 타입이 char가 아니라 int인 것이다(58장의 fgetc 이야기와 같은 뿌리다).

반례. char를 그대로 넘기기

char *p = line;
while (*p) { if (isspace(*p)) ... ; p++; }   /* 0x80 이상 바이트에서 계약 밖 */

아스키만 들어온다는 보장이 없으면 반드시 변환한다.

while (*p) { if (isspace((unsigned char)*p)) ... ; p++; }

한글·일본어·유럽어 텍스트를 다루는 프로그램에서 이 한 줄이 실제 사고와 무사고를 가른다.

문. 아스키만 쓰는 프로그램이라면 로케일과 와이드 문자는 몰라도 되는가?

답. 당장은 그렇게 보이지만, 두 자리에서 발목이 잡힌다. 첫째, 프로그램은 대개 남의 입력을 받는다 — 파일 이름, 사용자 이름, 붙여 넣은 문자열에 한글이나 이모지가 섞이는 것을 막을 수 없다. 둘째, 로케일은 아스키 문자의 처리까지 바꾼다. 터키어 로케일에서 toupper('i')가 점 있는 대문자 İ가 되는 것이 유명한 사례이고, 소수점 기호가 쉼표가 되는 로케일에서는 printf("%f")의 출력마저 달라진다.

그래서 이 책의 권고는 “몰라도 된다”가 아니라 “기본 로케일을 벗어나는 순간을 의식하라”다. 79장의 UTF-8 뷰처럼 바이트를 그대로 다루는 설계가 이 문제를 가장 크게 줄여 준다.

62.2 두 번째 함정 — 로케일

<ctype.h>의 판정은 현재 로케일에 달렸다. 기본은 "C" 로케일이고, setlocale(LC_ALL, "")을 부르면 환경 변수가 정한 로케일로 바뀐다. 그 순간부터 isalpha가 참을 돌려주는 바이트의 집합이 달라질 수 있다.

로케일이 바꾸는 것은 문자 분류만이 아니다.

LC_NUMERIC이 특히 위험하다. 독일·프랑스 로케일에서는 소수점이 쉼표라, printf("%f", 3.14)가 3,140000을 찍고 strtod("3.14", …)는 3에서 멈춘다. 사람에게 보여 줄 숫자와 파일·프로토콜에 적을 숫자는 다른 규칙을 따라야 한다는 뜻이다.

실제 사례. 로케일이 데이터를 망가뜨린 무늬

같은 프로그램이 개발자의 기계(영어 로케일)에서는 3.14를 쓰고, 사용자의 기계(독일어 로케일)에서는 3,14를 쓰는 일이 실제로 반복해서 일어났다. CSV 파일이 열에 따라 파싱되지 않거나, 설정 파일을 저장한 뒤 다시 읽지 못하거나, 두 나라의 서버가 주고받는 JSON이 어긋나는 식이다.

처방은 분명하다. 기계가 읽을 숫자는 로케일에 의존하지 않는 경로로 다룬다 — "C" 로케일을 유지하거나, 직접 자리 표기법을 다루거나, 로케일 독립 함수를 쓴다. C11의 <uchar.h>와 여러 라이브러리가 이 문제를 피하려고 별도 경로를 두는 이유이기도 하다.

흔한 오해. “setlocale을 부르지 않으면 로케일 문제는 없다”

대체로 맞지만 예외가 있다. 프로그램이 쓰는 다른 라이브러리가 setlocale을 부를 수 있고(GUI 툴킷이 흔히 그런다), 그 순간부터 내 코드의 printf("%f")도 영향을 받는다. 게다가 로케일은 프로세스 전역이라 여러 갈래로 도는 프로그램에서는 경쟁이 된다. POSIX의 uselocale이나 newlocale 같은 스레드 지역 로케일이 그래서 생겼지만, 표준 C에는 없다.

62.3 와이드 문자 — <wchar.h>·<wctype.h>·<uchar.h>

C95가 wchar_t와 그 함수들을 들여왔다. 발상은 “한 글자를 한 단위로”였지만, 현실은 그 발상을 배신했다.

  • wchar_t의 크기가 구현마다 다르다. 리눅스는 4바이트(UTF-32에 가깝다), Windows는 2바이트(UTF-16이라 보조 평면 문자가 두 단위가 된다). 즉 “한 글자 = 한 wchar_t”가 어디서나 성립하지 않는다.
  • 변환 함수(mbstowcs 등)는 로케일에 의존한다. UTF-8 문자열을 다루려면 로케일이 UTF-8이어야 한다.
  • 그래서 이식성 있는 프로그램은 와이드 문자 대신 UTF-8 바이트열을 그대로 다루는 쪽을 택하는 경우가 많다.

C11이 보탠 <uchar.h>의 char16_t·char32_t는 크기가 고정이라 이 문제를 피한다. 다만 라이브러리 지원이 얇아, 실무에서는 여전히 전용 유니코드 라이브러리를 쓰거나 직접 다룬다.

플랫폼 노트. Windows와 UTF-16

Windows API의 “W” 계열 함수는 UTF-16(wchar_t)을 받는다. 그래서 Windows 프로그램은 경계에서 UTF-8과 UTF-16을 오가야 하고, 이 변환이 실패할 수 있다는 사실(짝이 맞지 않는 서러게이트)을 잊으면 안 된다. 17장의 인코딩 사슬 이야기가 API 층에서 재현되는 자리이며, 제12부의 문자열 장에서 다루는 u16 계열이 정확히 이 다리를 놓는 도구다.
