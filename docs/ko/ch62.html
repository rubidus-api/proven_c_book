62 진단과 제어 — <errno.h>·<assert.h>·<signal.h>·<setjmp.h>

이 장이 끝나면

프로그램이 잘못됐을 때 쓰는 네 헤더를 한자리에서 본다. 오류 번호를 담는 전역, 계약 위반을 잡는 단언, 바깥에서 날아오는 신호, 그리고 스택을 건너뛰는 점프. 45장에서 세운 “오류는 값이다”라는 규율이 왜 그렇게 중요한지, 대안들의 실제 모습을 보면 분명해진다.

돌아보기

45장에서 C의 오류 통보 방식이 반환값·전역 상태·프로그램 중단 셋뿐이라 했다. 그러면 errno라는 전역은 정확히 언제 믿을 수 있는가?

답

실패가 확인된 직후에만 믿을 수 있다. 표준의 규칙은 두 겹이다. 첫째, 성공한 호출도 errno에 값을 넣을 수 있다 — 그래서 “0이 아니면 실패”가 아니라 “함수가 실패를 알린 뒤에 이유를 읽는” 순서여야 한다. 둘째, 값은 다음 라이브러리 호출이 언제든 덮어쓸 수 있다 — 그래서 읽었으면 즉시 저장한다. 이 두 규칙이 전역 상태로 오류를 나르는 설계의 대가다.

62.1 errno — 전역으로 오류를 나르는 대가

examples/ch62/errno_demo.c

#include <stdio.h>
#include <errno.h>
#include <string.h>
#include <stdlib.h>

int main(void)
{
    /* ① 성공한 호출도 errno 를 건드릴 수 있다 — 그래서 직전에 0 으로 놓는다 */
    errno = 0;
    FILE *ok = fopen("errno_demo_tmp.txt", "w");
    printf("성공 후 errno = %d\n", errno);
    if (ok) { fputs("x", ok); fclose(ok); }

    /* ② 실패하면 errno 에 이유가 남는다 */
    errno = 0;
    FILE *f = fopen("/definitely/not/here.txt", "r");
    if (!f) {
        printf("실패: errno=%d, strerror=[%s]\n", errno, strerror(errno));
        perror("perror 출력");     /* 앞에 문맥을 붙여 stderr 로 */
    }

    /* ③ 중간에 다른 호출이 끼면 errno 가 덮인다 */
    errno = 0;
    f = fopen("/definitely/not/here.txt", "r");
    int saved = errno;                    /* 곧바로 저장해 둔다 */
    printf("정리 작업 중...\n");           /* printf 가 errno 를 바꿀 수 있다 */
    printf("저장해 둔 errno=%d (%s)\n", saved, strerror(saved));

    /* ④ strtol 은 errno 로 범위 초과를 알린다 */
    errno = 0;
    long v = strtol("999999999999999999999", NULL, 10);
    printf("strtol 범위 초과: errno==ERANGE? %s (값=%ld)\n",
           errno == ERANGE ? "예" : "아니오", v);

    remove("errno_demo_tmp.txt");
    return 0;
}

실행 결과

perror 출력: No such file or directory
성공 후 errno = 0
실패: errno=2, strerror=[No such file or directory]
정리 작업 중...
저장해 둔 errno=2 (No such file or directory)
strtol 범위 초과: errno==ERANGE? 예 (값=9223372036854775807)

출력이 규칙을 그대로 보여 준다. 호출 직전에 0으로 놓고, 실패를 확인한 뒤 읽고, 다른 일을 하기 전에 저장한다. printf 한 줄이 사이에 끼는 것만으로 값이 바뀔 수 있기 때문이다.

errno는 변수처럼 보이지만 매크로다. 여러 갈래로 도는 프로그램에서는 갈래마다 다른 값을 봐야 하므로, 구현이 스레드 지역 저장소를 가리키는 매크로로 정의한다.

함수하는 일메모
strerror(n)오류 번호 → 문장★ 정적 버퍼. 스레드 안전하지 않다
perror(s)s: 이유를 stderr로문맥 문자열을 붙이는 습관
strerror_r호출자 버퍼에 채움POSIX. 두 가지 판이 있어 혼란
strerror_s같은 취지부속서 K(63장)

표준이 이름을 정한 오류 번호는 셋뿐이다 — EDOM(정의역), ERANGE(범위), EILSEQ(인코딩). 나머지 ENOENT·EACCES 같은 것들은 POSIX나 플랫폼이 정한다. 즉 errno 값을 비교하는 코드는 이식성이 그만큼 좁아진다.

62.2 assert — 계약을 코드로 적는 가장 싼 방법

45장에서 배운 그 매크로다. 규칙을 다시 못박으면 이렇다.

  • assert는 프로그램 내부의 불변식을 확인한다. “여기까지 왔다면 p는 널이 아니다” 같은 것.
  • 바깥에서 온 값을 검사하는 데 쓰지 않는다. 사용자 입력·파일 내용·네트워크 데이터는 if로 검사하고 오류로 처리한다.
  • NDEBUG가 정의되면 통째로 사라진다(17장). 그래서 부수효과가 있는 표현식을 넣으면 안 된다.

✗ assert 안에 일을 시키기

assert(fclose(f) == 0);      /* 릴리스 빌드에서는 fclose 자체가 사라진다 */
assert(i++ < n);             /* i 가 증가하지 않는 빌드가 생긴다 */

검사와 부수효과를 분리한다.

int rc = fclose(f);
assert(rc == 0);
(void)rc;                    /* 릴리스에서 미사용 경고 방지 */

C11은 static_assert(C23에서는 _Static_assert 없이도 쓸 수 있다)를 들여왔다. 컴파일 시간에 확인하므로 실행 비용이 0이고, sizeof나 상수 조건에 쓴다.

static_assert(sizeof(int) >= 4, "이 코드는 32비트 int 를 가정한다");

62.3 신호 — 바깥에서 날아오는 방해

<signal.h>는 프로그램 밖에서 오는 사건(Ctrl+C, 잘못된 메모리 접근, 산술 오류)을 다룬다. 표준이 정한 신호는 여섯 개뿐이고(SIGINT·SIGSEGV· SIGFPE·SIGILL·SIGABRT·SIGTERM), 나머지는 플랫폼의 것이다.

핵심은 처리기 안에서 할 수 있는 일이 거의 없다는 사실이다. 표준이 허용하는 것은 이 정도다.

  • volatile sig_atomic_t 타입 변수에 값을 대입하기
  • _Exit나 abort 부르기
  • 같은 신호의 처리기를 다시 설정하기

printf도, malloc도 부를 수 없다 — 그 함수들이 중간까지 실행된 상태에서 신호가 끼어들 수 있기 때문이다(비동기 신호 안전이 아니다). 실무의 관용구는 “처리기는 깃발만 세우고, 실제 처리는 주 흐름에서”다.

static volatile sig_atomic_t stop = 0;
static void on_int(int sig) { (void)sig; stop = 1; }
/* main 루프에서: while (!stop) { ... } */

⚠ “SIGSEGV를 잡아서 프로그램을 계속 돌릴 수 있다”

잡을 수는 있지만 계속 돌릴 수는 없다. SIGSEGV는 이미 계약이 깨진 뒤에 오는 신호다(46장의 정의되지 않은 동작). 처리기에서 정상으로 복귀하면 같은 명령이 다시 실행되어 무한히 반복되거나, 손상된 상태 위에서 계속 달린다. 디버깅용으로 스택 추적을 남기고 _Exit로 끝내는 것이 현실적인 최선이고, “복구”는 애초에 그 접근을 하지 않도록 고치는 것이다.

62.4 비지역 점프 — setjmp/longjmp

setjmp로 지금 자리를 기억해 두고, 나중에 깊은 곳에서 longjmp로 되돌아 오는 장치다. 예외가 없는 언어에서 예외 비슷한 것을 만들려는 시도이고, 그만큼 대가가 크다.

  • longjmp 뒤에도 값을 믿을 수 있는 지역 변수는 volatile로 선언한 것뿐이다. 나머지는 레지스터에 있었을 수 있어 값이 미정이다.
  • 정리 코드가 실행되지 않는다. 건너뛴 함수들이 잡아 둔 자원(파일·메모리)은 그대로 샌다. C++의 소멸자 같은 장치가 없기 때문이다.
  • setjmp를 부른 함수가 이미 반환했다면 longjmp는 계약 밖이다.
  • 신호 처리기에서 longjmp로 빠져나오는 것은 특히 위험하다.

그래서 실무의 결론은 대개 “쓰지 않는다”이다. 쓰는 자리가 있다면 인터프리터의 오류 복구나 파서의 깊은 실패처럼, 정리할 자원이 아레나 하나로 묶여 있는 구조에 한한다(제12부의 아레나가 그 조건을 만든다).

◉ 오류 처리 방식이 만든 코드의 모양

같은 프로그램을 세 가지 방식으로 짜면 모양이 이렇게 갈린다.

  • 반환값 + errno: 호출마다 if가 붙고 오류 경로가 눈에 보인다. 번거롭지만 흐름이 정직하다.
  • setjmp/longjmp: 본문은 깔끔해지지만 자원 정리를 사람이 전부 기억해야 하고, 어디로 튀는지 코드에서 보이지 않는다.
  • goto cleanup: C 코드베이스에서 가장 널리 정착한 절충이다. 실패하면 한 곳으로 모여 역순으로 정리한다. 리눅스 커널이 이 무늬를 관행으로 못박았고, 29장에서 “goto는 절제해서”라고 한 그 절제된 용법이 바로 이것이다.

세 방식 모두 “실패를 값으로 다루고, 정리를 잊지 않는다”는 같은 문제를 푼다. 제12부의 라이브러리는 여기에 네 번째 답 — 실패를 타입으로 만드는 것 — 을 얹는다.
