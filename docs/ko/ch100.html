돌아보기

쉼표로 구분된 정수를 읽어 합계를 찍는 도구를 짜 달라는 요청이 들어왔다. 앞의 44장 에서 strtol 계열로 정수 하나를 안전하게 읽는 법도 배웠고, fgets 로 한 줄을 읽는 법도 안다. 그러면 곧바로 main.c 를 열어 반복문을 쓰면 되지 않는가?

답. 곧바로 코딩에 들어가면 요청에 빠진 구멍을 코드가 메운다 — 그것도 소리 없이. 10,x,30 이 오면 멈춰야 하는지 10 만 더하고 끝내야 하는지, 10,20, 같은 끝 쉼표는 괜찮은지, 빈 입력에는 0 을 찍고 성공해야 하는지 오류로 끝내야 하는지 아무도 말하지 않았기 때문이다.

★ 명세 없이 짠 코드는 모호한 자리마다 「아무 값이나 내고 종료 0 으로 끝나는」 쪽으로 흐른다. 그래서 이 부의 첫 장은 구현이 아니라 완료 조건과 실패 조건을 표에 못박는 일에서 시작한다.

이 장의 필요성과 맥락

지금까지는 한 장마다 하나의 개념이나 헤더를 뜯어보았다. 이 제13부 100–105장 는 그 지식을 하나의 작은 도구에 끝까지 엮는 자리다. 첫 장인 여기서는 코드를 짜기 전에 명세부터 적는다 — 44장 의 파싱 규율, 55장 의 계약 사고, 59장 의 종료 상태 약속이 실제 요구 문서에서 어떤 칸으로 변하는지 눈으로 확인하기 위해서다.

이 장이 끝나면

이 장을 마치면 두 가지를 손에 쥔다. 첫째, 정책 없이 급히 짠 첫 초안이 엉뚱한 입력 앞에서도 왜 태연히 성공으로 끝나는지 실물로 확인한다. 둘째, sumcsv 여섯 장이 끝까지 지킬 입력·출력·종료 상태·완료 조건 계약을 정해, 뒤따르는 파서·산술·입출력·시험 장이 무엇을 구현해야 하는지 한눈에 놓는다.

이 장에서 답할 질문

  1. 빈 입력 "" 의 합을 0 으로 주면 왜 안 되는가?
  2. atoi 대신 strtoll 을 썼는데도 첫 초안이 왜 실패를 못 잡았는가?

100.1 정책 없는 첫 초안이 저지르는 일#

설명을 듣기 전에, 실제로 많은 사람이 처음 짤 법한 sumcsv 초안을 먼저 돌려 본다. 이 코드는 44장 에서 본 parse_int 를 거의 그대로 가져와 fgets 와 쉼표 전진 루프에 끼운 것이다.

examples/sumcsv/01-spec/sumcsv_naive.c

/* 44장에서 가져온 파서를 곧바로 합산 루프에 끼운 첫 초안 ---
   정책이 없으면 잘못된 입력에도 합계와 종료 상태 0 이 나온다. */
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <stdbool.h>

struct parse_i64 {
    bool        ok;
    long long   value;
    const char *rest;
};

static struct parse_i64 parse_int(const char *text)
{
    struct parse_i64 r = { .ok = false, .value = 0, .rest = text };
    if (!text) return r;

    errno = 0;
    char *end = nullptr;
    long long v = strtoll(text, &end, 10);
    if (end == text || errno == ERANGE) return r;

    r.ok = true;
    r.value = v;
    r.rest = end;
    return r;
}

int main(void)
{
    char line[256];
    if (!fgets(line, sizeof line, stdin)) {
        printf("0\n");
        return 0;
    }

    long long sum = 0;
    const char *p = line;
    for (;;) {
        struct parse_i64 r = parse_int(p);
        if (!r.ok) break;
        sum += r.value;
        p = r.rest;
        if (*p == ',') p++;
        else break;
    }
    printf("%lld\n", sum);
    return 0;
}

실행 결과

  "10,20,30"     -> stdout=60     exit=0
  "10,x,30"      -> stdout=10     exit=0
  "10,20,"       -> stdout=30     exit=0
  "10,,30"       -> stdout=10     exit=0
  "" (EOF)       -> stdout=0      exit=0
  "   "          -> stdout=0      exit=0

한 줄의 코드는 컴파일 경고도 없고 10,20,30 에 60 을 낸다. 그러나 나머지 다섯 줄의 출력을 보라.

  • "10,x,30" — 두 번째 필드가 숫자가 아닌데도 10 을 출력하고 종료 0 으로 끝났다. parse_int 가 x 에서 실패하자 루프가 그냥 break 로 빠져나와 그때까지의 합계만 인쇄했기 때문이다.
  • "10,20," — 끝의 쉼표 뒤에 아무것도 없는데 30 과 종료 0 이 나왔다.
  • "10,,30" — 가운데 필드가 비었는데 10 과 종료 0 이 나왔다.
  • "" 와 " " — 숫자가 하나도 없는 빈 입력과 공백 줄을 모두 합계 0, 종료 0 으로 통과시켰다.

★ 프로그램이 멈추지 않고 끝까지 돌아 버린다 — 바로 거기가 위험하다. 셸 스크립트나 다른 파이프라인이 ./sumcsv < data.csv 를 불렀을 때, 종료 코드 0 을 받고 표준 출력에서 10 을 읽으면 그 뒤의 x,30 이 버려졌다는 사실을 알 방법이 없다.

흔한 오해. “정상 입력만 잘 돌면 나머지는 나중에 막으면 된다”

오류 정책을 뒤로 미루면 나중에 막기 어려운 쪽으로 코드가 굳는다. 첫 초안에서 fgets 가 실패하면 0 을 내기로 한 결정, 파싱이 멈추면 break 로 빠져 나와 그때까지의 sum 을 찍기로 한 결정은 이미 동작하는 규약이 된다.

더 큰 문제는 어떤 경우가 오류인지조차 구현 전에 합의하지 않으면, 시험 코드를 쓸 수도 없다는 것이다. 시험은 코드가 아니라 명세에 대고 짜는 물건이다.

100.2 요청의 빈칸을 질문으로 채우기#

“쉼표로 구분된 정수를 더해 달라”는 한 줄 요청에는 결정되지 않은 질문이 다섯 갈래 이상 숨어 있다. 구현을 시작하기 전에 이 질문마다 예와 아니오를 못박는다.

왜 1판에서는 한 줄만 받기로 좁혔는가. 여러 줄, 열 번호 선택, 따옴표 감싼 필드까지 한꺼번에 넣으면 파서·버퍼 수명·상태 관리가 뒤엉킨다. 먼저 한 줄 판의 경계와 시험을 빈틈없이 세운 뒤, 마지막 장(105장)에서 여러 줄과 따옴표로 넓히며 무엇이 달라지는지 겪는 편이 낫다.

★ 표의 마지막 행 — 실패 시 표준 출력은 0바이트 — 을 눈여겨본다. 부분 합계라도 먼저 찍고 오류가 나면 뒤늦게 종료 코드만 1 로 바꾸는 도구는, 출력을 파이프로 받는 다음 단계에 깨진 숫자를 흘린다. 계산과 검사를 모두 끝낸 뒤에만 표준 출력에 한 번 쓴다.

문. 빈 입력 "" 의 합을 0 으로 주면 왜 안 되는가?

답. 합을 0 으로 정하는 설계 자체가 틀린 것은 아니다 — 다만 명시적인 선택이어야 한다. 파일이 0바이트로 깨졌거나 생성 스크립트가 비어 버린 상황에서 조용히 0 과 종료 0 이 나오면 장애가 가려지기 쉬워서, 1판 계약에서는 빈 입력과 공백만 있는 줄을 모두 거부한다. 어느 쪽을 고르든 문서와 시험이 같은 말을 해야 한다.

문. atoi 대신 strtoll 을 썼는데도 첫 초안이 왜 실패를 못 잡았는가?

답. 44장 에서 배운 대로 parse_int 는 “문자열 앞에서 정수 하나를 떼어 내고 남은 자리 rest 를 돌려주는 부품”이지, 줄 전체가 유효한 쉼표 목록인지 검사하는 함수가 아니기 때문이다. 부품을 옳게 썼어도 그 앞뒤의 구분자 정책과 줄 끝 검사까지 호출자가 채우지 않으면, 바깥 계약은 그대로 뚫린다.

100.3 코드보다 먼저 쓰는 완료 조건#

계약을 정했다면 코드 파일을 열기 전에 “무엇을 통과해야 이 도구가 끝난 것인가”를 종이에 적어 둔다. 부록 O 가 권하는 첫 프로젝트 명세와 같은 틀이다.

이 여섯 줄이 곧 앞으로 다섯 장의 목차다. 101장 에서 구문·구분·범위 파서를 짜고, 102장 에서 <stdckdint.h> 로 누적 넘침과 실패 원자성을 세우며, 103장 에서 긴 줄·둘째 줄·쓰기 실패를 막는다. 그다음 104장 에서 여러 파일과 Makefile 과 골든 시험과 자동 시험을 묶어 체크리스트 전부를 자동으로 돌린다.
